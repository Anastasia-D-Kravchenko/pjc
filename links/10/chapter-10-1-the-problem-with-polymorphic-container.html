Chapter 10.1 - The problem with polymorphic container

Posted May 7, 2025
By Filip Kwiatkowski
5 min read

Most common uses of polymorphism

Polymorphism shines when we are preparing a piece of code that accepts a hierarchy of types supporting a given range of behaviors.

In graphical applications (GUI), we deal with collections of widgets, where a widget can be a button, text, or a separate container holding other widgets. Each widget knows how to draw itself — sometimes this involves drawing text, sometimes creating a button-like shape, and sometimes drawing all sub-widgets (in the case where the element is an additional collection of widgets).

In computer games, any entity is often represented by some common base class. For example, all elements in games created in the Unity engine, which need to store data or be identifiable, must inherit from the Entity class. A similar situation occurs in the Unreal Engine, where we have classes like Actor or Object.

In both of these cases, we deal not only with individual functions that accept a polymorphic parameter but mainly with polymorphic containers. That is, containers that store objects of different types.

This somewhat contradicts our notion of type safety. After all, in Java as well as in C++, we cannot suddenly place an integer in an array storing strings. While this is true, in Java, we have learned a way to circumvent this problem. Collections (including arrays; and in C++, all containers) can indeed store objects of different types, provided that those types have a common base class.

Polymorphic container

#include <algorithm>    // std::ranges::shuffle
#include <random>       // std::random_device
#include <vector>

#include <fmt/base.h>

struct Animal {
    virtual auto makeSound() const -> void { }
};

struct Cat : Animal {
    auto makeSound() const -> void override {
        fmt::println("Meow");
    }
};

struct Dog : Animal {
    auto makeSound() const -> void override {
        fmt::println("Woof");
    }
};

auto main() -> int {
    auto animals = std::vector<Animal>();

    for (auto i = 0; i < 5; i++) animals.push_back(Cat());
    for (auto i = 0; i < 5; i++) animals.push_back(Dog());

    std::ranges::shuffle(animals, std::random_device());

    for (auto const& animal : animals) {
        animal.makeSound();
    }
}

Naturally, we expect that running this program will result in the string Meow being displayed five times and the string Woof being displayed five times, in random order. However, this is not the case. But before we see why, it’s worth quickly explaining what we’re doing in the code above:

1
2

for (auto i = 0; i < 5; i++) animals.push_back(Cat());
for (auto i = 0; i < 5; i++) animals.push_back(Dog());

Here we added five Cats and five Dogs to the vector.

1

std::ranges::shuffle(animals, std::random_device());

Here we are shuffling the order of elements in the vector (we’re “shuffling it” — like shuffling a deck of cards)1.

Now let’s move on to the output. Unfortunately, to our surprise, we won’t see anything.

That’s because due to object slicing, we won’t be operating on objects of type Cat or Dog, but on “raw” Animal.

But how’s that? We used references even in the for () loop in line 31 to prevent this problem.

That’s correct. Unfortunately, this problem occurred earlier. Specifically, in line 24.

std::vector stores its elements in adjacent memory locations. Therefore, it needs to know how much memory each of them occupies. It knows this through the specification of the template argument (<Animal> in std::vector<Animal>). However, this has certain consequences — for each of its elements, it only reserves space for Animal, not for the entire Cat or Dog. Just in the declaration of the container, we doomed ourselves to object slicing.

So how do we fix it?

Use references… again?

Good guess, but unfortunately, it won’t work. Changing the container declaration from this:

1

auto animals = std::vector<Animal>();

To this:

1

auto animals = std::vector<Animal&>();

(additional & character after Animal).

This will result in about 230 lines of compilation error. Not much can be gleaned from them, so let’s just remember the summary:

Containers storing references cannot be created.

Why?

In a large (and incomplete but sufficient for now) nutshell — because references must be initialized upon creation and cannot be “reassigned” later. The vector internally performs operations that — if we had a vector of references — would require creating them in an “unconnected” state. Then it would have to “reassign” them to other objects. And — as we’ve already mentioned — that’s not possible.

To understand why std::vector performs such operations, one must understand how it works internally. It utilizes dynamically allocated memory, which is the subject of the next subsection.
