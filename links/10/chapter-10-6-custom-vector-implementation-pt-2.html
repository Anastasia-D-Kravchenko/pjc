namespace pjc {
    template <typename T>
    class Vector {
        int size_ = 0;
        T* data_ = nullptr;

    public:
        auto push_back(T const& newElement) -> void {
            size_ += 1;

            auto buffer = new T[size_];
            for (auto i = 0; i < size_ - 1; i++) {
                buffer[i] = data_[i];
            }
            buffer[size_ - 1] = newElement;

            data_ = buffer;
        }

        auto size() -> int {
            return size_;
        }

        auto print() -> void {
            for (auto i = 0; i < size_; i++) {
                fmt::print("{} ", data_[i]);

The issue arises when .push_back() overwrites data_ = buffer;, essentially “forgetting” about the previous array. The memory occupied by this array leaks, meaning it’s still marked as reserved for our program but is inaccessible from our perspective.

Surprisingly, this can be addressed quite easily. We just need to delete the unnecessary array just before forgetting about it:

1

auto push_back(T const& newElement) -> void {
    size_ += 1;

    auto buffer = new T[size_];
    for (auto i = 0; i < size_ - 1; i++) {
        buffer[i] = data_[i];
    }
    buffer[size_ - 1] = newElement;

    delete[] data_; // new operation
    data_ = buffer;
}

delete[] data_ releases the memory pointed to by data_. There’s no need to worry about the situation where .push_back() is used for the first time because even if data_ indeed points to nullptr then, both delete nullptr and delete[] nullptr guarantee that they will do nothing.

Here, we should use delete[], not delete, because we allocated memory with new[], not new. Using delete on memory allocated with new[] or delete[] on memory allocated with new results in Undefined Behavior (UB).

Now our memory is correctly deallocated. Right?

Well… almost. Consider this code:

Here we create a vector, add one element to it (thus creating a single-element array), and then forget about it. Who “cleans up” this array?

Nobody. And it should be cleaned up! Fortunately, we already know a tool that will help us in this situation — the destructor.

When local vector objects are destroyed, their destructor will be invoked. It’s enough to add it to the pjc::Vector template and within its body, free the memory:

        }

}

Yes. But not from the other issues. What happens in the following scenario?

Let us inspect a memory view just before the assignment of first = second:

We haven’t implemented the = (assignment) operator, so C++ provided it for our template. It performs primitive field assignments, overriding .size_ and .data_ with the corresponding fields of the vector on the right-hand side of the assignment operator.

This means that the operation first = second will result in the following situation:

So memory leak?

Yes, but that’s not the only problem. The array with the value 1 leaks memory, but when we exit the main() function block, we will invoke the destructors of first and second, resulting in the execution of code corresponding to these operations:

delete[] first.data_;
delete[] second.data_;

Memory must be deallocated, but only once. The double deletion problem results in Undefined Behavior.

We want to handle this case correctly. Let’s implement the assignment operator for our template:

namespace pjc {
    template <typename T>
    class Vector {
        int size_ = 0;
        T* data_ = nullptr;

    public:
        // added operator=
        auto operator=(Vector const& other) -> void {
            delete[] data_;
            data_ = other.data_;
            size_ = other.size_;
        }

        auto push_back(T const& newElement) -> void {
            size_ += 1;

            auto buffer = new T[size_];
            for (auto i = 0; i < size_ - 1; i++) {
                buffer[i] = data_[i];
            }
            buffer[size_ - 1] = newElement;

            delete[] data_;
            data_ = buffer;
        }

        auto size() -> int {
            return size_;
        }

        auto print() -> void {
            for (auto i = 0; i < size_; i++) {
                fmt::print("{} ", data_[i]);
            }
        }

        ~Vector() {
            delete[] data_;
        }
    };
}

Here just after first = second we encounter the following situation:

graph LR
  A(first.data_) --> D
  C(second.data_) --> D["｜ 10 ｜"]

Now we call first.push_back(20). .push_back() creates a new array, copies the elements, and deletes the old one. That means we’ll have the following situation:

graph LR
  A(first.data_) --> B["｜ 10 ｜ 20 ｜"]
  C(second.data_) --> D:::hidden

Why so?

Because we executed delete[] on the array that first.data_ originally pointed to just before we overwritten this pointer with the memory address of a larger array (to which we added 20). second.data_ was pointing to the same array — unlucky coincidence.

Of course, it’s not just “unlucky coincidence”, but poorly designed behavior in pjc::Vector. The operator= shouldn’t simply copy the pointer. This is known as a shallow copy, and it’s usually not what we want. The operator= should allocate memory independently, rather than making an object “spy” on what another has created.

The problem manifests itself in the next line, second.push_back(30). .push_back() sees that second.size_ was 1 just now, so it needs to copy something from the original second.data_. The issue is that this pointer points to the array we deleted from memory.

A correct implementation of the assignment operator (=) will fix this issue. It should perform a deep copy:

auto operator=(Vector const& other) -> void {
    delete[] data_;
    size_ = other.size_;

    // deep copy
    data_ = new T[size_];
    for (auto i = 0; i < size_; i++) {
        data_[i] = other.data_[i];
    }
}

Here, operator= will be in a situation where other.data_ and .data_ are the same. And we start by doing delete[] data_, which will render other.data_ (which is the same as .data_) unusable!

Let’s fix this problem:

auto operator=(Vector const& other) -> void {
    // we perform operations only if this is not a self-assignment
    if (this != &other) {
        delete[] data_;
        size_ = other.size_;

        data_ = new T[size_];
        for (auto i = 0; i < size_; i++) {
            data_[i] = other.data_[i];
        }
    }
}

this is a pointer to the object for which the method is called. Its usage is equivalent to this in Java.

And since this points to the object for which the method is called, it means it holds the address of that object. &other returns the address of the right operand of the assignment. If these addresses are identical, we’re dealing with assigning the object to itself. We perform operations only if it’s not self-assignment.

Is that all, finally?

Yes.

No. A similar problem will emerge for the copy constructor of the vector. It means that we must implement it correctly too.

Vector(Vector const& other) : size_(other.size_), data_(new T[other.size_]) {
    for (auto i = 0; i < other.size_; i++) {
        data_[i] = other.data_[i];

}

As we can see, we had to implement all of the three special member functions from The Big Three — the copy constructor, the assignment operator and the destructor. It is usually the case that if we must implement either of those, we most likely need to implement them all. After all, they are all part of The Big Three.

If we need to implement any method that is part of The Big Three, we most likely need to implement the rest of them too.

namespace pjc {
    template <typename T>
    class Vector {
        int size_ = 0;
        T* data_ = nullptr;

    public:
        Vector() = default; // needs to be present, because otherwise the only valid constructor would be the below one
    
        Vector(Vector const& other) : size_(other.size_), data_(new T[other.size_]) {
            for (auto i = 0; i < other.size_; i++) {
                data_[i] = other.data_[i];
            }
        }

        auto operator=(Vector const& other) -> void {
            if (this != &other) {
                delete[] data_;
                size_ = other.size_;

                data_ = new T[size_];
                for (auto i = 0; i < size_; i++) {
                    data_[i] = other.data_[i];
                }
            }
        }

        auto push_back(T const& newElement) -> void {
            size_ += 1;

            auto buffer = new T[size_];
            for (auto i = 0; i < size_ - 1; i++) {
                buffer[i] = data_[i];
            }
            buffer[size_ - 1] = newElement;

            delete[] data_;
            data_ = buffer;
        }

        auto size() -> int {
            return size_;
        }

        auto print() -> void {
            for (auto i = 0; i < size_; i++) {
                fmt::print("{} ", data_[i]);
            }
        }

        ~Vector() {
            delete[] data_;
        }
    };
}

We have the first explanation of the problem — you cannot create a pointer to a reference. Why? Because a reference is not formally an object. It’s an alias to some other object. The C++ language doesn’t accept constructions that attempt to treat a reference as a full-fledged object.

Additionally, we have another problem. Even if it were possible to form a pointer to a reference, the implementation of the vector itself would have to use operations that would be erroneous for references. Let’s take another look at the implementation of .push_back():

Now, let’s see what would happen if T were, for example, a reference to an int (int&). We would perform the operation auto buffer = new T[size_], which would allocate an array of references to ints of size size_.

Well, what’s the problem?

But what would these references be connected to? We can’t have references that are not bound to anything.

Indeed…

Moreover, later they would need to be rebound (in a loop).

This means that to create a correctly functioning polymorphic container, we need references (to avoid object slicing) that can be unbound and rebound.

Such a reference is called a pointer.

In a way, you can think of pointers as nullable references that can be rebound.

Actually, pointers can do a bit more, but for now, this simplification is sufficient for us.

So let’s use pointers and see how a correct polymorphic container should look like — in the next chapter.
