Vector of pointers to the base class

#include <algorithm>    
#include <random>       
#include <vector>

#include <fmt/base.h>

struct Animal {
    virtual auto makeSound() const -> void { }
};

struct Cat : Animal {
    auto makeSound() const -> void override {
        fmt::println("Meow");
    }
};

struct Dog : Animal {
    auto makeSound() const -> void override {
        fmt::println("Woof");
    }
};

auto main() -> int {
    auto animals = std::vector<Animal>();

    for (auto i = 0; i < 5; i++) animals.push_back(Cat());
    for (auto i = 0; i < 5; i++) animals.push_back(Dog());

    std::ranges::shuffle(animals, std::random_device());

    for (auto const& animal : animals) {
        animal.makeSound();
    }
}

Unfortunately, due to object slicing, this code didn’t store objects of type Cat or Dog in the animals vector. It stored “raw” animals, so calling .makeSound() effectively did nothing.

Object slicing was the problem we were solving by avoiding creating copies. We achieved this using references. Now, however, we know that both references and pointers can work on original objects (helping us avoid copying). Since we can’t have a vector of references, let’s use pointers. Let’s simplify the creation and addition of elements to the vector at the same time:

auto main() -> int {
    auto animals = std::vector<Animal*>();  // vector of pointers
    auto c1 = Cat();
    auto c2 = Cat();
    auto d1 = Dog();
    auto d2 = Dog();
    
    animals.push_back(&c1);
    animals.push_back(&c2);
    animals.push_back(&d1);
    animals.push_back(&d2);
}

As you can see, we’re no longer using std::vector<Animal>, but std::vector<Animal*> (Animal vs Animal*). We’re adding pointers to the vector, not the animals themselves (obtained by applying the & operator, which gives us memory addresses of objects, i.e., pointers to them).

Now let’s call the .makeSound() method on all objects (pointers) in animals:

    }
}

It immediately catches our eye that we’re using the -> operator. Why isn’t there a dot (.) there?

That’s because if instead of ptr->makeSound() we used ptr.makeSound(), we would encounter the following error: request for member 'makeSound' in 'ptr', which is of pointer type 'Animal* const' (maybe you meant to use '->' ?).

In C++, when we want to access a method or a field of a complex object, we use the dot operator (.). The exception is when we’re dealing with a pointer. In that case, instead of the dot, we use the arrow (->). This is a remnant from the C language.

This way, we managed to create a correctly functioning polymorphic container!

Difficulty in managing object lifetimes

Unfortunately, the fact that the example above is correct doesn’t mean that we won’t break anything. Not only does using pointers require mastering complex syntax, but it also requires ensuring the correctness of our programs from multiple perspectives. We need to:

  • ensure that the pointers on which we execute delete / delete[] always point to “their own” data (data that no one else will manage, i.e., call their delete / delete[]) — which involves the issue of shallow copy;
  • remember that they can point to nothing (nullptr);
  • remember that a pointer doesn’t extend the object’s lifetime.

This last point is quite interesting. Let’s look at an example that is somewhat the opposite of a memory leak. First, let’s create a function getIntPointer():

#include <fmt/base.h>

auto getIntPointer() -> int* {
    auto localInt = 1337;
    return &localInt;
}

auto main() -> int {
    auto ptr = getIntPointer();
    fmt::println("{}", *ptr);
}

It’s very easy to overlook a huge problem that this code exhibits — we have UB here because we’re trying to access a non-existing object!

How so?

Let’s pay attention to the fact that localInt is a local variable with automatic lifetime. This means that when we exit the block in which it was created, it will cease to exist. Returning a pointer to a local variable is an error because we’ll be operating on the address of an object that has been destroyed.

Running the above code can do anything. That’s how it is with Undefined Behavior. It might display 1337, it might display 0, it might display nothing, or the program might crash.

But why are we talking about this? Well, while returning a vector like this poses no problem:

auto getVector() -> std::vector<int*> {
    auto local1 = 1;
    auto local2 = 2;
    auto local3 = 3;

    auto vec = std::vector<int*>{&local1, &local2, &local3};
    return vec;
}

The vector takes care of the lifecycle of the elements it holds. When it holds ints, it appropriately copies them “into itself”. However, when it holds pointers, the objects it “cares for” are the pointers themselves, not the objects they point to. In the latter example, all local variables disappear when the return statement is executed. These three pointers held by the returned vector will be unusable.

This is a significant problem because — as it may seem — it means we cannot create factory methods for polymorphic containers:

auto makeAnimalsVector() -> std::vector<Animal*> {
    auto animals = std::vector<Animal*>();

    auto c = Cat();
    auto d = Dog();

    animals.push_back(&c);
    animals.push_back(&d);

    return animals;
}

In this example, the returned vector contains pointers to the already non-existing cat and dog. That’s a huge problem. Can it be addressed?

Yes, it can. We just need to use something we already know. We just need to ensure that exiting the function that creates these two objects does not result in their deletion. We just need to ensure that this cat and dog are not objects with automatic lifetimes, but rather objects with dynamic lifetimes. We need to use dynamic memory allocation:

auto makeAnimalsVector() -> std::vector<Animal*> {
    auto animals = std::vector<Animal*>();

    auto c = new Cat(); // new!
    auto d = new Dog(); // new!

    animals.push_back(c); // no &
    animals.push_back(d); // no &

    return animals;
}

Everything looks great!

But wait… We’re using new, but where is the delete..?

…A valid point.

Cat and Dog were created using new, so somewhere we should use delete. It would be mistaken to assume that the vector will “clean up” these objects on its own. It does indeed use dynamic memory allocation (just like our pjc::Vector), but it’s only concerned with its own pointer to the array of elements. These elements — in our case — are pointers. The vector simply performs delete[] on its array of pointers. It doesn’t execute delete on each of them. To avoid memory leaks, you should save the vector and execute delete on its elements:

auto main() -> int {
    auto const animals = makeAnimalsVector();

    for (auto const ptr : animals) {
        ptr->makeSound();
    }

    for (auto const ptr : animals) {
        delete ptr;
    }
}

It’s… incredibly inconvenient. Isn’t there a way to simplify this a bit?

There is. You should use smart pointers, which will be covered in the next chapter.

It’s very hard to notice this problem, but… we have UB in this code example.

Why?

Because the created objects of type Cat and Dog are not properly destroyed. And it’s not entirely the fault of delete. To illustrate this problem, let’s add destructors to our class hierarchy that inform us when an object is being destroyed:

struct Animal {
    virtual auto makeSound() const -> void { }

    ~Animal() { fmt::println("Animal destroyed"); }
};

struct Cat : Animal {
    auto makeSound() const -> void override {
        fmt::println("Meow");
    }

    ~Cat() { fmt::println("Cat destroyed"); }
};

struct Dog : Animal {
    auto makeSound() const -> void override {
        fmt::println("Woof");
    }

    ~Dog() { fmt::println("Dog destroyed"); }
};

As we know, the order of destructor calls within the same block is the reverse of the order of constructor executions. First, we created a, which is of type Animal. The action of its destructor can be observed in line 5 of the output. Then we created c, which is of type Cat. Its destructor displayed what we observed in lines 3-4. Finally, we created d, which is Dog. Its destruction was called first — we can see this in the first two lines of the output.

The destructor of the derived class, at the end of its execution, calls the destructor of the base class. This is the reverse situation compared to what we can observe with constructors. The constructor of the derived class first calls the constructor of the base class.

And here we have a problem. We have Cat and Dog, but their destructor didn’t get called. Only the destructor from their base class was called.

We can deduce the reason why this happened. Hint: it’s because we have a pointer to the base class, and we call delete on it, which invokes the destructors.

We’ve encountered a similar situation before, when having access to a derived object through a variable of the base type (then a reference), we called an overridden method, but only the version from the base class was invoked. Object slicing is not the issue here. The issue is the lack of a virtual method!
