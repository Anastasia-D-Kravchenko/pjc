Abbreviated function template syntax

Let’s revisit the template from the previous part of the lecture:

template <typename T, typename U>
auto printBigger(T const& first, U const& second) -> void {
    if (first > second) {
        std::cout << first;
    } else {
        std::cout << second;
    }
    std::cout << '\n';
}

When type placeholders are used in such a straightforward manner (we’ll learn about the not-so-straightforward way later), they can be replaced with a syntax called abbreviated function template. This is achieved using the auto keyword. The code from the listing above can be written as follows:

1
2
3
4
5
6
7
8

auto printBigger(auto const& first, auto const& second) -> void {
    if (first > second) {
        std::cout << first;
    } else {
        std::cout << second;
    }
    std::cout << '\n';
}

As you can see, this is evidently a simpler way. We omit some fancy template or typename. So why did we start with this more difficult way of creating templates? There are two reasons:

  1. The template <...> notation is more commonly used because the auto notation doesn’t allow for many useful constructs1.
  2. With the introduced typename T, specifically the placeholder T, it’s easier to grasp the idea of “matching”, especially in the case of arguments of different types.

Limitations of Abbreviated Templates

As mentioned earlier, auto, which replaces the template <...> syntax, has certain limitations. In the previous part of the chapter, for the printBigger() template we discussed, we used two placeholders (typename T, typename U) to allow the template to accept arguments of different types.

However, what if we want to enforce accepting two arguments of the same type? For example, we want to avoid any kind of conversion (both in the body) and ensure that the arguments have exactly the same type. Using the “original” template notation, this is very straightforward:

1
2

template <typename T>
auto acceptsTwoSameTypeArguments(T first, T second) -> void { }

However, achieving this with auto is impossible very difficult. It requires using tools that we will only learn about much later.

In such situations, it’s advisable to consider using the classic way of creating templates.

Lambdas and templates

As we already know, lambdas have a unique, unknown type to us. So how is it that an algorithm like std::ranges::count_if() is able to accept a lambda? After all, to write a function that takes some argument, you need to specify its type, right?

Right. Except that std::ranges::count_if() isn’t a function. It’s a function template2. It introduces a placeholder for the type that accepts any range and another placeholder for the type that accepts a predicate. A predicate that can be of any type.

To understand the example more precisely, let’s implement our own count_if():

#include <vector>

#include <fmt/ranges.h>

namespace pjc {
    template <typename T>
    auto count_if(std::vector<T> const& source, auto const predicate) -> int {
        auto counter = 0;

        for (auto const& element : source) {
            if (predicate(element)) {
                counter += 1;
            }
        }

        return counter;
    }
}

auto main() -> int {
    auto const ints  = std::vector<int>{1, 2, 3, 4, 5};
    auto const count = pjc::count_if(ints, [](int const i) { return i % 2 == 0; });
    fmt::println("{}", count);
}

To ensure that our count_if() doesn’t clash with std::ranges::count_if(), we placed it in a newly created namespace pjc. Its implementation is very simple:

  • We use template <typename T> to introduce a placeholder T, which will be used as the element type of the input vector, allowing us to accept any vector. We need to do this because we can’t write std::vector<auto>. Then, using the abbreviated syntax, we introduce a parameter that serves as the predicate.
  • We iterate over all elements of the source vector, and if any element satisfies the accepted predicate (calling the predicate with this argument returns true), we increment the counter by 1.
  • We return the counter.

In fact, most elements of the C++ standard library are templates. They are considered one of the most important elements of the language. Often on the internet, you’ll come across the abbreviation STL, which stands for Standard Template Library.

Details of how templates work in the STL

After familiarizing ourselves with the above example, several important questions may arise:

std::ranges::count_if() works not only with vectors but also with std::set or even with std::string itself. Our pjc::count_if() only accepts vectors. Why is that?

For simplicity. Of course, instead of:

1
2

template <typename T>
auto count_if(std::vector<T> const& source, auto const predicate) -> int { ... }

We can do the following:

1

auto count_if(auto const& source, auto const predicate) -> int { ... }

In such a situation, source could be any container. Similarly, the tools of the standard library work — they very rarely accept a specific type.

But in this case, how do we know that someone will pass a container as the first argument? What prevents calling this count_if() with, for example, an int instead of a vector of ints? And while we’re at it, what’s to stop the user from passing something completely nonsensical as the predicate, not a lambda, not a function, but, say, an int? What will happen if we try to use the template like this:

1
2
3

auto notRange     = int();
auto notPredicate = int();
pjc::count_if(notRange, notPredicate);

A very good question with a straightforward answer — the code won’t compile. However, it’s worth looking into why that’s the case. Well, there’s nothing stopping the header auto count_if(auto& source, auto predicate) -> int from allowing source and predicate to be ints. The problem is that in the body of the function, we have the following code:

for (auto const& element : source) {
    if (predicate(element)) {
        counter += 1;
    }
}

My deepest sympathies to anyone who has attempted to understand how the compiler tries to “help” us. An essential part says:

  • The range-based for () loop requires… a range. int is not a range because you can’t call .begin() on it or pass it to the begin() function.
  • predicate cannot be used as a function. Well, of course, it’s an int after all.

So, the only significant parts are the beginning and the end of the error message.

Such cryptic compilation errors are unfortunately a part of everyday life when working with templates. They are very powerful, but also very difficult to analyze tools, which is why compilers sometimes struggle to provide clear and helpful error messages.
