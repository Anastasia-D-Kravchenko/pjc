Deep copying

public class Main {
    public static void main(String[] args) {
        int[] arr1 = {1, 2, 3};
        int[] arr2 = arr1;

        arr1[1] = 10;
        System.out.println(arr2[1]);
    }
}

In both listings, we are changing the middle element of some data structure. In the case of C++, it’s std::vector, and in Java, it’s an array of ints.

Before modification, we copy the data structure to a new variable. The modification is done using the “original” object and later readings are done using the copy.

The results of executing both programs may be somewhat surprising:

1

2

1

10

In the case of Java (which we are already familiar with), the situation is relatively simple. arr1 and arr2 refer to the same array allocated in the program’s memory. Modifying an element through one of these variables is visible through the other.

In the case of C++, the situation is different. The operation auto vec2 = vec1 creates a full copy of vec1 named vec2. Changes to vec1 will not affect vec2, and vice versa. This is called deep copying.

The difference in the behavior described above is called the distinction between reference semantics and value semantics.

In Java, we deal with reference semantics. This means that variables refer to objects. A copy of the variable is only a copy of the reference. In this way, you can have multiple variables that provide access to the same object. The exception is variables of primitive types (e.g., int, boolean, double).

In C++, we have value semantics. This means that variables are actual objects. Copying a variable creates a completely independent object.

C++ value semantics also apply to function parameters:

These sometimes surprising results of comparison operators are due to the fact that == in Java means:

  1. For primitive variables, value comparison.
  2. For complex variables, comparison whether both variables refer to the same object.

Point number 2 was the reason why mastering the usage and understanding of the significance of the .equals() method in Java was so important.

How to compare two different containers?

Let’s consider the following example:

#include <algorithm>
#include <iostream>
#include <string>
#include <vector>

auto main() -> int {
    auto str = std::string("hello");
    auto vec = std::vector<char>{'o', 'l', 'l', 'e', 'h'};

    std::ranges::reverse(vec); // to not make it too easy
}

The idea of this listing is to show that sometimes two different containers consist of the same elements. Sometimes we want to check if this is the case. For example, in this case both str and vec store characters (char) that form the string hello.

Unfortunately, attempting to use a comparison like str == vec will result in a compilation error.

#include <algorithm>
#include <iostream>
#include <string>
#include <vector>

auto main() -> int {
    auto str = std::string("hello");
    auto vec = std::vector<char>{'o', 'l', 'l', 'e', 'h'};

    std::ranges::reverse(vec);

    auto equal = true;
    if (str.size() != vec.size()) {
        equal = false;
    } else {
        for (auto i = 0; i < str.size(); i++) {
            if (str[i] != vec[i]) {
                equal = false;
            }
        }
    }

    std::cout << equal;
}

Such a solution works correctly, but it’s far from optimal in terms of readability. It would be best to use the standard algorithm that has already been mentioned in this chapter, which is std::ranges::equal():

    std::ranges::reverse(vec);

    auto equal = std::ranges::equal(str, vec);

    std::cout << equal;
}

Keyword const

The const keyword declares an entity (an object) as immutable. For example, when we create an object of type int const, we will not be able to modify it:

1
2
3
4
5

auto main() -> int {
    auto const x = 10;

    x = 20;
}

1
2
3

main.cpp:4:7: error: assignment of read-only variable 'x'
    4 |     x = 20;
      |     ~~^~~~

Some people may see a similarity to the final keyword in Java. While this is a very good comparison for primitive data types from Java, in the case of complex types, C++ starts to differ significantly.

For example, when we create a final array in Java, like this: final int[] arr = {1, 2, 3}, there is nothing stopping us from changing one of its elements, e.g., using arr[0] = -1. The only thing we cannot do with such a variable is to overwrite it entirely, for example, with arr = new int[1337].

A similar situation applies to other collections in Java.

However, in C++, const represents much stronger immutability semantics. For example, you cannot add any elements to a const vector. You cannot modify any elements it stores. You cannot remove any elements from it, and you cannot overwrite the entire container. std::vector<T> const is truly read-only.

Just like in other languages (e.g., JavaScript (JS) / TypeScript (TS), Rust, or functional languages), immutability in C++ is considered as desirable. It helps to avoid hard-to-detect bugs related to unexpected changes in memory state (especially for data with broad access points or data that is shared between multiple threads).

Unfortunately, this was not obvious at the time this language was created. Therefore (just like in JS / TS) — unfortunately — it is expected to use a longer and less convenient syntax for declaring types (using const practically everywhere).
