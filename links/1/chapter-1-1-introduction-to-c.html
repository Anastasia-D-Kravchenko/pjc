Chapter 1.1 - Introduction to C++

Posted Feb 25, 2025
By Filip Kwiatkowski
6 min read

The first two chapters of this chapter (Philosophy of learning multiple languages and C++ language) are only theoretical introductions to the subject. They do not contain mandatory information on learning C++ language. Therefore, you can skip them and go straight to IDE Configuration.

The exception is the information provided in boxes such as this one. You can find two such in C++ Language.

Philosophy of learning multiple languages

The purpose of learning an alternative language to one already learned (Java) is primarily to broaden the programmer’s perspective on the possibilities it offers. Knowing only one language — even very well — the programmer is limited by the way of reasoning imposed by that tool. By learning the C++ language, which is full of both similarities and differences to Java, the programmer will be better able to identify existing paths to achieve the goal of choosing the right tool, architecture, and implementation.

When a programmer encounters a problem that is not trivially solvable by the tool they are using (e.g., there is no ready-made function in the standard library of the chosen language that would achieve the intended purpose, such as adding method overloads based on generic type specialization, partitioning an array in place, or simply inverting Stringa1), they are faced with a choice:

  1. Implement the solution by hand.
  2. Change the tool (e.g., to another programming language) to one that solves the problem in a simpler way.
  3. Simulate a piece of another tool’s environment (e.g., part of another programming language’s standard library) to make the implementation of the solution simpler.

When the programmer is not aware of the features of other ecosystems, solutions 2 and 3 cease to be viable options. One cannot make a decision to use an alternative tool if one is not aware that another tool can help achieve the goal.

Thus, it can be seen that a broader awareness of alternatives opens up many new paths that may turn out to be the best strategy to achieve a given goal. In addition, it is worth noting that option No. 1 becomes more attractive with better knowledge of other tools. Just knowing that another tool solves a problem in a given way allows you to create a more thoughtful solution. This is because you can later compare it with known alternatives.

C++ language

C makes it easy to shoot yourself in the foot; C++ makes it harder, but when you do it blows your whole leg off.

~ *Bjarne Stroustrup, creator of the C++ language.

The C++ language is a huge collection of powerful tools that unfortunately do not always work well together. This makes it possible to achieve virtually anything with it (without incurring a major performance cost to the resulting program), but often involves a disproportionate amount of difficulty. That’s why the language was (and still is) used for many critical applications requiring a high level of abstraction paired with performance.

However, alternatives have emerged to present a simplified tool with greater brevity. C++-inspired languages such as Java, C# and indirectly Python began to introduce tools that encouraged their use far beyond what C++ had to offer.

The language, however, did not give in. Adaptations of competing tools have meant that C++ — especially in the C++20 iteration — can achieve similar levels of ease of use as alternative languages, while still retaining its strengths of backwards compatibility, high performance and generic programming.

Accordingly, this subject will focus on the latest, widely adopted iteration of the C++ language, C++202.

On the subject, the C++20 standard is.

Note, however, that this has both positive and negative effects.

First of all, the upside is learning the latest adopted iteration of the technology. When creating new projects in C++, unless the programmer encounters good reasons to use older versions (e.g., an old, incompatible with newer versions library or problems with upgrading tools in the company due to migration or licensing issues), as a rule, the latest standard is usually chosen. It contains the most facilities, the most useful tools and ultimately the fewest bugs.

The downside of learning the latest technology is the relatively small number of materials available.

Due to the popularity of the C++ language, a great deal of material about it can be found on the Internet. As a rule, these materials refer to older, outdated elements of the language. Therefore, you should very carefully verify the reliability of the information found on the Internet. When in doubt, it is best to consult the source with the tutor or the lecturer3.

IDE

Within the course, the recommended environment is JetBrains CLion.

The compiler built into CLion should be sufficient to support all the tools presented in the subject. The exception is users of some versions of macOS — they may have to download a separate compiler. In such cases, it is recommended to use the package manager Homebrew and install the latest GCC compiler (the brew install gcc command should be sufficient — according to the documentation it installs GCC 14.2.0). Later, in the environment, set the newly downloaded compiler.

Project structure

Projects created within the CLion environment consist of the following:

  • A hidden folder .idea, which contains the elements concerning the configuration of CLion within this project (including some plugins). It will not be of interest to us on this subject.
  • The cmake-build-debug folder, where the elements created as part of compiling and building our project land by default. These include, but are not limited to, executable files (e.g., .exe) or compiled libraries downloaded from the Internet.
  • The CMakeLists.txt file, which contains the configuration and build instructions for our project. Its name, the list of files that make up the project (or programs), identification of external dependencies, etc. Advanced Java developers may think of this as the equivalent of pom.xml from Maven projects or the equivalent of build.grade from Gradle projects. We will be analyzing and modifying this file in the future.
  • The main.cpp file, where we put our code.
  • Additional folders / files that we will create as part of writing more and more complex programs.
