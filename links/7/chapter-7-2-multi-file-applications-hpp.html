Chapter 7.2 - Multi-file applications - .cpp and .hpp files

Posted Apr 13, 2025
By Filip Kwiatkowski
7 min read

Declaration in one file, definition in another

As it’s known, in C++, we cannot call a function if we don’t know its header, which we can learn from its declaration.

This is especially evident when our project consists of multiple source files. Let’s assume the following situation — we have three source files:

  • main.cpp
  • maths.cpp
  • printer.cpp

Where in maths.cpp and printer.cpp, we have many different functions:

It’s impossible not to notice that we lose up to 8 lines (9 if we count the empty line) just to declare functions that are elsewhere.

Attempting to maintain such code undoubtedly leads to chaos in the project structure. There must be a better way. Fortunately, there is — they are called header files.

Header files

A file with the extension .cpp we called an implementation file or source file. It contained source code. A file with the extension .hpp1 we will call a header file. The name clearly indicates its purpose — it will store headers.

Let’s create two additional files — printer.hpp and maths.hpp. Their purpose is to store declarations, so let’s move the appropriate declarations from main.cpp to them:

Time to summarize the appearance of our project and answer a couple of questions.

Wait a moment, what is this #pragma once?

We’ll cover that in the next part of the chapter. For now, it’s worth remembering that it’s effectively added at the beginning of every header file.

Summary of changes and project structure description

Our project now consists of 6 files:

  • CMakeLists.txt
  • main.cpp
  • pairs of files maths.hpp and maths.cpp
  • pairs of files printer.hpp and printer.cpp

The CMakeLists.txt file hasn’t changed in any specific way — add_executable() still relies solely on .cpp files2.

Instead of manually listing all the function declarations it wants to use, main.cpp includes the appropriate header files using #include. As we can recall from the Summary and Extras after Lecture 1, the #include directive does nothing more than simply paste the contents of the file. Effectively, header files exist to automate the process of copying and pasting declarations of elements we want to use from other files.

However, it’s hard not to notice that these #includes look slightly different from before. When including headers from the standard library or from {fmt}, we used #include <name>. Here, we clearly have #include "name", so we’ve swapped angle brackets for quotation marks.

Behind these differences lies a longer piece of history of original application splitting into multiple files, many design decisions of which were made in the context of very performance-limited computers. Nowadays, project build structures are significantly different, and C++ lags behind in catching up with this evolution. C++ Modules are on the horizon, but there’s still a long way to go before they become widely adopted.

Returning to the topic of <> versus "" — there are many configuration options and nuances that can effectively undermine any “absolute” argument trying to explain the use of one over the other, so we won’t delve into the theory. It’s just worth remembering the following guideline:

If we’re including a header from some ready-made library, we use angle brackets (#include <name>). If we’re including a header from our project, we use quotation marks (#include "name").

Further subdivision into subfolders

As is often the case when working with computers, sometimes it’s worth placing files in separate subfolders to achieve a clearer structure. There’s nothing stopping us from applying this practice to C++ projects. Naturally, you can create a separate folder for each domain or module of the project. Later, you just need to use relative names accordingly:
