Chapter 7.3 - Multi-file applications - classes and problems they cause with header files

Posted Apr 13, 2025
By Filip Kwiatkowski
6 min read

Splitting classes into header and implementation files

As the implementation of a class grows to larger numbers of lines, a good idea might be to split it into a header file and an implementation file. The accepted practice is that in the header file, we declare and define the class, where we only declare (without defining) its methods. The definitions of these methods are placed in the implementation file:

#pragma once

struct Point {
    int x;
    int y;

    auto distanceToOrigin() const -> double;
};

#include "point.hpp"

#include <cmath>

auto Point::distanceToOrigin() const -> double {
    return std::hypot(x, y);
}

A few important facts:

  • In the header file, we stated that Point consists of two members (x and y) and has a method distanceToOrigin(). We have its declaration but without its definition.
  • In the implementation file, we want to implement the distanceToOrigin() method belonging to the Point class. To do this, we must use an interesting syntax using the familiar :: operator. We say that we implement distanceToOrigin() from Point. Hence Point::distanceToOrigin(). Otherwise, how would it be known which class the distanceToOrigin() method belongs to? What if two classes have such a method, and we want to implement them differently? The problem is that this file wouldn’t know what Point even is if we didn’t include "point.hpp". Effectively, we pasted the pattern of our class into the .cpp file so that it could be known that Point indeed has a distanceToOrigin() method. Without this, the Point::distanceToOrigin() fragment would generate an error because the compiler wouldn’t know that there is a class named Point within this .cpp file.
  • The header file informing the “outside world” that there is a Point class doesn’t need to know how Point::distanceToOrigin() is implemented. It doesn’t know that it uses std::sqrt(), so #include <cmath> (which introduces this function) doesn’t need to be executed for the header file — it’s enough to execute it within the implementation file.

However, the question remains:

What is this #pragma once?

The pragma once Directive

In the earlier part of the lecture, we saw an interesting line of code that appeared always in the first line of header files — #pragma once. It’s worth discussing its purpose and presenting the problems it solves.

Simply put:

The #pragma once directive guarantees that within one implementation file, a given header will be included only once.

Let’s look at a simple example — creating a header with some class, immediately defining it (not necessarily defining its methods). It’s relatively obvious that if we defined the class twice, an error would occur, right?

Even if both implementations are identical, we can’t duplicate definitions within one .cpp file.

But nobody in their right mind would do that. So where’s the problem?

What if we were using the previously presented point.hpp and did this?

#include "point.hpp"    // once
#include "point.hpp"    // twice

auto main() -> int {

}

Then, due to the fact that #include literally pastes the contents of the file, we would get a duplication of the class definition!

But who would do that?

Exactly? Nobody. But what if we have the following dependencies:

  1. point.hpp defines the structure of the Point class.
  2. line.hpp defines the structure of Line, which consists of two points.
  3. In main.cpp, we use both of them.

So:

In main.cpp, we include point.hpp and line.hpp, whose the content is, among other things, #include "point.hpp". So effectively, we #include "point.hpp" twice.

That’s a problem. We can’t always know which headers use which1. Sometimes it’s an implementation detail that can change, so we shouldn’t rely on it.

However, this code still compiles. That’s because when the preprocessor sees that in main.cpp, we have two #includes of the same file, which is guarded by #pragma once, it includes that file only once.

Templates

Templates can be… problematic. That’s because a template adapts to deduced types, and the compiler generates required implementations. The compiler, to generate a specific template instance, needs to see the entire implementation “at once.” This means that:

Templates must be defined in header files.

You can’t easily “split” a template into two files. Certainly not into a “classic” pair of .hpp + .cpp. When you use a template in a header file, you should define it in the same file (i.e., right away).

Global using

Quick quiz — what exactly does #include do?

It copies and pastes the entire contents of the file — without any philosophy. Simple.

Very good. Next question — why can using namespace be dangerous?

Because it can introduce “global” names that we are not aware of, and as a result, we may make mistakes.

Again, very good. And what happens if we do using namespace in a header file and someone includes that file using #include?

…That person will involuntarily use using namespace in their code, perhaps even without knowing it…

Fantastic. So we have a rule to stick to:

We don’t use global using namespace in header files. Never. Some people use it in .cpp files (because they are never included), but no one should use it in header files.

The same applies, of course, to using declarations, e.g., using std::string;.

Macros

A macro like #define allows us to replace a fragment of code with some other. For example:

#include <fmt/base.h>

#define true false

auto main() -> int {
    auto shouldDisplay = true;

    if (shouldDisplay) fmt::println("Hello");
}

This code will not display anything.

On one hand, nobody would likely replace true with false, but quite a few issues have arisen because someone abused macros. The relationship with macros and header files is similar to that between these files and using:

We don’t create macros in header files.

  1. That’s partly why sometimes we can use std::string without #include <string>. For example, the <iostream> header may directly or indirectly include the <string> header. However, we shouldn’t rely on it. ↩
