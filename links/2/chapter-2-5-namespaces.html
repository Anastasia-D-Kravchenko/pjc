Chapter 2.5 - Namespaces

Posted Mar 6, 2025
By Filip Kwiatkowski
5 min read

Grouping elements and repeated names

A good name is one of the key things to design when creating software. Considering the fact that many problems repeat within multiple applications, libraries, or even the same systems, there may be a situation where we want to use the same name twice, but in different contexts.

For example, removing all numbers equal to 5 from a vector is completely different from removing a file with a specific path. Nevertheless, when designing both functions, we would probably decide to name both of them remove().

Unfortunately, attempting to create two functions with the same name will result in failure. The error generated by the compiler will indicate redefinition:

But in the example above, we were talking about a function that takes a vector and some number to remove, and of a function that would take a single argument in the form of a file path to be removed. Would it not be overloading in this case, and everything would work?

Yes. The following code will compile correctly:

auto main() -> int { }

Nevertheless, it is not an ideal solution. Ideologically, we do not want to create an overload that would do completely different things depending on the type of arguments. Overloads are meant to achieve a similar goal but offer different levels of detail or work with different types of data. It’s hard not to notice that removing an element from a vector and removing a file are indeed completely different operations.

A similar situation may occur to someone who creates two text files on their computer with the name vacation.txt. One is intended to store notes with vacation plans, and the other is intended to store notes with plans for the company’s development - during the vacation.

It is not possible to create two files with the same name (including the extension, which is, of course, part of the file name) in the same folder.

But these files can be placed in separate folders.

A folder is effectively a named group of files. It is used for convenient storage of elements. It has a name that adds context - the file vacation.txt in the work folder will obviously concern something different than the file vacation.txt in the leisure folder.

Namespaces serve as such folders for classes, functions, and other language elements.

We have already encountered several namespaces:

  • std - there you can find, among others, std::vector, std::string, std::cin.
  • ranges - this is a subnamespace of the std namespace. There are algorithms like std::ranges::sort() or std::ranges::reverse().
  • fmt - the first custom namespace we encountered. It was created for the needs of the {fmt} library to avoid potential name conflicts. For example, C++23 will have a function print() placed in the std namespace. If namespaces were not used, fmt::print() and std::print() could accidentally introduce naming conflicts.

We can, of course, create our own namespaces. This is done in a very simple way:

    fmt::println("Hello!");

Then the code won’t compile link. The error will indicate a lack of definition for the declaration pjc::sayHello().

Very cool. It (probably) makes sense for larger projects, but what about smaller ones we do in PJC? Do we have to create namespaces everywhere?

No. If our application is very small, there is no need to complicate it by adding our own namespaces.
