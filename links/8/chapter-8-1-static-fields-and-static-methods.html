Chapter 8.1 - Static fields and static methods

Posted Apr 24, 2025
By Filip Kwiatkowski
4 min read

Keyword static

Static fields and methods are a crucial part of most object-oriented languages. They represent the abstraction of data and functionalities that contextually belong to a class, although they are not dependent on its objects.

In the C++ language, the static keyword, when placed before a class field or method, converts the entity into a static element. Access to such an element is done using the class name and the :: operator (rather than . as in Java).

For example, when creating a static method bar() of the Foo class, we call it using the syntax Foo::bar():

1
2
3
4
5
6
7

struct Foo {
    static auto bar() -> void { }
};

auto main() -> int {
    Foo::bar();
}

Static methods cannot be const (but can accept const arguments), because they aren’t called on any objects.

As you can see, static methods work practically the same as in other popular languages. However, in the case of static fields (variables), the situation is slightly more complicated. This is because the “trivial” way of using them unfortunately won’t work:

1
2
3

struct Foo {
    static int value = 0;
};

1
2
3

main.cpp:2:16: error: ISO C++ forbids in-class initialization of non-const static member 'Foo::value'
    2 |     static int value = 0;
      |                ^~~~~

The reasons for this behavior are quite intricate, although they can be partially summarized as follows: Static variables in classes effectively act as global variables that exist independently of whether any class object has been created. Often, the class definition appears in a header file, which is then #included potentially multiple times. Such a class definition contains full declarations (e.g., methods), which are later defined in a separate .cpp file (i.e., implemented once without duplicates).

If we were to allow the syntax static int value = 0;, such an instruction would also be a definition. If the class were defined in multiple .cpp files (through #include), we would repeat the definition of the value field. Redefinition is not a legal operation in C++.

But wait, if redefinition is not legal, then why can we have multiple class definitions? After all, if struct Foo { ... }; is a definition, and that’s what we always did with classes placed in header files, which we then potentially included multiple times in different .cpp files, weren’t we effectively dealing with class redefinition?

A great point. If someone hasn’t intuitively noticed this inconsistency, it’s worth reading it again.

The answer is brief — because class definitions are by default marked as inline1.

Keyword inline

The inline keyword is used to specially mark constructs such as functions or variables. An element marked as inline can be defined multiple times in multiple translation units (basically compiled .cpp files, which will then be linked with others to create one application).

Let’s assume a simple example where we don’t want to define a function in a .cpp file after declaring it in a .hpp file. We want to define it directly in the header file. This can cause a problem when we try to include such a file in several .cpp files:

1
2
3
4
5

#pragma once

auto theAnswer() -> int {
    return 42;
}

1
2
3

#include "functions.hpp"

auto main() -> int { }

1

#include "functions.hpp"

Of course, we build the application based on these two implementation files, so we do add_executable(PJC main.cpp impl.cpp).

Such an application will compile but won’t link. The linker error might look like this:

1

impl.cpp:3: multiple definition of `theAnswer()'; CMakeFiles/PJC.dir/main.cpp.obj:main.cpp:3: first defined here

As you can see, the error indicates that in the source file impl.cpp, we have a duplication of the definition of the function theAnswer(), which was already seen earlier in the main.cpp file.

The method to fix this error seems straightforward — just don’t define this function in the header file, but add an appropriate .cpp file where we will place its definition, leaving only the declaration in the header file.

Interestingly, in the vast majority of cases this is exactly what we should do. Implementation in the header file should be an exception, not the rule. Exceptions include:

  • Class definitions - usually full method declarations;
  • Template definitions;
  • Implementations of libraries that want to allow inclusion solely by downloading and including header files;
  • And other minor cases.

static inline fields

Returning to the original problem, where we tried to declare a static field of type int:

1
2
3

struct Foo {
    static int value = 0;
};

There are two ways to fix the build process error:

  1. Add the inline specifier, so change static int value = 0; to static inline int value = 0;.
  2. Remove the initialization, so change static int value = 0; to static int value; and add the definition of the value field in a separate (only one) implementation file using the syntax int Foo::value = 0;.

The first option is simpler. It’s worth using this (introduced in C++17) alternative.

  1. Unfortunately, that’s not entirely true. Effectively, you can simplify it like this, but the truth is more complex — it concerns the precise definition of the ODR rule, which states that this rule simply works differently for user-defined types. ↩
