Posted Apr 24, 2025

Operator overloading as methods and free functions

In the earlier part of the chapter, we learned (and noticed) that operators can be overloaded in two ways — as methods and as free functions. Most operators can be overloaded in both ways. However, there are some exceptions.

operator= cannot be overloaded as a free function. It must be implemented as a method. This is to prevent anyone from “outside” changing what happens when objects of types created by someone else are overwritten. What a disaster it could be if we overrode operator= for std::string without realizing how much we just broke in the {fmt} implementation?

operator+, which we examined in the previous chapter, can be overloaded in both ways. Let’s consider the example with the Point class:

#include <string>

#include <fmt/format.h>

struct Point {
    int x;
    int y;
};

auto operator+(Point const left, Point const right) -> Point {
    return Point(left.x + right.x, left.y + right.y);
}

auto format_as(Point const p) -> std::string {
    return fmt::format("({}, {})", p.x, p.y);
}

auto main() -> int {
    auto p1 = Point(1, 2);
    auto p2 = Point(5, 8);
    fmt::println("{}", p1 + p2);
}

Now, let’s change it so that the overloading of operator+ is not implemented as a free function, but as a method:

#include <string>

struct Point {
    int x;
    int y;

    auto operator+(Point const right) const -> Point {
        return Point(x + right.x, y + right.y);
    }

auto format_as(Point const p) -> std::string {
    return fmt::format("({}, {})", p.x, p.y);
}

auto main() -> int {
    auto p1 = Point(1, 2);
    auto p2 = Point(5, 7);
    fmt::println("{}", p1 + p2);
}

The effect is still identical. Let’s look at the only difference in the code:

1
2
3

auto operator+(Point const right) const -> Point {
    return Point(x + right.x, y + right.y);
}

We should observe some interesting things:

  1. The left argument has disappeared.
  2. The method is marked as const.

When overloading a binary operator using a method, its left operand becomes the object on which it is called.

This means that with the snippet:

1
2
3

auto p1 = Point(1, 2);
auto p2 = Point(5, 7);
fmt::println("{}", p1 + p2);

This + is effectively called on p1. x and y from the operator overloading implementation refer to p1.x and p1.y.

p2 becomes right, of course.

We marked the overloaded operator (as a method) as const because we want to indicate that this operator does not modify the left operand (in the above example — p1). In the example where we implemented it as a free function, both arguments were const. The right operand was const, but for the method to have the left operand marked as immutable, the entire method must be marked as such.

Problem with overloading operator as a method for existing classes

In the previous chapter, we provided operator+ for two std::vector<int> as well. It was also overloaded as a free function. So how could it be changed to a method?

It cannot.

We do not have access to the std::vector template. We cannot “open” it and add operator+ as a method there. Hence the necessity to provide it as a free function.

Common examples where the operator is provided as a free function

We cannot edit existing classes (at most we can add template specializations, but what if the given type is not a template?).

We cannot always use {fmt} (for example, if the product created by our company is under a non-compliant license).

Nevertheless, sometimes we want our types to be “displayable”. Before introducing {fmt}, we used std::cout. The type of this object is std::ostream. This means that if we wanted to provide the ability to display our type (e.g., Point), it would have to be done using a properly overloaded << operator:

#include <iostream>

#include <fmt/format.h>

struct Point {
    int x;
    int y;
};

auto operator+(Point const left, Point const right) -> Point {
    return Point(left.x + right.x, left.y + right.y);
}

auto operator<<(std::ostream& out, Point const p) -> std::ostream& {
    out << '(' << p.x << ", " << p.y << ')';
    return out;
}

auto main() -> int {
    auto p1 = Point(1, 2);
    auto p2 = Point(5, 8);
    std::cout << p1 + p2;
}

This time again, we’re using <iostream>, where objects of type std::ostream and std::istream use << and >>. This means that in order for Point to be displayed, the appropriate operator must be overloaded:

1
2
3
4

auto operator<<(std::ostream& out, Point const p) -> std::ostream& {
    out << '(' << p.x << ", " << p.y << ')';
    return out;
}

It’s worth noting that since the left operand is of type std::ostream, and it’s clearly a class created by someone else, there’s no other way to provide the required operator than by using a free function.

Other operators that must be overloaded as methods

We’ve already learned about operator=, which must be overloaded as a method. What other operators require this?

There are three such operators1:

  • operator()
  • operator[]
  • operator->

We won’t worry about the last one.

operator()

The function call operator is the operator that allows objects of our class to be called like functions. Let’s look at an example:

#include <string>

#include <fmt/base.h>

struct Printer {
    std::string message;

    auto operator()() const -> void {
        fmt::println("{}", message);
    }
};

auto main() -> int {
    auto greeter   = Printer("Hello");
    auto announcer = Printer("Get ready!");

    greeter();
    announcer();
    greeter();
}

#include <fmt/base.h>

struct Reverser {
    auto operator()(int const a) const -> int {
        return -a;
    }
};

auto main() -> int {
    auto reverse1 = Reverser();
    auto reverse2 = [](int const a) { return -a; };

    fmt::println("{} {}", reverse1(3), reverse2(3));
}

The output, as before, is the same, namely -3 -3.

The similarity is not accidental — that’s exactly how lambdas work!

A lambda literal (some form of [](){}) results in the creation of an anonymous type, which — among other things — has an overloaded operator() with a body consistent with what we provided in the literal. Then the literal is replaced with the creation of an object of the newly created type.

Of course, what exactly is found in the type generated by the lambda expression is a bit more complicated. However, it’s not relevant at this point.

operator[]

The indexing operator must also be defined as a method. It is used to standardize the way elements of most containers are accessed. Thanks to it, std::array, std::vector, or std::string can offer the same way of accessing data. Recall that in Java:

  • arrays are indexed using [];
  • lists (and generally collections) using .get();
  • and text types using .charAt().

In C++, it’s always [].

Until C++23, operator[] could only take a single argument. This meant that when representing a multidimensional collection, one had to use inefficient (or complicated) constructions that provided syntax like [i][j][k][...] or provide indexing through operator().

Its implementation doesn’t differ particularly from the rest of the operators. Let’s consider, for example, a wrapper type around std::string that displays information when someone tries to access this std::string:

#include <fmt/base.h>

class StringWrapper {
    std::string buffer;

public:
    StringWrapper(std::string const & buffer) : buffer(buffer) { }

    auto operator[](int const index) -> char& {
        fmt::println("Accessing index #{}" , index);
        return buffer[index];
    }

    auto print() const {
        fmt::println("{}", buffer);
    }
};

auto main() -> int {
    auto sw = StringWrapper("Hello");
    sw.print();
    sw[0] = 'h';
    sw.print();
    sw[2] = 'e';
    sw[3] = 'e';
    sw[4] = 'y';
    sw.print();
}

main.cpp:22:28: error: passing 'const StringWrapper' as 'this' argument discards qualifiers [-fpermissive]
   22 |     fmt::println("{}", sw[0]);
      |                            ^
main.cpp:9:10: note:   in call to 'char& StringWrapper::operator[](int)'
    9 |     auto operator[](int const index) -> char& {
      |          ^~~~~~~~

This cryptic error is C++’s way of saying that operator[] doesn’t promise that its invocation won’t modify the object’s content. We’re not doing that, but the compiler doesn’t always catch it. To fix this, we should declare it as const:

1
2
3
4

auto operator[](int const index) const -> char& {
    fmt::println("Accessing index #{}" , index);
    return buffer[index];
}

Note that the only change is adding const before ->.

Unfortunately, now a different error appears!

1
2
3

main.cpp:11:28: error: binding reference of type 'char&' to 'const __gnu_cxx::__alloc_traits<std::allocator<char>, char>::value_type' {aka 'const char'} discards qualifiers
   11 |         return buffer[index];
      |                            ^

Let’s translate the error into plain language — it’s saying that we claim return buffer[index] will return char& (because that’s what we wrote after ->). The problem is that… we can’t do that. Within a const method, the expression return buffer[index] returns char const&.

It probably sounds terribly illogical, strange, tragic, and senseless. But on the other hand, the effect is quite understandable — a const method shouldn’t return a raw (non-const) reference to an object’s member. If it could, such code would have to compile:

1
2
3
4

auto main() -> int {
    auto const sw = StringWrapper("Hello");
    sw[0] = 10;
}

Which would obviously be nonsensical. const is supposed to signify true immutability. You can only invoke const methods on such an object. But if operator[], when const, allowed returning a non-const reference to a member, the above code would compile without any problem.

So how does it work with std::vector then? I can perform indexing on both const and non-const vectors. With a non-const vector, it allows me to modify objects, while with a const vector, it doesn’t. How is that done? Some kind of “third state”?

Not exactly. It’s done through overloading:

#include <fmt/base.h>

class StringWrapper {
    std::string buffer;

public:
    StringWrapper(std::string const & buffer) : buffer(buffer) { }

    auto operator[](int const index) -> char& {
        fmt::println("Accessing (maybe mutating) index #{}" , index);
        return buffer[index];
    }

    auto operator[](int const index) const -> char const& {
        fmt::println("Accessing (immutably) index #{}" , index);
        return buffer[index];
    }


    auto print() const {
        fmt::println("{}", buffer);
    }
};

auto main() -> int {
    auto const first = StringWrapper("Hello");
    auto second      = StringWrapper("Friends");
    fmt::println("{} {}", first[0], second[0]);
}

When we have a const object (first) and use indexing, the const version is selected. When we have a non-const object (second) and use indexing, the version without const is selected.

Methods can be overloaded based on their “constness”.

It’s also worth noting that the non-const version returns char&, whereas the const version returns char const&. This ensures everything works smoothly3.

Other Operators that Must Be Overloaded as Free Functions

All other operators can be overloaded as free functions.

  1. Why exactly these three must be implemented as methods? I don’t know. If someone knows, please let me know. I’ve seen many opinions, but none were confirmed by reliable sources that explain why this decision was made by the C++ language standardization committee. ↩

  2. The first two lines of the presented output may be printed in the reverse order. That’s because C++ is allowed to evaluate function arguments out of order (i.e., not necessarily from left to right). ↩

  3. C++ programmers have long expressed some discontent about the necessity of such overloads. C++23, along with the “deducing this” feature, partly addresses this, though it’s not a perfect solution to the problem. ↩
