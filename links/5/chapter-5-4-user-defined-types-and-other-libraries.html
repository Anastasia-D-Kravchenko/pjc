It’s worth looking at line number 19, which says — among other things — that: static assertion failed: Cannot format an argument. To make type T formattable provide a formatter<T> specialization: https://fmt.dev/latest/api.html#udt

We have a starting point to look for clues: https://fmt.dev/latest/api.html#udt

As we can read in the linked section, we have two options:

  1. Specify the format_as() function in the same namespace as our type (in this case, in the global namespace because we haven’t enclosed our type in a namespace).
  2. Use template specialization of the formatter structure.

Option 2 is challenging, so let’s go with option 1:

Use format_as if you want to make your type formattable as some other type with the same format specifiers. The format_as function should take an object of your type and return an object of a formattable type. It should be defined in the same namespace as your type.

~ {fmt} documentation.

    int y;

It works!

Well, aren’t we creating a temporary object of type std::pair just so that fmt::println() knows how to display our Point? Sounds like an inefficient solution.

You’re right. Using format_as() is usually not the most optimal approach, but surprisingly, it’s rarely a concern. Text display is a very heavy operation, and creating an additional (relatively small) object (or even two) per displayed element isn’t that significant in this context.

To achieve the best performance, we would use option 2, which is specializing the formatter type. However, it’s disproportionately more challenging, so we’ll stick with the format_as() approach.

Maximum convenience, minimum performance

In the world of Java, no one cares that when displaying an object using System.out.println(), the .toString() method is called, which constructs a temporary object of type String that becomes useless right after the display is finished. If we’re not concerned about achieving optimum performance in the display process (where the slowest part is interaction with the external world, not the preparation of temporary objects), we can simply always default to returning std::string instead of searching for types that fmt can work with:

1

#include <fmt/format.h>

struct Point {
    int x;
    int y;
};

auto format_as(Point const p) { return fmt::format("({}, {})", p.x, p.y); }

fmt::format() indeed returns std::string, which {fmt} can format, of course.

The above listing allows for several interesting observations:

  • fmt::println() respects our custom formatting rules when displaying a range of user-defined types.
  • There are many ways to fill a vector with points — primarily, we can add them using .push_back(), but we can also use initializer lists (as seen in line 22).
  • Creating a point isn’t limited to something that looks like a classic constructor call (e.g., Point(5, 6)). Points can also be created using braces (Point{1, 2} and {3, 4}). The fact that braces are allowed here stems from the C language. Additionally, when the expected type is known, its name can be omitted (we remember about default value literals — {}).

Containers that require additional functionality

Unfortunately, when we try to create std::set<Point> or std::map<Point, T>, the compiler will protest. This is because — as we know — elements in std::set and keys in std::map are stored in ascending order. But what does it mean for one Point to be “greater” than another? Neither we nor the compiler know this — hence the inability to store these elements in these containers.

However, this doesn’t mean that sorting a container of points is impossible.

Range algorithms and containers of user-defined types

So, how do we sort std::vector<Point>? The “classic” way unfortunately won’t work:

struct Point {

auto main() -> int {
    auto points = std::vector<Point>{ {1, 2}, {0, 0}, {2, 0} };
    std::ranges::sort(points);  // error

The compiler doesn’t know how to set points. Let’s tell it how to do it — we’ll use a comparator.

However, first, we need to answer the question ourselves: what does it mean for one point to be “greater” than another?

In mathematics, points do not have a well-defined order. Therefore, we can come up with any strategy we like. In this chapter, points will be ordered according to their distance from the point \((0, 0)\). As part of this strategy, we will create a method in the Point class that returns the distance to this point:

#include <algorithm>
#include <cmath>    // std::hypot
#include <utility>
#include <vector>

#include <fmt/ranges.h>

struct Point {

    int y;

auto main() -> int {
    auto points = std::vector<Point>{ {1, 2}, {0, 0}, {2, 0} };
    std::ranges::sort(points, [](Point const left, Point const  right) {
        return left.distanceToOrigin() < right.distanceToOrigin();
    });
    fmt::println("{}", points);
}

Okay, but what was that const thing doing in the .distanceToOrigin()’s signature?

Excellent question. This is a so-called const method.

const methods

const methods (member functions) are created when just before the return-type-specifying arrow (->) we add a const keyword.

const method differs from the non-const version in such a way that it promises that its invocation will not change the state of the object.

It is very important, becasue if we had a const object, we should not be allowed to modify its state. And since we should not modify its state, we should not be able to call a method that does exactly that.

Let’s look at it from a logical standpoint — on, for example, an object of type const std::vector<int> we cannot call .push_back() or .erase(), can we? Those methods change the state of the object. However, there is no problem with calling .size() or .empty(). That’s because the latter ones are const methods.

On a const object you can only call const methods. On a “normal” (non-const / mutable) object you can call both const and non-const methods.

As it is the case with objects, by default we should be marking methods as const. If we don’t do that (and the method neither should, nor does mutate the state of the object), then not only we incorrectly state our intents, but also potentially risk producing non-working code — mostly because of the fact how popular const references are. Such reference, even if bound to a non-const object, cannot call non-const methods.

Sorting in std::set

Sounds good, but since we can solve the problem of unsortable points using a comparator when using std::ranges::sort(), can’t we do this in a similar way to create std::set<Point>?

We can, but it’s slightly more complicated. An example will be included in the summary and extras of this chapter.

Lambda capture group

Lambda capture group allows a lambda to operate on objects that have not been passed to it through arguments.

Let’s assume an example where among a group of points, we want to find the one closest to another point. A sample function that achieves this goal may have the following header:

1

auto closestTo(std::vector<Point> const& points, Point const other) -> Point;

So among points, we look for an element that is closest to other.

Its usage looks like this:

            {3, 2}, {1, 0}, {5, 9}, {2, 12}
    };

    fmt::println("{}", closestTo(points, {4, 4}));
}

Of all these points, the closest one will be \((3, 2)\), so that should indeed be the result of running the program.

1

(3, 2)

The implementation of closestTo() doesn’t seem exceptionally complicated. We can use a comparator that calculates the distance of both of its arguments to other and returns true if the distance of the left argument is closer.

However, it’s hard not to notice that effectively, we are comparing distances. The distances of the considered points to other. In that case, let’s use projection instead of a comparator. Let’s consider all elements in points as their distances to other and find the smallest one using std::ranges::min:

1
2
3
4
5

auto closestTo(std::vector<Point> const& points, Point const other) -> Point {
    return std::ranges::min(points, {}, [](Point const candidate) {
        return std::hypot(candidate.x - other.x, candidate.y - other.y);
    });
}

The solution seems quite simple. According to the previous plan, we use std::ranges::min() along with a lambda that is a projection of our points from points to their distance to other.

Why? After all, other is visible throughout the entire closestTo() function, and the lambda is a part of it, right?

Almost. To understand the problem, let’s revert to a “more basic” tool. Instead of using a lambda, let’s use a regular function:

auto projectDistance(Point const candidate) {
    return std::hypot(candidate.x - other.x, candidate.y - other.y);

    return std::ranges::min(points, {}, projectDistance);
}

Upon closer inspection of the projectDistance() function, we can clearly identify the error. How is this function supposed to know what other is?

Lambdas are shorthand for creating an object of an anonymous type, which provides us with special functionality (in the form of a special function) that allows us to use it like a regular function (i.e., call it using () after its name).

Since ultimately some function with the same body as the one specified in the lambda is created, it’s not surprising that its body has no idea what other is.

Fortunately, there is a solution. Lambdas were created, among other things, to be conveniently used inside other functions. Functions have local variables, so it’s logical to assume that someone would want to use a lambda operating on those variables.

The realization of this assumption is a tool called the capture group. It’s that innocuous-looking fragment [] that we always write at the beginning of a lambda.

The whole problem will be solved if we place the name other there:

1
2
3
4
5

auto closestTo(std::vector<Point> const& points, Point const other) -> Point {
    return std::ranges::min(points, {}, [other](Point const candidate) {
        return std::hypot(candidate.x - other.x, candidate.y - other.y);
    });
}

The syntax [other] in the context of a lambda instructs it to copy this object into its local memory. Just like Point has fields int x and int y, now our lambda has a field Point const other.

The exact mechanism that enables us to perform these operations will be discussed in the future — then we’ll implement a class “from scratch” that can behave like a function.

For now, remember that lambda logic is similarly limited to that applying to regular functions. If we don’t pass a non-global object as an argument, the lambda can’t work on it.

The [other] syntax copies the point into the lambda, but we don’t always want to copy an object when we want to work on it. The [&other] syntax allows us to avoid the copy. The lambda then has a local field of type Point const&. Of course, for small types, this has little significance, but we may not want to copy other, larger objects that we need to capture, right?

Well, but wouldn’t it be simpler to just pass other as an argument in our lambda? Why this capture?

An excellent question. Let’s show how it would look in the code:

template <
        typename Range,
        typename Comparator = std::ranges::less,
        typename Projection = std::identity
>
auto min(Range& range, Comparator comparator = {}, Projection projection = {}) {
    auto current  = range.begin();
    auto end      = range.end();
    auto minSoFar = *current;

    while (++current != end) {
        auto currentProjected = projection(*current);
        auto minProjected     = projection(minSoFar);

        if (comparator(currentProjected, minProjected)) {
            minSoFar = *current;
        }
    }

    return minSoFar;
}

The part where the projection is used is what interests us the most:

As you can see, the current “candidate” and the object currently considered “smallest” are passed through the projection, and then the results of this projection are passed to the comparator.

The algorithm calls the projection with one argument at a time. Always.

This effectively nullifies our idea of passing the second argument to the projection. Simply put, the architecture and usage pattern of the projection prevent us from creating such a solution. Hence, the need for “side doors” for additional objects — in the form of the capture group.
