Chapter 5.2 - Enumerations

Posted Mar 30, 2025
By Filip Kwiatkowski
5 min read

Enumerated types

Sometimes, we want to represent a more restrictive range of data, and sometimes a less restrictive range of data. Sometimes we want to use long long to store potentially huge numbers, and sometimes we want to use char to ensure that we only deal with single-byte variables.

The problem arises when our target range of data is not equal to any built-in type. How can we mark in the type system that we want an object to store only numbers from 0 to 5? Or maybe we want to store values between 1 and 3? Perhaps 1, 2, 4, and 5, but not 3? Or maybe we want to store some named values, like directions such as north, east, south, and west, but none others.

Of course, in such cases, we can use built-in types like int or std::string and validate the correctness of the stored data with every modification.

Alternatively, we can try to create our own class that will wrap such an int or std::string, providing public methods that will automatically perform such validation.

Or — simplest of all — we can use an enumerated type. In Java, it was enum, and in C++, it’s enum class.

In C++, there’s also the “raw” enum. However, it should not be used — it’s a less safe version of this tool. You should always use enum class.

Defining and using enumerated types

To create your own enumerated type, use the appropriate keywords and define the legal values within curly braces:

enum class Direction {
    North, East, South, West
};

The defined type Direction can be used to create a variable1:

Enumerations instead of boolean arguments

Enumerations also allow replacing many places where a bool argument would be unintuitive to use. For example, let’s assume we’re creating a function equalContents, which should return true when both vectors passed as arguments have the same content:

1
2
3
4
5
6

template <typename T>
auto equalContents(
        std::vector<T> const& left, std::vector<T> const& right
) -> bool {
    return left == right;
}

Everything is fine until someone says: “But actually, the vector 1 2 3 has the same content as 3 2 1, just in a different order”.

That’s correct. We can either ignore it or add a function equalContentsIgnoreOrder(). On the other hand, we can add an argument to the created function that will determine whether to care about the order of elements or not:

1
2
3
4
5

8

template <typename T>
auto equalContents(
        std::vector<T> const& left, std::vector<T> const& right,
        bool const orderingRequired
) -> bool {
    if (orderingRequired) return left == right;
    else return std::ranges::is_permutation(left, right);
}

The function looks good again — we can call it with an argument of true when we want to require identical element order, or with an argument of false when we don’t care about the order of elements.

std::ranges::is_permutation() checks whether both ranges contain identical elements that may be arranged in a different order.

Nevertheless, it’s hard to ignore that if one doesn’t know the name of the third parameter of the equalContents() function, it’s not entirely clear how to call it. What does equalContents(vec1, vec2, true) mean? What does true signify? On one hand, it’s clear — orderingRequired is a good name that clearly indicates that passing true requires maintaining the order.

The problem is that an equally good name would be ignoreOrdering. In such a case, passing true would mean something completely different.

While nowadays, it’s easy to peek at parameter names through powerful programming environments (IDEs), it’s still worth going a step further to make it easier for people reading our code in the future — consider using an enumeration type.

The idea is to create a type Ordering, which will have only two possible values — Required and NotRequired. Then, based on it, we will either delegate the comparison to the == operator or to std::ranges::is_permutation. The entire code with an example looks like this:

#include <algorithm>
#include <vector>

#include <fmt/base.h>

enum class Ordering {
    Required, NotRequired
};

template <typename T>
auto equalContents(
        std::vector<T> const& left, std::vector<T> const& right,
        Ordering const ordering
) -> bool {
    if (ordering == Ordering::Required) return left == right;
    else return std::ranges::is_permutation(left, right);
}

auto main() -> int {
    auto v1 = std::vector<int>{1, 2, 3};
    auto v2 = std::vector<int>{3, 2, 1};

    fmt::println(
            "{} {}",
            equalContents(v1, v2, Ordering::Required),
            equalContents(v1, v2, Ordering::NotRequired)
    );
}

It might seem insignificant, but when we read tens of thousands of lines of code a day while working, such — as it may seem — excessive emphasis on obviousness is a certain indicator of high-quality code.

It’s worth noting that our type Ordering effectively does the same thing as bool. It has only two legal values. However, giving it a more meaningful and precise name, and enforcing it to be “more obvious” when calling the equalContents() function, makes such code easier to read.

  1. The presented method initializes the variable currentDirection with the value Direction::North. This is because, during such initialization, we attempt to convert the value 0 to Direction. The value 0 stems from the fact that when we create a direct-initialized numerical value (e.g., by writing int() or char()), an object with the value 0 is created. Enumerations (enumerated types) in C++ are overlays on some underlying numerical type working “in the background.” When we don’t specify any numerical values, the legal enumerated values start from 0 for the first one, 1 for the second one, 2 for the third one, and so on. ↩
