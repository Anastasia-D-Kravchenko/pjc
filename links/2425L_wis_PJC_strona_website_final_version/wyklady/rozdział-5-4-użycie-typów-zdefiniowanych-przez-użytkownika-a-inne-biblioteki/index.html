Mamy zatem punkt zaczepienia, gdzie szukać podpowiedzi: https://fmt.dev/latest/api.html#udt

Jak możemy przeczytać w podlinkowej sekcji, mamy dwie możliwości:

  1. Sprecyzować funkcję format_as() w tej samej przestrzeni nazw, co nasz typ (w tym przypadku w globalnej przestrzeni, bo nie objęliśmy naszego typu namespacem).
  2. Użyć specjalizacji szablonowej struktury formatter.

Opcja nr 2 jest trudna, więc skorzystajmy z opcji nr 1:

Use format_as if you want to make your type formattable as some other type with the same format specifiers. The format_as function should take an object of your type and return an object of a formattable type. It should be defined in the same namespace as your type.

~ Dokumentacja {fmt}.

Point wygląda jak para. {fmt} umie sformatować std::pair (gdy dołączymy <ranges.h>), dlatego zdefiniujemy format_as() dla Point tak, aby ta funkcja zwracała std::pair:

    int y;

    fmt::println("{}", point);

Wszystko działa!

No tak, ale czy przypadkiem nie tworzymy tutaj tymczasowego obiektu typu std::pair tylko po to, żeby fmt::println() wiedział, jak wyświetlić nasz Point? Brzmi jak nieoptymalne rozwiązanie.

Zgadza się. Używanie format_as() zwykle jest nieoptymalnym podejściem, ale wbrew pozorom rzadko trzeba się tym przejmować. Wyświetlanie tekstu jest z reguły bardzo obciążającą operacją dla programu i stworzenie dodatkowego (relatywnie małego) obiektu (czy nawet dwóch) per wyświetlany element nie jest aż tak znaczące w tym kontekście.

Chcąc osiągnąć optimum wydajności, należałoby skorzystać z opcji nr 2, czyli specjalizacji typu formatter. Jest to jednak nieproporcjonalnie trudniejsze, dlatego zostaniemy raczej przy podejściu z format_as().

Maksimum wygody, minimum wydajności

W świecie Javy nikt się nie przejmuje, że wyświetlając obiekt przy pomocy System.out.println() wywoływana jest metoda .toString(), która konstruuje tymczasowy obiekt typu String, który stanie się bezużyteczny tuż po zakończeniu wyświetlania. Jeżeli nie interesuje nas optimum wydajności przy procesie wyświetlania (którego i tak najwolniejszą częścią jest interakcja ze światem zewnętrznym, a nie przygotowanie tymczasowych obiektów), możemy, zamiast szukać typów, z którymi fmt umie pracować, po prostu zawsze domyślnie zwracać std::string:

#include <fmt/format.h>

struct Point {
    int x;
    int y;
};

auto format_as(Point const p) { return fmt::format("({}, {})", p.x, p.y); }

fmt::format() zwraca std::string, który — oczywiście — {fmt} umie sformatować.

#include <utility>

struct Point {
    int x;
    int y;

auto format_as(Point const p) { return std::pair<int, int>(p.x, p.y); }

auto main() -> int {
    auto points = std::vector<Point>();

    points.push_back(Point(3, 14));
    points.push_back(Point(2, 71));
    points.push_back(Point(1, 61));

    fmt::println("{}", points);

    fmt::println("{}", points);

Powyższy listing pozwala na kilka ciekawych obserwacji:

  • fmt::println(), gdy wyświetla zakres typów zdefiniowanych przez użytkownika, respektuje nasze własne zasady formatowania.
  • Istnieje wiele sposobów na wypełnienie wektora punktami — przede wszystkim możemy je dodawać przy pomocy .push_back(), ale jednocześnie możemy też zdecydować się na użycie listy inicjalizacji (jak to widać w linijce nr 22).
  • Stworzenie punktu nie ogranicza się tylko do czegoś, co wygląda jak klasyczne wywołanie konstruktora (np. Point(5, 6)). Można też je tworzyć przy pomocy klamer (Point{1, 2} oraz {3, 4}). Fakt, że klamry są tutaj dozwolone, wywodzi się z języka C. Dodatkowo, gdy oczekiwany typ jest znany, można pominąć jego nazwę (pamiętamy o literale domyślnych wartości — {}).

Kontenery wymagające dodatkowej funkcjonalności

Niestety, gdy spróbujemy stworzyć std::set<Point> czy std::map<Point, T>, kompilator zaprotestuje. To dlatego, że — jak wiemy — elementy std::set oraz klucze w std::map są przechowywane w kolejności rosnącej. Tylko co to znaczy, że jeden Point jest “większy” od drugiego? Nie wiemy tego ani my, ani kompilator — stąd brak możliwości przechowywania tych elementów w tych kontenerach.

Nie oznacza to jednak, że posortowanie kontenera punktów jest niemożliwe.

Wpierw jednak musimy sami sobie odpowiedzieć na pytanie, co to znaczy, że jeden punkt jest “większy” od drugiego.

W matematyce punkty nie mają dobrze zdefiniowanego porządku. Zatem możemy wymyślić kompletnie dowolną strategię. W ramach tego rozdziału punkty zostaną uporządkowane względem ich odległości do punktu \((0, 0)\). W ramach tej strategii stworzymy w Point metodę, która zwraca odległość do tego punktu:

#include <algorithm>
#include <cmath>    // std::hypot
#include <utility>
#include <vector>

#include <fmt/ranges.h>

struct Point {
    int x;
    int y;

        return std::hypot(x, y);

};

auto format_as(Point const p) { return std::pair<int, int>(p.x, p.y); }

auto main() -> int {
    auto points = std::vector<Point>{ {1, 2}, {0, 0}, {2, 0} };
    std::ranges::sort(points, [](Point const left, Point const  right) {
        return left.distanceToOrigin() < right.distanceToOrigin();
    });
    fmt::println("{}", points);
}

Ok, ale o co chodziło z tym const w dziwnym miejscu w nagłówku metody .distanceToOrigin()?

Doskonałe pytanie. Jest to tak zwana const metoda, czyli metoda stała.

const metody

Metody stałe, czyli const member functions, powstają, gdy tuż przed strzałką (->) precyzującą typ zwracany dopiszemy słowo kluczowe const.

const metoda (metoda stała) różni się od “klasycznej” w taki sposób, że obiecuje, że jej wywołanie nie zmieni stanu obiektu.

Jest to bardzo istotne, ponieważ gdybyśmy mieli const obiekt, to nie powinniśmy być w stanie modyfikować jego stanu. A skoro nie powinniśmy być w stanie modyfikować jego stanu, to nie powinniśmy być w stanie wywołać metody, która może ten stan zmienić.

Spójrzmy na to z logicznego punktu widzenia — na, przykładowo, const std::vector<int> nie możemy wywołać .push_back() czy .erase(), prawda? Przecież zmieniają one stan obiektu. Ale już nic nie stoi na przeszkodzie, aby wywołać na takim obiekcie metodę .size() czy .empty(). To dlatego, że są to const metody.

Na const obiekcie możemy wywoływać tylko const metody. Na “klasycznym” (nie const / mutowalnym) obiekcie możemy wywoływać zarówno const jak i nie-const metody.

Tak samo, jak w przypadku obiektów, domyślnym powinno być oznaczanie metod jako const. Gdy tego nie zrobimy (a metoda ani nie powinna, ani faktycznie nie zmienia stanu obiektu), to nie tylko będziemy błędnie oznaczać nasze intencje, ale też często nasz kod nie będzie działać — głównie z uwagi na to, jak popularne są const referencje. Taka referencja, nawet jeśli jest połączona z nie-const obiektem, nie będzie mogła wywołać nie-const metody.

Sortowanie w std::set

Brzmi dobrze, ale skoro możemy rozwiązać problem niesortowalnych punktów przy pomocy komparatora w momencie używania std::ranges::sort(), to czy nie możemy zrobić tego w podobny sposób tak, aby móc stworzyć std::set<Point>?

Możemy, ale jest to nieco bardziej skomplikowane. Przykład zostanie umieszczony w podsumowaniu i dodatkach tego rozdziału.

Grupa przechwytująca lambdy

Lambda-capture group, czyli grupa przechwytująca lambdy pozwala lambdzie operować na obiektach, które nie zostały przekazane do niej przez argumenty.

Załóżmy przykład, gdzie wśród grupy punktów chcemy znaleźć taki, który jest najbliższy jakiemuś innemu punktowi. Przykładowa funkcja, która realizuje ten cel, może mieć następujący nagłówek:

1

auto closestTo(std::vector<Point> const& points, Point const other) -> Point;

Czyli wśród points szukamy takiego elementu, który jest najbliższej other.

Jej użycie wygląda następująco:

Implementacja closestTo() nie wydaje się być wyjątkowo skomplikowana. Można użyć komparatora, który oblicza odległość obydwu swoich argumentów do other i zwraca true, jeżeli odległość lewego argumentu jest bliższa.

Nie sposób jednak nie zauważyć, że efektywnie porównujemy odległości. Odległości rozważanych punktów do other. W takim razie użyjmy projekcji zamiast komparatora. Patrzmy na wszystkie elementy z points poprzez ich odległości do other i znajdźmy najmniejszą z nich przy użyciu std::ranges::min:

auto closestTo(std::vector<Point> const& points, Point const other) -> Point {
    return std::ranges::min(points, {}, [](Point const candidate) {
        return std::hypot(candidate.x - other.x, candidate.y - other.y);
    });
}

Rozwiązanie wydaje się dosyć proste. Zgodnie z wcześniejszym planem, używamy std::ranges::min() oraz lambdy, która jest projekcją naszych punktów z points na ich odległość do other.

Prawie. Aby zrozumieć problem, wróćmy do “bardziej podstawowego” narzędzia. Zamiast z lambdy, skorzystajmy ze zwykłej funkcji:

    return std::hypot(candidate.x - other.x, candidate.y - other.y);

    return std::ranges::min(points, {}, projectDistance);

Przyglądając się dokładnie funkcji projectDistance() możemy już dosyć jasno zidentyfikować błąd. Skąd ta funkcja ma wiedzieć, czym jest other?

Lambdy to skrócony zapis tworzenia obiektu o anonimowym typie, który udostępnia nam specjalną funkcjonalność (w postaci specjalnej funkcji), która pozwala używać go jak zwykłą funkcję (czyli wywoływać za pomocą () po nazwie).

Skoro koniec końców jakaś funkcja o ciele identycznym, jak to, które precyzujemy w lambdzie, jest tworzona, to nic dziwnego, że jej ciało nie ma pojęcia, czym jest other.

Na szczęście istnieje ratunek. W końcu lambdy zostały stworzone głównie po to, aby móc ich wygodnie używać w środku innych funkcji. Funkcje często wprowadzają lokalne zmienne, a więc logicznym byłoby założyć, że ktoś chciałby stworzyć lambdę operującą na tych zmiennych.

Realizacją tego założenia jest narzędzie o nazwie grupa przechwytująca. To ten niewinnie wyglądający fragment [], który zawsze piszemy na początku lambdy.

Cały problem zostanie rozwiązany, jeżeli wstawimy tam nazwę other:

2
3

auto closestTo(std::vector<Point> const& points, Point const other) -> Point {
    return std::ranges::min(points, {}, [other](Point const candidate) {
        return std::hypot(candidate.x - other.x, candidate.y - other.y);
    });
}

Składnia [other] w kontekście lambdy każe jej skopiować ten obiekt do swojej lokalnej pamięci. Tak samo jak Point ma pole int x i int y, teraz nasza lambda ma pole Point const other.

Dokładny mechanizm, który umożliwia nam te operacje, zostanie omówiony w przyszłości — wtedy zaimplementujemy “od zera” klasę, która może się zachowywać jak funkcja.

Na ten moment należy zapamiętać, że logika lambd jest podobnie ograniczona jak ta aplikująca się do zwykłych funkcji. Jeżeli nie przekażemy nieglobalnego obiektu przez argument, to lambda nie może na nim pracować. Jedynym sposobem, aby ten problem rozwiązać, to przechwycić obiekty, z których chcemy skorzystać.

Składnia [other] kopiuje punkt do lambdy, ale nie zawsze chcemy obiekt kopiować, gdy interesuje nas praca nad nim. Składnia [&other] pozwoli nam uniknąć kopii. Lambda wtedy ma lokalne pole typu Point const&. Oczywiście w przypadku małych typów ma to małe znaczenie, ale niekoniecznie chcemy kopiować inne, duże obiekty, które musimy przechwycić, prawda?

No dobrze, ale czy nie prościej byłoby po prostu w naszej lambdzie przekazać other przez argument? Po co ten capture?

template <
        typename Range,
        typename Comparator = std::ranges::less,
        typename Projection = std::identity
>
auto min(Range& range, Comparator comparator = {}, Projection projection = {}) {
    auto current  = range.begin();
    auto end      = range.end();
    auto minSoFar = *current;

    while (++current != end) {
        auto currentProjected = projection(*current);
        auto minProjected     = projection(minSoFar);

        if (comparator(currentProjected, minProjected)) {
            minSoFar = *current;
        }
    }

    return minSoFar;
}
