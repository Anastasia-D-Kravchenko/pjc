Rozdział 11.1 - Inteligentne wskaźniki

Opublikowano May 20, 2025

Wskaźnik surowy a wskaźnik inteligentny

Wskaźnik surowy to taki, który nie robi nic innego, jak tylko wskazuje na dane. “Klasyczny” T*. Przykładowo:

1
2
3
4
5
6

auto main() -> int {
    auto localInt = int();

    auto first  = &localInt;
    auto second = new int();
}

Tutaj zarówno first jak i second to surowe wskaźniki. Niewątpliwie potrafią one stanowić problem. O ile z first wszystko jest w porządku, bo wskazuje jedynie na obiekt o automatycznym czasie życia (czyli tutaj na localInt), to second wskazuje na obiekt o dynamicznym czasie życia. Musimy zatem pamiętać, aby za jego pomocą wywołać delete, bo inaczej spotkamy się z wyciekiem pamięci.

Pojawia się jednak pytanie — dlaczego? Czemu wskaźniki “nie umieją po sobie posprzątać”? Czemu second nie może samo wywołać delete?

Odpowiedź jest relatywnie prosta — ponieważ legalne jest stworzenie takiego wskaźnika jak first. Nic nie stoi na przeszkodzie, aby tworzyć wskaźniki do obiektów o innym czasie życia niż dynamiczny. Lub tworzyć wiele wskaźników do jednego obiektu. Gdyby każdy taki wskaźnik wywoływał delete, to mielibyśmy multum problemów.

Na szczęście jest proste rozwiązanie — wiemy, że gdy operujemy na dynamicznie alokowanej pamięci, to musimy korzystać ze wskaźników. Gdy możemy, to unikamy ich bezpośredniego użycia — np. stosując odpowiedni kontener. Czasem jednak po prostu potrzebujemy wskaźnika, który wskazuje na dynamicznie zaalokowane dane. Taki wskaźnik powinien zarządzać tą pamięcią. Powinien on w jakiś sposób się wyróżniać, aby było wiadomo, że to wskaźnik na dane, które trzeba usunąć.

Dlatego wykorzystano możliwości płynące z tego, jak w C++ działają destruktory i stworzono tak zwane inteligentne wskaźniki. Najważniejszym z nich jest tak zwany wskaźnik unikalny, czyli std::unique_ptr.

std::unique_ptr

std::unique_ptr jest bardzo prostym narzędziem. Przechowuje on surowy wskaźnik na dane i jego destruktor wywołuje delete (lub delete[] — on sam wie, które ma wywołać) na tym wskaźniku. Spójrzmy na prosty przykład:

1
2
3
4
5
6
7
8

11

#include <memory> // std::unique_ptr

auto main() -> int {
    {
        auto iLeakMemory = new int();
    }

    {
        auto iDontLeakMemory = std::unique_ptr<int>(new int());
    }
}

Jak same nazwy wskazują, iLeakMemory, przez to, że nie wywołujemy na nim delete, powoduje wyciek pamięci w nr 6. Ale już iDontLeakMemory, będąc inteligentnym wskaźnikiem, nie powoduje żadnego wycieku pamięci. Obydwa obiekty (te nazwane wskaźniki) giną linijkę niżej pod tą, w której powstały, ale tylko nasz inteligentny wskaźnik wie, że powinien zwolnić jakąś pamięć — więc to robi.

Składnia std::unique_ptr<T>(new int()) może nie jest wyjątkowo trudna do zrozumienia (w końcu jedynie “opakowujemy” surowy wskaźnik w inteligentny), ale jednak nie pisze się jej najprzyjemniej. Warto skorzytać z funkcji-fabryki:

Zamiast korzystać z podstawowej składni std::unique_ptr<T>(new T()), warto używać wygodniejszej metody-fabryki: std::make_unique<T>().

Używając std::make_unique<T>(), w nawiasach podajemy argumenty konstruktora do T. Na przykład, aby stworzyć inteligentny wskaźnik na dynamicznie alokowanego inta o wartości 10, można zrobić tak:

1

auto ptr = std::make_unique<int>(10);

Podobnie z std::string:

1

auto ptr = std::make_unique<std::string>("initial text"):

Działa to też z konstruktorami, które pobierają wiele argumentów (nawet jeśli są domyślne):

1
2

auto first  = std::make_unique<std::vector<int>>(3);
auto second = std::make_unique<std::vector<int>>(3, 7);

first jest wskaźnikiem na wektor przechowujący 0 0 0, a second na wektor przechowujący 7 7 7.

Wygodnie jest też korzystać z tablicowych wersji tych funkcji-fabryk:

1
2
3
4
5

#include <memory>

auto main() -> int {
    auto tenInts = std::make_unique<int[]>(10);
}

Wtedy w nawiasach okrągłych podajemy wielkość tablicy.

Praktyczne wykorzystanie szablonu std::unique_ptr

Dobrym pomysłem może być zamienienie implementacji naszego wektora z poprzedniego rozdziału na taką, która korzysta z inteligentnych wskaźników. Zobaczmy, czy będzie to trudne i jak się kod zmieni. Zacznijmy od podstaw:

#include <memory>

namespace pjc::smart {
    template <typename T>
    class Vector {
        int size_ = 0;
        std::unique_ptr<T[]> memory_ = nullptr;
    };
}

Nic nie stoi na przeszkodzie, aby std::unique_ptr (tutaj — do tablicy elementów typu T) był polem w obiektach jakiejś klasy. Dodajmy publiczne metody:

namespace pjc::smart {
    template <typename T>
    class Vector {
        int size_ = 0;
        std::unique_ptr<T[]> memory_ = nullptr;

    public:
        auto size() const -> int {
            return size_;
        }

        auto push_back(T const& newElement) -> void {
            
        }
    };
}

I skoncentrujmy się na implementacji .push_back(). Wpierw ta metoda jest pusta, ale wiadomo, że na pewno musimy zaalokować większy bufor pamięci i zwiększyć wartość pola .size_:

1
2
3
4
5

auto push_back(T const& newElement) -> void {
    size_ += 1;

    auto biggerMemory = std::make_unique<T[]>(size_);
}

Warto zwrócić uwagę, że mimo iż jeszcze nic ciekawego nie zrobiliśmy, na pewno nie mamy żadnych wycieków pamięci. Użyjmy naszego wektora w następujący sposób:

1
2
3
4

auto main() -> int {
    auto vec = pjc::smart::Vector<int>();
    vec.push_back(7);
}

.push_back() zaalokowało pamięć, ale jako że wskazywał na nią obiekt typu std::unique_ptr, który umarł podczas kończenia działania tej metody, ta większa pamięć została poprawnie zwolniona. Dodatkowo warto zwrócić uwagę, że gdy vec ginie w main()ie, to giną też jego pola — .size_ i .memory_. To drugie to inteligentny wskaźnik, więc na pewno poprawnie wywoła delete[] (tablicowy — wie to ze swojego typu).

Podczas alokowania większej ilości pamięci, należy skopiować wszystkie elementy z poprzedniego, mniejszego segmentu do nowego. std::unique_ptr wspiera indeksowanie, ale zamiast używania surowej pętli, można wywołać na nim .get(), który zwróci kopię wewnętrznego wskaźnika na dane. Wskaźnik jest legalnym iteratorem1, więc będziemy mogli skorzystać z algorytmu std::ranges::copy_n:

1
2
3
4
5
6

auto push_back(T const& newElement) -> void {
    size_ += 1;

    auto biggerMemory = std::make_unique<T[]>(size_);
    std::ranges::copy_n(memory_.get(), size_ - 1, biggerMemory.get());
}

Należy jeszcze dodać nowy element na koniec naszego większego bloku pamięci:

1
2
3
4
5
6
7

auto push_back(T const& newElement) -> void {
    size_ += 1;

    auto biggerMemory = std::make_unique<T[]>(size_);
    std::ranges::copy_n(memory_.get(), size_ - 1, biggerMemory.get());
    biggerMemory[size_ - 1] = newElement;
}

I teraz odpowiednio nadpisać .memory_ tak, aby dawało nam dostęp do nowej, większej tablicy:

1
2
3
4
5

8

auto push_back(T const& newElement) -> void {
    size_ += 1;

    auto biggerMemory = std::make_unique<T[]>(size_);
    std::ranges::copy_n(memory_.get(), size_ - 1, biggerMemory.get());
    biggerMemory[size_ - 1] = newElement;
    memory_ = biggerMemory;
}

Niestety ostatnia linijka nie zadziała. To dlatego, że obiektów typu std::unqiue_ptr nie można tak po prostu kopiować lub nadpisywać.

Obiekty typu std::unique_ptr są niekopiowalne i nie można ich nadpisywać innymi obiektami2.

Można jednak zrobić sprytną sztuczkę. Załóżmy, że .memory_ wskazuje na tablicę 3 intów i właśnie dodajemy czwartego. Zwróćmy uwagę na to, jak wygląda nasza pamięć tuż pod koniec wykonywania metody .push_back() (bez niekompilującego się fragmentu memory_ = biggerMemory):

block-beta
  columns 3
  A("memory_") space C["｜ 1 ｜ 2 ｜ 3 ｜"]
  B("biggerMemory") space D["｜ 1 ｜ 2 ｜ 3 ｜ 4 ｜"]
  A --> C
  B --> D

Gdyby metoda zakończyła teraz działanie, .memory_ by dalej wskazywało “starą” tablicę, a biggerMemory by usunęło naszą nową, większą tablicę. Jednak my przecież chcemy, żeby było zupełnie odwrotnie!

Prostą sposobem na naprawienie tego problemu będzie zamienienie tego, na co wskazują te inteligentne wskaźniki:

block-beta
  columns 3
    A("memory_") space C["｜ 1 ｜ 2 ｜ 3 ｜"]
    B("biggerMemory") space D["｜ 1 ｜ 2 ｜ 3 ｜ 4 ｜"]
    A --> D
    B --> C

Można to bardzo prosto osiągnąć przy pomocy std::ranges::swap(), który umie zamieniać wartościami nie tylko zakresy:

1
2
3
4
5

8

auto push_back(T const& newElement) -> void {
    size_ += 1;

    auto biggerMemory = std::make_unique<T[]>(size_);
    std::ranges::copy_n(memory_.get(), size_ - 1, biggerMemory.get());
    biggerMemory[size_ - 1] = newElement;
    std::ranges::swap(memory_, biggerMemory);
}

Warto jeszcze raz przyjrzeć się temu, czemu ta “sztuczka” działa. Po omawianej zamianie obiekt biggerMemory, który jest lokalną zmienną (o automatycznym czasie życia), będzie wskazywał na starą, mniejszą tablicę, a pole .memory_ będzie wskazywało na nową, większą tablicę obiektów.

Jako że biggerMemory to lokalny std::unique_ptr, to wraz z końcem wykonania metody .push_back() zginie. Zginie, zabierając ze sobą tę starą tablicę. W końcu jest inteligentnym wskaźnikiem i ginąć zwolni pamięć, na którą wskazuje.

#include <algorithm>
#include <memory>

namespace pjc::smart {
    template <typename T>
    class Vector {
        int size_ = 0;
        std::unique_ptr<T[]> memory_ = nullptr;

    public:
        auto size() const -> int {
            return size_;
        }

        auto push_back(T const& newElement) -> void {
            size_ += 1;

            auto biggerMemory = std::make_unique<T[]>(size_);
            std::ranges::copy_n(memory_.get(), size_ - 1, biggerMemory.get());
            biggerMemory[size_ - 1] = newElement;
            std::ranges::swap(memory_, biggerMemory);
        }
    };
}

auto main() -> int {
    while (true) {
        auto vec = pjc::smart::Vector<int>();
        vec.push_back(7);
    }
}

Taki kod nie powoduje żadnych wycieków pamięci. Jest krótszy i prostszy od tego, który powstał przy użyciu surowych wskaźników na dynamicznie alokowaną pamięć.

Konsekwencje niekopiowalności

std::unique_ptr nie może być skopiowany. To dlatego, że gdyby mógł, to moglibyśmy mieć dwa takie wskaźniki wskazujące na takie same dane. Po pewnym czasie moglibyśmy wtedy spróbować zniszczyć obydwa, co by skutkowało problemem podwójnego usunięcia, czyli UB.

Wbrew pozorom to dobra wiadomość. Przypomnijmy sobie, że gdy mieliśmy do czynienia z własną implementacją wektora używającą surowych wskaźników, to kopiowanie tego wektora prowadziło do szybkiego UB.

Tutaj znaleźliśmy się w dużo lepszej sytuacji. Operacja kopiowania, która prowadziłaby do błędów, zwyczajnie się nie kompiluje! To dobrze. Wiemy zatem, że coś pominęliśmy — naprawmy to. Od razu dostarczy konstruktor kopiujący i operator nadpisania:

Vector() = default;

Vector(Vector const& other)
    : size_(other.size_), memory_(std::make_unique<T[]>(other.size_)) {
    std::ranges::copy_n(other.memory_.get(), size_, memory_.get());
}

auto operator=(Vector copiedOther) -> Vector& {
    std::ranges::swap(memory_, copiedOther.memory_);
    std::ranges::swap(size_, copiedOther.size_);
    return *this;
}

Kolejno zdefiniowaliśmy:

  1. Domyślny konstruktor. Musimy go dostarczyć (choćby oznaczając jako = default), bo gdy dostarczymy konstruktor kopiujący, to C++ przestaje automatycznie generować inne konstruktory.
  2. Konstruktor kopiujący. Alokuje on odpowiednio pamięć i kopiuje elementy z innego wektora.
  3. Operator nadpisania. Korzysta on z tak zwanego idiomu kopiowania i zamieniania (ang. copy and swap idiom), czyli tworzy lokalną kopię wektora-źródła, zamienia nasze pola z tą kopią i na koniec niszczy tę kopię. Dodatkowo warto zwrócić uwagę, że zwraca *this, czyli referencję na nadpisywany obiekt. Dzięki temu można korzystać ze składni vec1 = vec2 = vec3 = ...;.

Z jednej strony std::unique_ptr wydaje się trudnym i nieprzyjemnym narzędziem. Nie pozwala na kopiowanie, nie pozwala na iterowanie i bez dostarczenia dodatkowego kodu (jak np. konstruktor kopiujący) nie pozwoli na skopiowanie obiektów zawierających go jako pole. Ale koniec końców okazuje się, że pozwala nam na pisanie krótszego i bezpieczniejszego kodu, a elementy, bez których się nie kompiluje, i tak byśmy musieli sami dostarczyć — prędzej czy później.

  1. Surowy wskaźnik jest legalnym iteratorem. Nie można używać std::unique_ptr jak zwykłego iteratora. ↩

  2. Można nadpisywać i kopiować z przenoszeniem (tematyka semantyk przenoszenia, (ang. move semantics)), ale jeszcze tego nie umiemy. ↩
