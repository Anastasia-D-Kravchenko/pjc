Rozdział 10.1 - Problem z polimorficznym kontenerem

Opublikowano May 7, 2025
Autor Filip Kwiatkowski
4 min czytania

Najczęstsze wykorzystania polimorfizmu

Polimorfizm lśni wtedy, gdy przygotowujemy jakiś fragment kodu akceptujący jakąś hierarchię typów, które wspierają daną gamę zachowań.

W aplikacjach graficznych (GUI) mamy do czynienia z kolekcjami kontrolek (ang. widget), gdzie kontrolką może być przycisk, tekst czy osobny kontener przechowujący inne kontrolki. Każda kontrolka umie siebie wyrysować — czasem polega to na wyrysowaniu tekstu, czasem na narysowaniu czegoś na kształt przycisku, a czasem na wyrysowaniu wszystkich podkontrolek (przypadek, gdy elementem jest dodatkowa kolekcja kontrolek).

W grach komputerowych często dowolny byt (ang. entity) jest reprezentowany przez jakąś wspólną klasę bazową. Przykładowo, wszystkie elementy w grach tworzonych w silniku Unity, które mają przechowywać jakieś dane lub być identyfikowalne, muszą dziedziczyć po klasie Entity. Podobna sytuacja ma miejsce w przypadku silnika Unreal Engine, gdzie mamy klasy Actor czy Object.

W obydwu tych przypadkach mamy do czynienia nie tylko z pojedynczymi funkcjami, które akceptują polimorficzny parametr, ale głównie z polimorficznymi kontenerami. To znaczy z takimi kontenerami, które przechowują obiekty różnych typów.

Kłóci się to trochę z naszym pojęciem bezpieczeństwa typów. Bo przecież zarówno w Javie, jak i w C++, nie możemy w tablicy przechowującej napisy nagle umieścić liczby całkowitej. O ile jest to prawdą, to już w Javie poznaliśmy sposób na pewne obejście tego problemu. Kolekcje (w tym tablice; a w C++ wszystkie kontenery) jak najbardziej mogą przechowywać obiekty różnych typów, o ile te typy mają wspólną klasę bazową.

Polimorficzny kontener

Stwórzmy przykład, bazując na znanej nam już hierarchii klas zwierząt (dodatkowo oznaczając, że metoda .makeSound() nie zmodyfikuje obiektu, na rzecz którego jest wywołana; osiągniemy to oznaczając ją jako const):

struct Animal {
    virtual auto makeSound() const -> void { }

struct Cat : Animal {
    auto makeSound() const -> void override {
        fmt::println("Meow");
    }

struct Dog : Animal {
    auto makeSound() const -> void override {
        fmt::println("Woof");

#include <algorithm>    // std::ranges::shuffle
#include <random>       // std::random_device
#include <vector>

#include <fmt/base.h>

struct Animal {
    virtual auto makeSound() const -> void { }
};

struct Cat : Animal {
    auto makeSound() const -> void override {
        fmt::println("Meow");
    }
};

struct Dog : Animal {
    auto makeSound() const -> void override {
        fmt::println("Woof");
    }
};

auto main() -> int {
    auto animals = std::vector<Animal>();

    for (auto i = 0; i < 5; i++) animals.push_back(Cat());
    for (auto i = 0; i < 5; i++) animals.push_back(Dog());

    std::ranges::shuffle(animals, std::random_device());

    for (auto const& animal : animals) {
        animal.makeSound();
    }
}

Naturalnie oczekujemy, że wynikiem uruchomienia tego programu będzie pięciokrotne wyświetlenie napisu Meow i pięciokrotne wyświetlenie napisu Woof, w losowej kolejności. Tak jednak nie jest, ale zanim zobaczymy, dlaczego, warto szybko wyjaśnić, co kolejno robimy w kodzie powyżej:

1
2

for (auto i = 0; i < 5; i++) animals.push_back(Cat());
for (auto i = 0; i < 5; i++) animals.push_back(Dog());

Tutaj dodajemy do wektora po pięć obiektów klas Cat oraz Dog.

1

std::ranges::shuffle(animals, std::random_device());

Tutaj losujemy kolejność elementów wektora (tasujemy go — jak talię kart)1.

Teraz przejdźmy do outputu. Niestety, ku naszemu zdziwieniu, nie ujrzymy nic.

To dlatego, że przez object slicing nie będziemy wykonywać operacji na obiektach typu Cat czy Dog, tylko na “surowych” Animal.

Ale jak to? Przecież nawet w pętli for () w 31. linijce użyliśmy referencji, aby zapobiec temu problemowi.

Zgadza się. Niestety ten problem wystąpił już wcześniej. Konkretnie w linijce 24.

std::vector przechowuje swoje elementy w sąsiadujących miejscach w pamięci. Dlatego musi wiedzieć, ile każdy z nich zajmuje pamięci. Wie to dzięki sprecyzowaniu argumentu szablonowego (<Animal> w std::vector<Animal>). Ma to jednak pewne konsekwencje — dla każdego swojego elementu rezerwuje on miejsce wystarczające jedynie na Animal, a nie na całego Cat czy Dog. Już w samej deklaracji kontenera skazaliśmy się na object slicing.

Jak zatem go naprawić?

Użyć referencji… znowu?

Dobry trop, choć niestety nie zadziała. Zamiana deklaracji kontenera z takiej:

1

auto animals = std::vector<Animal>();

Na taką:

1

auto animals = std::vector<Animal&>();

(dodatkowy znak & po Animal).

Poskutkuje około 230 linijkami błędu kompilacji. Niewiele będzie można z nich wyczytać, tak więc zapamiętajmy jedynie podsumowanie:

Nie można tworzyć kontenerów przechowujących referencje.

Dlaczego?

W dużym (i niepełnym, ale na ten moment wystarczającym) skrócie — bo referencje muszą być zainicjalizowane wraz z ich stworzeniem i nie mogą być później “przepinane”. Wektor wewnętrznie wykonuje operacje, które — gdybyśmy mieli wektor referencji — wymagałyby stworzenia ich w “niepołączonym” stanie. Następnie by je “przepiął” na inne obiekty. A — jak już powiedzieliśmy — tak się nie da.

Aby się dowiedzieć, dlaczego std::vector wykonuje takie operacje, należy zrozumieć, w jaki sposób działa wewnętrznie. Korzysta on z dynamicznie alokowanej pamięci, której poświęcony jest następny podrozdział.

  1. Takie użycie std::random_device nie jest optymalne, choć na pewno da nam lepszą gwarancję losowości od popularnie używanego std::rand(). Zainteresowanym polecam obejrzeć tę prelekcję. ↩
