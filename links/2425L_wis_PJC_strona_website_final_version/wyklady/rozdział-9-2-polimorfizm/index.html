Rozdział 9.2 - Polimorfizm

Opublikowano May 5, 2025
Autor Filip Kwiatkowski
5 min czytania

Polimorfizm

Polimorfizm, a właściwie polimorficzne wywołanie metody, polega na dostępie do obiektu typu dziedziczącego poprzez zmienną typu bazowego i wywołanie metody z klasy bazowej, która jest nadpisana we wspomnianej klasie dziedziczącej. Z perspektywy kogoś, kto tę metodę wywołuje, nie wiemy, z jakim konkretnie obiektem mamy do czynienia. Nie wiemy, jak konkretnie się ta metoda zachowa, ale wiemy, jaki rodzaj zachowania powinien mieć miejsce.

Przykładowo, mając klasę Animal, która potrafi wydawać dźwięki (ma metodę .makeSound()) oraz dwie dziedziczące po niej klasy — Cat oraz Dog, które nadpisują tę metodę, oczekujemy, że gdy zamiast “zwykłego” Animal dostaniemy Cat albo Dog i wywołamy .makeSound(), to wywoła się ich nadpisana wersja. Wyglądałoby to tak:

#include <fmt/base.h>

struct Animal {
    auto makeSound() const -> void { }
};

struct Cat : Animal {
    auto makeSound() const -> void {
        fmt::println("Meow");
    }
};

struct Dog : Animal {
    auto makeSound() const -> void {
        fmt::println("Woof");
    }
};

auto interactTwice(Animal animal) -> void {
    animal.makeSound();
    animal.makeSound();
}

auto main() -> int {
    auto a1 = Cat();
    auto a2 = Dog();
    interactTwice(a1);
    interactTwice(a2);
}

Taki kod pomyślnie przejdzie proces kompilacji — nie powinno być to zaskakujące. O ile interactTwice() przyjmuje parametr typu Animal, to możemy tam wysłać argumenty typu Cat oraz Dog, bo skoro te klasy dziedziczą po Animal, to są — w pewnym sensie — tymi zwierzętami. Dlatego nie ma żadnego problemu z kompilacją linijek 27 i 28.

Oczywiście oczekujemy, że wyświetli się następujący output:

To dlatego, że wywołały się wersje metody .makeSound() nie z Cat czy Dog, ale z Animal. Wynika to z następujących dwóch problemów:
  1. Metoda .makeSound() nie jest wirtualna.
  2. Mamy do czynienia z obcinaniem obiektów (ang. object slicing).
Dowiedzmy się, co to wszystko oznacza i rozwiążmy te problemy jeden po drugim.
Wirtualne metody
Aby polimorficzne wywołanie metody miało miejsce, coś musi wykonać pracę polegającą na sprawdzeniu faktycznego typu obiektu i, jeżeli ten typ nadpisuje wywoływaną metodę, wybrać tę nadpisaną wersję metody. Taki proces nazywany jest również wirtualnym wywołaniem metody i działa on wyłącznie dla metod wirtualnych.
W przypadku funkcji interactTwice(), z jej perspektywy parametr animal jest typu Animal i wywołując na nim .makeSound(), wywoływana jest implementacja z Animal. Nieważne, czy faktycznie przekażemy tam obiekt typu Animal czy Cat lub Dog.
Aby praca polegająca na faktycznym sprawdzeniu typu została wykonana, należy daną metodę oznaczyć jako wirtualną. Osiągamy to za pomocą słowa kluczowego virtual:

struct Animal {
//  auto makeSound() -> void { }               // old version
    virtual auto makeSound() const -> void { } // new version
};

Dzięki temu kompilator wygeneruje inny kod maszynowy1 dla wywołań metody .makeSound(). Kod ten będzie odpowiedzialny za wykonywanie tej pracy, o której była mowa w poprzednich trzech akapitach — sprawdzi faktyczny typ obiektu i jeżeli znajdzie w ramach tego typu nadpisaną wersję tej metody, to wywoła właśnie tę nadpisaną implementację.
Niestety, nie będzie to wystarczająca zmiana, aby oryginalny fragment kodu wyświetlił pożądany output. Wciąż będziemy widzieć puste linie.
Aby to naprawić, trzeba będzie poradzić sobie z drugim, wspomnianym problemem, czyli z obcinaniem obiektów.
Obcinanie obiektów
Object slicing, czyli obcinanie obiektów, polega na tym, że wysyłając argument typu dziedziczącego do funkcji, która oczekuje parametru typu bazowego2, informacja o tym, że jest to obiekt typu dziedziczącego, jest odcinana.
Ma to wbrew pozorom dużo sensu — C++ jest językiem o charakterze semantyki wartości, czyli wysyłając argument do funkcji, parametr funkcji staje się kopią tego argumentu. A skoro tworzona jest kopia, to wpierw należy przygotować na nią miejsce w pamięci operacyjnej programu. Jeżeli parametr jest typu Animal, to w pamięci alokowane jest miejsce wyłącznie na Animal.
Cat i Dog dziedziczą z Animal, więc mają wszystko to, co ta klasa bazowa. Mogą jednak być wzbogacone o dodatkowe pola i metody. Te dodatkowe elementy (pola, nadpisane wersje metod, itd.) są odcinane w procesie przekazywania argumentu przez kopię, gdy funkcje oczekuje typu bazowego.
Jak to zatem naprawić? Jak, zamiast kopiować, pracować na oryginale?
Użyć referencji.

#include <fmt/base.h>

struct Animal {
    virtual auto makeSound() const -> void { }        // virtual
};

struct Cat : Animal {
    auto makeSound() const -> void {
        fmt::println("Meow");
    }
};

struct Dog : Animal {
    auto makeSound() const -> void {
        fmt::println("Woof");
    }
};

auto interactTwice(Animal const& animal) -> void {    // reference
    animal.makeSound();
    animal.makeSound();
}

auto main() -> int {
    auto a1 = Cat();
    auto a2 = Dog();
    interactTwice(a1);
    interactTwice(a2);
}

Teraz już wszystko działa poprawnie — nie tracimy danych o faktycznym typie argumentów, ponieważ stosujemy referencję, a dzięki wirtualnemu wywołaniu metody, polimorficznie wywoływana jest wersja z odpowiedniej klasy dziedziczącej, a nie z klasy bazowej.
Podsumowując, polimorficzne wywołanie metody występuje wtedy, gdy wirtualna metoda jest wykonywana na obiekcie dziedziczącym poprzez referencję typu bazowego, gdzie ten dziedziczący typ nadpisuje tę metodę.
