Rozdział 4.1 - Szablony funkcji, cz. 1

Opublikowano Mar 24, 2025
Autor Filip Kwiatkowski
8 min czytania

Redukcja duplikacji kodu do generycznej, pojedynczej implementacji

Szablony funkcji stosuje się w celu zastąpienia implementacji działającej dla jednego typu implementacją, która działa dla wielu różnych typów.

Stosowanie szablonów to “krok dalej” w używaniu funkcji, a następnie przeciążeń funkcji.

Przykładowo, załóżmy, że nie mamy dostępu do biblioteki {fmt}, a bardzo często zdarza nam się chcieć wyświetlić kilka rodzajów wektorów. Wydaje się, że w takim wypadku najlepszym rozwiązaniem byłoby stworzenie zestawu przeciążeń funkcji, np. w ten sposób:

Od razu nasuwa się pewien prosty wniosek — mamy tu do czynienia z duplikacją kodu. Efektywnie ciała wszystkich przeciążeń funkcji print() są identyczne. W takich przypadkach warto zastąpić taki zestaw przeciążeń pojedynczym szablonem:

template <typename T>

auto main() -> int {
    auto const ints    = std::vector<int>{1, 2, 3};
    auto const strings = std::vector<std::string>{"one", "two", "three"};
    auto const doubles = std::vector<double>{3.14, 2.71, 1.61};

    print(ints);
    print(strings);
    print(doubles);
}

Omówmy teraz dokładnie elementy widoczne w implementacji szablonu print():

Na pierwszym miejscu widzimy linijkę template <typename T>. Linijka ta informuje, że pojedynczy element niżej będzie szablonem. Gdy tuż pod taką linijką napiszemy auto print(std::vector<T>& vec) -> void { ... }, to kompilator wie, że print() jest szablonem. Szablonem, który wprowadza nazwę T (bo napisaliśmy <typename T>).

T jest tak zwanym parametrem szablonu. Można o nim myśleć jako o swojego rodzaju zamienniku (ang. placeholder), który zostanie dopasowany do typu, który akurat jest potrzebny.

Przykładowo, gdy wywołujemy print(ints), to kompilator szuka pasującej nazwy print, którą można wywołać jak funkcję przekazując obiekt ints. Nie znajdzie jej, więc zacznie szukać, czy przypadkiem jakiś szablon nie może zostać dopasowany tak, aby to wywołanie się powiodło.

Tu przychodzi nasz szablon print(). Kompilator patrzy, czy argument pasuje do parametru. Argumentem jest std::vector<int>, a parametrem jest std::vector<T>. Na szczęście T to parametr szablonowy, pod który można próbować dopasować dowolny typ. Kompilator podmienia T na int, co sprawia, że argument pasuje do parametru. Tak dopasowany szablon generuje nam implementację, która jest wywoływana.

Szablony generują kod.

Szablon funkcji to nie jest funkcja. Gdy kompilator potrzebuje skorzystać z szablonu i dopasowanie parametrów się powiedzie, wygeneruje on odpowiednią implementację z zastąpionymi parametrami.

Cała sytuacja się powtarza, gdy kompilator widzi print(strings). Szuka on nazwy print, którą można wywołać jak funkcję, która przyjmie argument strings. Nie ma takiej. Zatem szuka teraz szablonu. Znajdzie nasz print() i spróbuje pod T dopasować std::string. Uda się to (bo czemu miałoby się nie udać — później zobaczymy, kiedy taka sytuacja może się nie udać), więc zostanie wygenerowana implementacja, która ma identyczny kod jak nasz szablon, ale zamiast T zostanie podstawiony typ std::string.

Analogiczna sytuacja występuje w przypadku wywołania print(doubles).

Ciekawa sytuacja ma miejsce, gdybyśmy wywołali print(ints) (albo dowolny inny print() z typem, którego szablon już raz został wygenerowany). Przypomnijmy sobie, że wcześniej dowiedzieliśmy się, że kompilator wpierw szuka jakiejś nazwy (np. funkcji), którą można wywołać jak funkcję z danym argumentem. Wyobraźmy sobie, że main() wygląda następująco:

auto main() -> int {
    auto const ints = std::vector<int>{1, 2, 3};

    print(ints);
    print(ints);

Wiemy już, co się dzieje, gdy kompilator dotrze do pierwszego print(). Poszuka pasującej nazwy (funkcji, lambdy, obiektu funkcyjnego, tak naprawdę czegokolwiek, co da się wywołać jak funkcję, która przyjmie ints). Nie znajdzie. Znajdzie za to nasz szablon. Podstawi T = int, a następnie wygeneruje implementację funkcji, która zachowa się tak, jak kod w naszym szablonie.

Ciekawa sytuacja, która została przed chwilą wspomniana, ma miejsce przy drugim print(ints). Dlaczego? Dlatego, że kompilator przed chwilą wygenerował odpowiednią implementację. Oznacza to, że nie musi robić tego drugi raz. Skorzysta z przed chwilą wygenerowanej implementacji.

Szablony z wieloma parametrami szablonowymi

Obecność <typename T> wprowadza nam placeholder na typ. Nie jest on jednak wyłącznie jednokrotnego użytku. Nic nie stoi na przeszkodzie, aby przyjąć więcej parametrów tego “typu”:

#include <iostream>
#include <vector>

template <typename T>
auto printBigger(
        std::vector<T> const& first, std::vector<T> const& second
) -> void {
    auto const& bigger = first.size() > second.size() ? first : second;

    for (auto const& element : bigger) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

auto main() -> int {
    auto const ints1 = std::vector<int>{1};
    auto const ints2 = std::vector<int>{1, 2};
    auto const ints3 = std::vector<int>{1, 2, 3};

    printBigger(ints1, ints2);
    printBigger(ints2, ints3);
}

Jak widać, w szablonie printBigger() użyliśmy T dwa razy. Szablon ten wyświetli zawartość dłuższego z przekazanych przez argument wektorów.

W tym momencie można sobie zadać pytanie, czy użycie std::vector jest konieczne przy używaniu szablonów. Nie jest. Przykład z ich użyciem został wybrany w celu zaprezentowania prostego, acz praktycznego problemu.

    printBigger(y, z);

Błąd, o ile wyjątkowo wymowny, mówi dosyć wprost o tym, jaki jest problem — printBigger() wymaga, aby obydwa argumenty były tego samego typu. To dlatego, że w obydwu przypadkach zastosowaliśmy ten sam placeholder T. My jednak przekazaliśmy jako argumenty int i double. Ewidentnie nie da się dopasować T tak, żeby na raz był intem oraz doublem. W takim wypadku kompilator protestuje.

Jak jednak naprawić ten błąd? Przecież nic nie stoi na przeszkodzie porównać int z double. Następujący kod się przecież poprawnie kompiluje:

    auto const x = int(10);
    auto const y = double(10.5);

    if (x < y) return 0;
    else return 1;

Rozwiązanie brzmi dosyć logicznie — mamy dwa różne typy, to wprowadzamy dwa różne placeholdery.
