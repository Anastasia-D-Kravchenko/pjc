Wyjątki

W kwestii wyjątków w C++ jest dobra i zła wiadomość:

Dobra wiadomość jest taka, że używanie ich w “klasyczny i poprawny sposób” jest jeszcze prostsze niż korzystanie z wyjątków w Javie.

Zła wiadomość jest taka, że tak naprawdę są dużo bardziej skomplikowane — zwłaszcza w kwestii szczegółów.

Na szczęście w 99% przypadków możemy kompletnie zignorować te szczegóły. Przyjrzyjmy się zatem najprostszemu przykładowi użycia wyjątków w C++:

#include <exception>    // std::exception

#include <fmt/base.h>

auto main() -> int {
    try {
        fmt::println("before `throw`");

        throw std::exception();

        fmt::println("after `throw`");
    } catch (std::exception const& ex) {
        fmt::println("Exception! Message: {}", ex.what());
    }
}

1
2

before `throw`
Exception! Message: std::exception

Wszystko wygląda znajomo — jest try, jest throw jest catch, a kod po throw się nie wykonuje. Nie ma .printStackTrace() ani .getMessage(), ale ta druga metoda jest zastąpiona metodą .what(), która — jak sama nazwa wskazuje — zwraca informację o tym, co się stało. Wszystko jasne!

I takie właśnie są realia — nie ma jakiś ukrytych problemów z klasycznym używaniem wyjątków, a to właśnie w taki klasyczny sposób powinniśmy ich używać. Oczywiście dowiemy się później, co oznacza nieklasyczne korzystanie z wyjątków, ale to potem. Teraz spójrzmy na kilka większych przykładów, które odświeżą i utrwalą naszą wiedzę o wyjątkach.

Własne wiadomości

Na pierwszy ogień idzie tworzenie wyjątku z własną wiadomością. W takim przypadku należy skorzystać z std::logic_error, które bezpośrednio dziedziczy po std::exception. To dlatego, że std::exception jest na tyle “bazowym” typem, że nawet nie ma konstruktora akceptującego jakikolwiek tekst!

#include <exception>    // std::exception
#include <stdexcept>    // std::logic_error

#include <fmt/base.h>

auto main() -> int {
    try {
        fmt::println("before `throw`");

        throw std::logic_error(
            "You can catch exceptions in a polymorphic manner"
        );

        fmt::println("after `throw`");
    } catch (std::exception const& ex) {
        fmt::println("Exception! Message: {}", ex.what());
    }
}

2

before `throw`
Exception! Message: You can catch exceptions in a polymorphic manner

Jak sam przykład wskazuje, gdy podnosimy wyjątek typu T, to możemy użyć typu U do złapania go, o ile U jest klasą bazową dla T. Czyli — mówiąc w skrócie:

Wyjątki można łapać polimorficznie.

Warto też zwrócić uwagę, że łapiemy wyjątki poprzez stałą referencję (const&). Nie ma powodu, aby kopiować wyjątki przy ich łapaniu.

Wychodzenie z dowolnie zagnieżdżonego stosu wywołań

Gdy funkcja wywołuje funkcję, a tamta z kolei wywołuje kolejną, gdzie tamta kolejna wywołuje jeszcze jedną (itd.), mówimy o stosie wywołań funkcji. Co to ma do wyjątków? Otóż:

Wyjątki pozwalają na wychodzenie z dowolnie zagnieżdżonego stosu wywołań.

#include <exception>
#include <stdexcept>

#include <fmt/base.h>

auto thisFunctionThrows() -> void {
    fmt::println("we will throw");
    throw std::logic_error("From nested call stack");
    fmt::println("we threw");
}

auto delegate() -> void {
    fmt::println("delegate begin");
    thisFunctionThrows();
    fmt::println("delegate end");
}

auto call() -> void {
    fmt::println("call begin");
    delegate();
    fmt::println("call end");
}

auto main() -> int {
    try {
        fmt::println("before `throw`");

        call();

        fmt::println("after `throw`");
    } catch (std::exception const& ex) {
        fmt::println("Exception! Message: {}", ex.what());
    }
}

Można sobie uprościć, mówiąc, że gdy podnosimy wyjątek, to “szuka” on najbliższego catcha.

Warto na spokojnie przeanalizować sobie powyższy kod, a najlepiej byłoby przejść po nim debuggerem. Wtedy można bardzo łatwo zobaczyć, jak wygląda proces “wychodzenia” z zagnieżdżonego stosu wywołania.

Wyjątki a poprawna obsługa zasobów

Szalenie ważnym elementem pracy z wyjątkami jest pewność, że zasoby, z których korzysta aplikacja, są poprawnie obsługiwane nawet w przypadku pojawienia się wyjątków.

#include <exception>
#include <stdexcept>

#include <fmt/base.h>

struct Foo {
    int id;

    Foo(int id) : id(id) { fmt::println("created {}", id); }
    ~Foo() { fmt::println("destroyed {}", id); }
};

auto thisFunctionThrows() -> void {
    auto foo = Foo(3);
    throw std::logic_error("From nested call stack");
    fmt::println("we threw");
}

auto delegate() -> void {
    auto foo = Foo(2);
    thisFunctionThrows();
    fmt::println("delegate end");
}

auto call() -> void {
    auto foo = Foo(1);
    delegate();
    fmt::println("call end");
}

auto main() -> int {
    try {
        auto foo = Foo(0);

        call();

        fmt::println("after `throw`");
    } catch (std::exception const& ex) {
        fmt::println("Exception! Message: {}", ex.what());
    }
}

Jak można zauważyć, destruktory obiektów są poprawnie wywoływane, nawet jeśli stworzone obiekty są głęboko w stosie wywołania. Oznacza to, że wyjątki nie przeszkadzają nam w dowolnym korzystaniu z wygodnych narzędzi takich jak std::vector czy std::fstream! A to oczywiście dlatego, że klasy te dostarczają odpowiednio napisane destruktory.

#include <exception>
#include <stdexcept>

#include <fmt/base.h>

struct Foo {
    int id;

    Foo(int id) : id(id) { fmt::println("created {}", id); }
    ~Foo() { fmt::println("destroyed {}", id); }
};

auto thisFunctionThrows() -> void {
    auto foo = new Foo(3);
    throw std::logic_error("From nested call stack");
    fmt::println("we threw");
}

auto delegate() -> void {
    auto foo = new Foo(2);

    fmt::println("delegate end");
}

auto call() -> void {
    auto foo = new Foo(1);
    delegate();
    fmt::println("call end");
}

auto main() -> int {
    try {
        auto foo = new Foo(0);

        call();

}

No to jest przecież oczywiste, że nie ma żadnego destroy N, ponieważ nigdzie nie ma delete.
To prawda, tylko problem w tym, że teraz trzeba odpowiedzieć sobie na trudne pytanie — gdzie te delete umieszczać?

Oraz nie wiedząc, że delegate() może rzucić wyjątkiem (a może czasami nie rzuca?), raczej umieścilibyśmy delete foo na końcu funkcji, czyli tak:

auto call() -> void {
    auto foo = new Foo(1);
    delegate();
    fmt::println("call end");
    delete foo;
}

To oczywiście nie zadziała, ponieważ z delegate() “ucieknie” wyjątek i “wyjdzie” z call(), przez co delete foo się nigdy nie wywoła.
Co robić?
Wziąć pod uwagę fakt, że jedną z najważniejszych cech destruktorów, czyli:
Destruktor obiektu o automatycznym czasie życia wykona się w momencie wychodzenia z bloku, w którym dany obiekt został stworzony.
Nieważne, czy wyszliśmy z bloku poprzez natrafienie na zamykającą go klamrę, czy poprzez return, czy poprzez throw.

auto thisFunctionThrows() -> void {
    auto foo = std::make_unique<Foo>(3);
    throw std::logic_error("From nested call stack");

    thisFunctionThrows();
    fmt::println("delegate end");
}

auto call() -> void {
    auto foo = std::make_unique<Foo>(1);
    delegate();
    fmt::println("call end");
}

auto main() -> int {
    try {
        auto foo = std::make_unique<Foo>(0);

        call();

        fmt::println("after `throw`");

    }
}
