Rozdział 8.1 - Pola i metody statyczne

Opublikowano Apr 24, 2025
Autor Filip Kwiatkowski
4 min czytania

Słowo kluczowe static

Statyczne pola i metody są bardzo ważną częścią większości języków obiektowych. Reprezentują abstrakcję danych oraz funkcjonalności, które kontekstowo należą do jakiejś klasy, choć nie są zależne od jej obiektów.

W języku C++ słowo kluczowe static, gdy umieści się je przed polem lub metodą klasy, zamienia dany byt w element statyczny. Dostęp do takiego elementu odbywa się przy pomocy nazwy klasy oraz operatora :: (a nie . jak w Javie).

Przykładowo, tworząc statyczną metodę bar() klasy Foo, wywołamy ją przy pomocy składni Foo::bar():

1
2
3
4
5
6
7

struct Foo {
    static auto bar() -> void { }
};

auto main() -> int {
    Foo::bar();
}

Statyczne metody nie mogą być const (ale mogą przyjmować const argumenty), bo nie są wywoływane na żadnym obiekcie.

Jak widać, statyczne metody działają praktycznie tak samo, jak w pozostałych, popularnych językach. Jednak w przypadku statycznych pól (zmiennych), sytuacja jest nieco bardziej skomplikowana. To dlatego, że “trywialny” sposób ich użycia niestety nie zadziała:

1
2
3

struct Foo {
    static int value = 0;
};

1
2
3

main.cpp:2:16: error: ISO C++ forbids in-class initialization of non-const static member 'Foo::value'
    2 |     static int value = 0;
      |                ^~~~~

Powody ku temu zachowaniu są dosyć zawiłe, choć można je częściowo podsumować w następujący sposób: Statyczne zmienne w klasach są efektywnie globalnymi zmiennymi, które istnieją niezależnie od tego, czy powstał jakikolwiek obiekt klasy. Najczęściej definicja klasy pojawia się w pliku nagłówkowym, który potem (potencjalnie wiele razy) #include‘ujemy. Taka definicja klasy jest pełna deklaracji (np. metod), które później są definiowane w osobnym pliku .cpp (czyli zaimplementowane raz — bez duplikatów).

Gdyby zezwolić na składnię static int value = 0;, to taka instrukcja byłaby również definicją. Gdyby klasa została zdefiniowana w wielu plikach .cpp (przez #include), to powtórzylibyśmy definicję pola value. Redefiniowanie nie jest legalną operacją w C++.

No ale chwila, skoro redefiniowanie nie jest legalne, to dlaczego możemy mieć wiele definicji klas? Przecież skoro struct Foo { ... }; to definicja, a właśnie to zawsze robiliśmy w klasach umieszczanych w plikach nagłówkowych, które potem potencjalnie wiele razy dołączaliśmy do różnych plików .cpp, to czy efektywnie nie mieliśmy do czynienia z redefinicją klas?

Bardzo dobra uwaga. Jeżeli ktoś nie zauważył intuicyjnie tej nieścisłości, to warto ją przeczytać jeszcze raz.

Odpowiedź jest bardzo krótka — bo definicje klas są domyślnie oznaczone jako inline1.

Specyfikator inline

Specyfikator inline służy do specjalnego oznaczania konstrukcji takich jak funkcja czy zmienna. Tak oznaczony element może być zdefiniowany wiele razy w wielu jednostkach translacji (w uproszczeniu — skompilowanych plikach .cpp, które potem będą linkowane wraz z innymi w celu stworzenia jednej aplikacji).

Załóżmy prosty przykład, gdzie nie chce nam się definiować funkcji w pliku .cpp po zadeklarowaniu jej w pliku .hpp. Chcemy ją zdefiniować od razu w pliku nagłówkowym. Może to powodować problem, gdy spróbujemy dołączyć taki plik do kilku plików .cpp:

1
2
3
4
5

#pragma once

auto theAnswer() -> int {
    return 42;
}

1
2
3

#include "functions.hpp"

auto main() -> int { }

1

#include "functions.hpp"

Oczywiście budujemy aplikację, bazując na tych dwóch plikach implementacyjnych, czyli robimy add_executable(PJC main.cpp impl.cpp).

Taka aplikacja się skompiluje, ale nie zlinkuje. Błąd linkera może wyglądać następująco:

1

impl.cpp:3: multiple definition of `theAnswer()'; CMakeFiles/PJC.dir/main.cpp.obj:main.cpp:3: first defined here

Jak widać, błąd mówi o tym, że w pliku źródłowym impl.cpp mamy duplikację definicji funkcji theAnswer(), która już wcześniej była widziana w pliku main.cpp.

Metoda na naprawę tego błędu wydaje się bardzo prosta — zwyczajnie nie definiować tej funkcji w pliku nagłówkowym, tylko dorobić odpowiedni plik .cpp, w którym umieścimy jej definicję, zostawiając w pliku nagłówkowym wyłącznie deklarację.

Co ciekawe, to w zdecydowanej większości przypadków właśnie tak powinniśmy robić. Implementacja w pliku nagłówkowym powinna być wyjątkiem, a nie regułą. Do wyjątków należą:

  • Definicje klas — zwykle pełne deklaracji metod;
  • Definicje szablonów;
  • Implementacje bibliotek, które chcą umożliwić dołączanie ich za pomocą wyłącznie ściągnięcia i dołączenia pliku lub plików nagłówkowych;
  • I inne, pomniejsze przypadki.

Pola static inline

Wracając do oryginalnego problemu, gdzie spróbowaliśmy zadeklarować statyczne pole typu int:

1
2
3

struct Foo {
    static int value = 0;
};

Istnieją dwa sposoby, aby naprawić błąd procesu budowania:

  1. Dodać specyfikator inline, czyli zamienić static int value = 0; na static inline int value = 0;.
  2. Usunąć inicjalizację, czyli zamienić static int value = 0; na static int value; oraz dodać definicję pola value w osobnym (tylko jednym) pliku implementacyjnym przy pomocy składni int Foo::value = 0;.

Ewidentnie widać, że pierwsza opcja jest prostsza. Nie zawsze była ona dostępna (wprowadzono ją w C++17), ale jeśli możemy z niej skorzystać, to warto to zrobić.

  1. To niestety nie do końca prawda. Efektywnie można tak sobie to upraszczać, ale prawda jest bardziej złożona — dotyczy ona dokładnej definicji zasady ODR, która mówi, że po prostu ta zasada działa inaczej dla typów zdefiniowanych przez użytkownika. ↩
