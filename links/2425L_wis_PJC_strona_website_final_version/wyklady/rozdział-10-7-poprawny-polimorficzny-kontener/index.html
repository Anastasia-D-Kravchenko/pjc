Wektor wskaźników do klasy bazowej

#include <algorithm>    
#include <random>       
#include <vector>

#include <fmt/base.h>

struct Animal {
    virtual auto makeSound() const -> void { }
};

struct Cat : Animal {
    auto makeSound() const -> void override {
        fmt::println("Meow");
    }
};

struct Dog : Animal {
    auto makeSound() const -> void override {
        fmt::println("Woof");
    }
};

auto main() -> int {
    auto animals = std::vector<Animal>();

    for (auto i = 0; i < 5; i++) animals.push_back(Cat());
    for (auto i = 0; i < 5; i++) animals.push_back(Dog());

    std::ranges::shuffle(animals, std::random_device());

    for (auto const& animal : animals) {
        animal.makeSound();
    }
}

Niestety, przez object slicing ten kod nie przechowywał obiektów typu Cat czy Dog w wektorze animals. Przechowywał “surowe” zwierzęta, przez co wywołanie .makeSound() efektywnie nic nie robiło.

Object slicing było problemem, który rozwiązywaliśmy poprzez unikanie tworzenia kopii. Osiągaliśmy to przy pomocy referencji. Teraz jednak wiemy, że zarówno referencje, jak i wskaźniki potrafią pracować na oryginałach obiektów (pomagają nam unikać kopiowania). Skoro nie można mieć wektora referencji, to skorzystajmy ze wskaźników. Uprośćmy przy okazji troszkę tworzenie i dodawanie elementów do wektora:

auto main() -> int {
    auto animals = std::vector<Animal*>();  // vector of pointers
    auto c1 = Cat();
    auto c2 = Cat();
    auto d1 = Dog();
    auto d2 = Dog();
    
    animals.push_back(&c1);
    animals.push_back(&c2);
    animals.push_back(&d1);
    animals.push_back(&d2);
}

Jak widać, nie korzystamy już z std::vector<Animal>, tylko z std::vector<Animal*> (Animal vs Animal*). Dodajemy do wektora nie same zwierzęta, a wskaźniki do nich (otrzymane dzięki zaaplikowaniu operatora &, który zwraca nam adresy pamięci do obiektów, czyli wskaźniki do nich).

Od razu rzuca się nam w oczy użycie operatora ->. Czemu nie ma tam kropki (.)?

Dlatego, że gdybyśmy zamiast ptr->makeSound() użyli ptr.makeSound(), to spotkalibyśmy się z następującym błędem: request for member 'makeSound' in 'ptr', which is of pointer type 'Animal* const' (maybe you meant to use '->' ?).

W C++, gdy chcemy dostać się do metody lub pola jakiegoś złożonego obiektu, używamy operatora kropki (.). Wyjątkiem jest sytuacja, gdy mamy do czynienia ze wskaźnikiem. Wtedy zamiast kropki używamy strzałki (->). Jest to pozostałość z języka C.

W ten sposób udało nam się stworzyć poprawnie działający polimorficzny kontener!

Trudność w zarządzaniu cyklem życia obiektów

Niestety to, że przykład wyżej jest poprawny, nie oznacza, że na pewno czegoś nie zepsujemy. Nie dość, że używanie wskaźników wymaga opanowania skomplikowanej składni, to jeszcze wymaga pilnowania poprawności działania naszych programów z wielu perspektyw. Trzeba:

  • pilnować, żeby wskaźniki, na których wykonujemy delete / delete[] zawsze wskazywały na “swoje własne” dane (takie, którymi nikt inny nie będzie zarządzać, czyli wywoływać swoich delete / delete[]) — czyli pamięć o problemie płytkich kopii (ang. shallow copy);
  • pamiętać, że mogą wskazywać na nic (nullptr);
  • pamiętać, że wskaźnik nie przedłuża czasu życia obiektu.

Ten ostatni punkt jest dosyć ciekawy. Spójrzmy na przykład, który jest poniekąd odwrotnością wycieku pamięci. Na początek stwórzmy funkcję getIntPointer():

Bardzo łatwo jest pominąć ogromny problem, który ten kod przejawia — mamy tutaj UB, ponieważ próbujemy dostać się do nieistniejącego obiektu!

Jak to?

Zwróćmy uwagę na to, że localInt jest zmienną lokalną o automatycznym czasie życia. Oznacza to, że wychodząc z bloku, w którym została stworzona, przestanie ona istnieć. Zwracanie wskaźnika do zmiennej lokalnej jest błędem, ponieważ będziemy operować na adresie obiektu, który został zniszczony.

Uruchomienie powyższego kodu może zrobić cokolwiek. Tak to bywa przy Zachowaniu Niezdefiniowanym. Może się wyświetlić 1337, może się wyświetlić 0, może się nic nie wyświetlić, albo program może scrashować.

Po co jednak o tym mówimy? Ano po to, że o ile takie zwracanie wektora nie stanowi żadnego problemu:

auto getVector() -> std::vector<int*> {
    auto local1 = 1;
    auto local2 = 2;
    auto local3 = 3;

    auto vec = std::vector<int*>{&local1, &local2, &local3};
    return vec;
}

Wektor dba o cykl życia elementów, które przechowuje. Gdy przechowuje inty, to odpowiednio je “do siebie” kopiuje. Natomiast gdy przechowuje wskaźniki, to tymi obiektami, o które “dba”, są same wskaźniki, a nie obiekty, na które one wskazują. W tym drugim przykładzie wszystkie localne zmienne giną wraz z zakończeniem polecenia return. Te trzy wskaźniki, które przechowuje zwracany wektor, będą nie do użytku.

Jest to spory problem, ponieważ — jak się może wydawać — sprawia to, że nie możemy tworzyć metod-fabryk dla polimorficznych kontenerów:

auto makeAnimalsVector() -> std::vector<Animal*> {
    auto animals = std::vector<Animal*>();

    auto c = Cat();
    auto d = Dog();

    animals.push_back(&c);
    animals.push_back(&d);

    return animals;
}

W tym przykładzie zwracany wektor zawiera wskaźniki do nieistniejącego już kota i psa. To ogromny problem. Czy da się mu zaradzić?

Da się. Wystarczy skorzystać z czegoś, co już poznaliśmy. Wystarczy sprawić, aby wyjście z funkcji, która tworzy te dwa obiekty, nie skutkowało ich usunięciem. Wystarczy sprawić, żeby ten kot i pies nie były obiektami o automatycznym czasie życia, tylko obiektami o dynamicznym czasie życia. Należy skorzystać z dynamicznej alokacji pamięci:

auto makeAnimalsVector() -> std::vector<Animal*> {
    auto animals = std::vector<Animal*>();

    auto c = new Cat(); // new!
    auto d = new Dog(); // new!

    animals.push_back(c); // no &
    animals.push_back(d); // no &

    return animals;
}

Wszystko wygląda świetnie!

Ale chwila… Używamy new, a gdzie jest delete..?

…Słuszna uwaga.

Cat i Dog zostały stworzone przy pomocy new, a więc gdzieś należałoby użyć delete. Mylnym byłoby zakładać, że wektor sam “posprząta” te obiekty. On faktycznie korzysta z dynamicznej alokacji pamięci (tak, jak nasz pjc::Vector), ale jego interesuje tylko jego własny wskaźnik na tablicę elementów. Te elementy — w naszym przypadku — są wskaźnikami. Wektor po prostu wykona delete[] na tej swojej tablicy wskaźników. Nie wykona delete na każdym z nich. Aby uniknąć wycieku pamięci, należałoby zapisać wektor i wykonać delete na jego elementach:

Jest to… niesamowicie niewygodne. Czy nie ma jakiegoś sposobu, żeby to troszkę uprościć?

Jest. Należy skorzystać z inteligentnych wskaźników (ang. smart pointers), o których będzie w następnym rozdziale.

Bardzo ciężko jest zauważyć ten problem, ale… mamy w tym przykładzie kodu UB.

Dlaczego?

Ponieważ stworzone obiekty typu Cat i Dog nie są poprawnie niszczone. I to nie do końca jest wina delete. Aby zobrazować ten problem, dodajmy do naszej hierarchii klas destruktory informujące nas o tym, że dany obiekt jest niszczony:

Jak wiemy, kolejność wywoływania destruktorów w ramach tego samego bloku jest odwrotna do kolejności wykonania konstruktorów. Wpierw stworzyliśmy a, które jest typu Animal. Działanie jego destruktora możemy zaobserwować w linijce nr 5 outputu. Następnie stworzyliśmy c, które jest typu Cat. Jego destruktor wyświetlił to, co zaobserwowaliśmy w linijkach 3-4. Na koniec stworzyliśmy d, czyli Dog. Jego zniszczenie zostało wywołane jako pierwsze — widzimy to w pierwszych dwóch linijkach outputu.

Destruktor klasy dziedziczącej, pod koniec swojego działania, wywołuje destruktor klasy bazowej. Jest to odwrotna sytuacja do tej, którą możemy zaobserwować przy konstruktorach. Konstruktor klasy dziedziczącej najpierw wywoła konstruktor klasy bazowej.

No i mamy problem. Mamy do czynienia z Cat i Dog, ale ich destruktor się nie wywołał. Wywołał się tylko destruktor z ich klasy bazowej.

Jesteśmy w stanie wydedukować powód, dlaczego tak się stało. Podpowiem, że chodzi o to, że mamy wskaźnik do klasy bazowej i na nim wywołujemy delete, który wywoła destruktory.

Już kiedyś spotkaliśmy się z sytuacją, gdy mając dostęp do obiektu dziedziczącego przy pomocy zmiennej typu bazowego (wtedy referencji), wywoływaliśmy nadpisaną metodę, ale wywoływała się wyłącznie wersja z klasy bazowej. Object slicing nie jest tutaj problemem. Jest nim brak wirtualnej metody!
