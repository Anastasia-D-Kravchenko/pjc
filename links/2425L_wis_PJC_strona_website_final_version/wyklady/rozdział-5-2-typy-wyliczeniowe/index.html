Typy wyliczeniowe

Zdarza się, że czasem chcemy reprezentować bardziej restrykcyjny zakres danych, a czasem mniej restrykcyjny zakres danych. Czasem chcemy użyć long long w celu przechowywania potencjalnie ogromnych liczb, a czasem chcemy użyć char, żeby mieć pewność, że będziemy korzystać wyłącznie z jednobajtowych zmiennych.

Problem pojawia się wtedy, gdy nasz docelowy zakres danych nie jest równy żadnemu wbudowanemu. Jak zaznaczyć w systemie typów, że chcemy, aby jakiś obiekt przechowywał wyłącznie liczby od 0 do 5? A może chcemy przechowywać wartości między 1 a 3? Może 1, 2, 4 i 5, ale już nie 3? A może chcemy przechowywać jakieś nazwane wartości, np. kierunki typu north, east, south i west, ale żadne inne.

Oczywiście możemy w takich przypadkach skorzystać z wbudowanych typów jak np. int czy std::string i przy każdej modyfikacji walidować poprawność przechowywanych danych.

Alternatywnie, możemy też spróbować stworzyć własną klasę, która będzie opakowywała takiego inta lub std::stringa udostępniając publiczne metody, które będą automatycznie wykonywały taką walidację.

Albo — najprościej — możemy użyć typu wyliczeniowego. W Javie był to enum, a w C++ jest to enum class.

W C++ dostępny też jest “surowy” enum. Nie należy jednak go używać — jest to mniej bezpieczna wersja tego narzędzia. Należy zawsze używać enum class.

Definiowanie i używanie typów wyliczeniowych

Aby stworzyć własny typ wyliczeniowy, wystarczy użyć odpowiednich słów kluczowych i w klamrach zdefiniować legalne wartości:

Typy wyliczeniowe zamiast argumentów logicznych

Enumeracje pozwalają też zastąpić wiele miejsc, gdzie argument typu bool byłby nieintuicyjny w użyciu. Przykładowo, załóżmy, że tworzymy funkcję equalContents, która ma zwrócić true gdy obydwa przekazane przez argument wektory mają taką samą zawartość:

1
2
3
4
5
6

template <typename T>
auto equalContents(
        std::vector<T> const& left, std::vector<T> const& right
) -> bool {
    return left == right;
}

Wszystko dobrze, dopóki ktoś nie powie: “Ale w sumie wektor 1 2 3 ma identyczną zawartość jak 3 2 1, tylko że w innej kolejności”.

Zgadza się. Możemy oczywiście to zignorować lub dodać funkcję equalContentsIgnoreOrder(), ale z drugiej strony możemy dodać do stworzonej funkcji argument, który będzie odpowiadał za wybór chęci (lub jej braku) pilnowania kolejności elementów:

1
2
3

template <typename T>
auto equalContents(
        std::vector<T> const& left, std::vector<T> const& right,
        bool const orderingRequired
) -> bool {
    if (orderingRequired) return left == right;
    else return std::ranges::is_permutation(left, right);
}

Funkcja wygląda znowu dobrze — możemy ją wywołać z argumentem true, gdy chcemy wymagać identycznej kolejności elementów lub z argumentem false, gdy nie interesuje nas pozycja elementów.

std::ranges::is_permutation() sprawdza, czy obydwa zakresy zawierają identyczne elementy, które mogą być ułożone w innej kolejności.

Mimo wszystko nie sposób nie zauważyć, że jeżeli nie zna się nazwy trzeciego parametru funkcji equalContents(), to nie za bardzo wiadomo, jak ją wywołać. Bo co oznacza equalContents(vec1, vec2, true)? Co oznacza to true? Z jednej strony jest to oczywiste — orderingRequired to dobra nazwa, która jasno wskazuje, że przekazanie true wymaga zachowania kolejności.

Problem w tym, że równie dobrą nazwą byłoby ignoreOrdering. W takim przypadku przekazanie wartości true oznaczałoby coś zupełnie odwrotnego.

O ile w dzisiejszych czasach można w łatwy sposób podejrzeć nazwy parametrów dzięki potężnym środowiskom programistycznym (IDE), to jednak warto pójść krok dalej i ułatwić pracę osobom czytającym nasz kod w przyszłości — warto rozważyć zastosowanie typu wyliczeniowego.

Pomysł polega na tym, że stworzymy typ Ordering, który będzie miał jedynie dwie możliwe wartości — Required oraz NotRequired. Następnie na jego podstawie będziemy albo delegować porównywanie do operatora == lub do std::ranges::is_permutation. Cały kod z przykładem wygląda następująco:

#include <algorithm>
#include <vector>

#include <fmt/base.h>

enum class Ordering {
    Required, NotRequired
};

template <typename T>
auto equalContents(
        std::vector<T> const& left, std::vector<T> const& right,
        Ordering const ordering
) -> bool {
    if (ordering == Ordering::Required) return left == right;
    else return std::ranges::is_permutation(left, right);
}

auto main() -> int {
    auto v1 = std::vector<int>{1, 2, 3};
    auto v2 = std::vector<int>{3, 2, 1};

    fmt::println(
            "{} {}",
            equalContents(v1, v2, Ordering::Required),
            equalContents(v1, v2, Ordering::NotRequired)
    );
}

Być może wydaje się to mało znaczące, ale gdy czytamy dziesiątki tysięcy linijek kodu dziennie podczas pracy przy kodzie, taki — jak się może wydawać — nadmierny nacisk na oczywistość jest pewnym wyznacznikiem kodu wysokiej jakości.

Warto zauważyć, że nasz typ Ordering efektywnie potrafi zrobić tyle samo, co bool. Ma wyłącznie dwie legalne wartości. Ale to właśnie nadanie mu bardziej znaczącej i precyzyjnej nazwy oraz wymuszenie bycia “bardziej oczywistym” w wywoływaniu funkcji equalContents() sprawia, że taki kod się wygodniej czyta.

  1. Prezentowany sposób inicjalizuje zmienną currentDirection wartością Direction::North. To dlatego, że przy takiej inicjalizacji próbujemy zamienić wartość 0 na Direction. Wartość 0 wzięła się z tego, że gdy tworzymy tak zwany direct-initialized wartość liczbową (np. pisząc int() czy char()), to tworzony jest obiekt z wartością 0. Enumeracje (typy wyliczeniowe) w C++ są nakładką na jakiś typ liczbowy działający “w tle”. Gdy nie sprecyzujemy żadnej wartości liczbowej legalnym wartościom wyliczeniowym, pierwsza będzie miała wartość 0, druga 1, trzecia 2, itp. ↩
