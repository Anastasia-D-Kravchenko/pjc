Pliki binarne a tekstowe

Plików tekstowych używamy, gdy chcemy zapisać dane, które mogą być potem odczytywane lub zmieniane przez użytkownika przy pomocy edytorów tekstowych (jak np. Notepad). Plików binarnych używamy wtedy, gdy chcemy zapisać dane z programu bez późniejszej potrzeby interpretowania ich jako tekst. Spójrzmy zatem najpierw na przykład, w którym osiągniemy ten sam efekt przy użyciu zarówno tekstowych, jak i binarnych plików:

Zapisywanie pojedynczego inta do pliku tekstowego

#include <fstream>

#include <fmt/base.h>
#include <fmt/ostream.h>

auto main() -> int {
    auto someInt = 1337;

    {
        auto file = std::fstream("data.txt", std::ios::out);
        fmt::println(file, "{}", someInt);
    }

    someInt = 0;    // resetting the value

    {
        auto file = std::fstream("data.txt", std::ios::in);
        file >> someInt;
    }

    fmt::println("{}", someInt);
}

Użyto tutaj wewnętrznych bloków ({ … }), które — dzięki destruktorom klasy std::fstream — w odpowiednim momencie zamkną połączenie z plikiem.

#include <fstream>

#include <fmt/base.h>

auto main() -> int {
    auto someInt = 1337;

    {
        auto file = std::fstream(
            "data.bin", std::ios::out | std::ios::binary
        );
        file.write(reinterpret_cast<char const*>(&someInt), sizeof(int));
    }

    someInt = 0;    // resetting the value

    {
        auto file = std::fstream(
            "data.bin", std::ios::in | std::ios::binary
        );
        file.read(reinterpret_cast<char*>(&someInt), sizeof(int));
    }

    fmt::println("{}", someInt);
}

Jak widać, obydwa fragmenty kodu mają taką samą strukturę — tworzymy std::fstream, zapisujemy dane do pliku, zamykamy połączenie z nim, a na koniec tworzymy drugi std::fstream, którym odczytujemy dane z pliku.

Ta ostatnia różnica nie ma tak naprawdę znaczenia. To tylko konwencja, że .txt oznacza tekst, a .bin oznacza dane binarne. Nic nie stoi na przeszkodzie zapisywać binarnie do .txt i tekstowo do .bin. Tylko wtedy użytkownik może chcieć otworzyć taki plik .txt w — przykładowo — notatniku. Zdziwi się, gdy zobaczy dane binarne.

Wersja tekstowa powinna być relatywnie zrozumiała. Przyjrzyjmy się nowym operacjom binarnym, a konkretnie linijkom:

  1. file.write(reinterpret_cast<char const*>(&someInt), sizeof(int))
  2. file.read(reinterpret_cast<char*>(&someInt), sizeof(int))

Metody .write() i .read() są bardzo proste, choć wcale na takie nie wyglądają. Oczekują one wskaźnika na dane i liczby bajtów, które:

  1. Zostaną zapisane do pliku.
  2. Zostaną nadpisane przez dane wczytane z pliku.

Innymi słowy:

  • file.write(reinterpret_cast<char const*>(&someInt), sizeof(int)):
    • file.write(…) — zapisz do pliku…
    • …dane zaczynające się w reinterpret_cast<char const*>(&someInt)…
    • …i skończ po zapisaniu tylu sizeof(int) bajtów.
  • file.read(reinterpret_cast<char*>(&someInt), sizeof(int)):
    • file.read(…) — wczytaj z pliku dane…
    • …i wklejaj je do (reinterpret_cast<char*>(&someInt)…
    • …ale skończ po wczytaniu i wklejeniu sizeof(int) bajtów.

Okeeeeej, ale czym na Odyna jest reinterpret_cast<char const*>(&someInt)?! I dlaczego w drugim przykładzie nie ma tam const?

To dosyć niekomfortowe pytanie, ale nie dlatego, że jest to trudne, ale dlatego, że nie sposób po wyjaśnieniu tego fragmentu nie zapytać “serio..?”

Otóż idea zapisywania i czytania danych binarnych jest relatywnie prosta — dostarczamy wskaźnik na pamięć i mówimy, ile bajtów trzeba zapisać / wczytać. Problem w tym, że &someInt to wskaźnik na int. int, jak widzieliśmy, zajmuje 4 bajty. Taki std::fstream, używając arytmetyki wskaźników na przekazanym adresie, “przechodziłby” po kolejnych intach, a nie po bajtach tego inta.

Potrzebujemy zatem dostać wskaźnik na pierwszy bajt tego inta. Rzecz w tym, że w językach C i C++ nie było typu danych podobnego do Javowego byte‘a, dlatego do tego celu wybrano jedyny typ, który miał gwarancję zajmowania jednego bajta, czyli char. Instrukcja reinterpret_cast<char const*>(&someInt) mówi, abyśmy pobrali adres w pamięci someInt (poprzez &someInt), a potem interpretowali ten adres jako wskaźnik nie na int, a na pierwszy bajt tego inta (ale trzeba użyć char). const jest tu dodane dlatego, że nie potrzebujemy w tej operacji modyfikować pamięci naszego inta. W drugim przykładzie mamy czytanie, a zatem musimy modyfikować bajty naszego inta — stąd w reinterpret_cast<char*>(&someInt) nie ma const.

Serio..?

No więc właśnie.

#include <algorithm>
#include <fstream>
#include <vector>

#include <fmt/ranges.h>

auto main() -> int {
    auto ints = std::vector<int>{2, 1, 3, 7};
    fmt::println("{}", ints);

    {
        auto file = std::fstream(
            "data.bin", std::ios::out | std::ios::binary
        );
        file.write(
            reinterpret_cast<char const*>(ints.data()),
            sizeof(int) * ints.size()
        );
    }

    std::ranges::fill(ints, 0);    // resetting the values
    fmt::println("{}", ints);

    {
        auto file = std::fstream(
            "data.bin", std::ios::in | std::ios::binary
        );
        file.read(
            reinterpret_cast<char*>(ints.data()),
            sizeof(int) * ints.size()
        );
    }

    fmt::println("{}", ints);
}

Problem z zapisywaniem nietrywialnych typów

int, bool, char, double czy nawet typy takie jak struct Point { int x; int y; } są trywialne. Obiekty tych typów można “tak po prostu” zapisać binarnie do plików. #include <string>
#include <vector>

#include <fmt/base.h>

auto main() -> int {
    auto emptyVector = std::vector<int>();
    auto smallVector = std::vector<int>{2, 1, 3, 7};
    auto bigVector   = std::vector<int>(1337, 1998); // 1337 elements

    auto emptyString = std::string();
    auto smallString = std::string("hello");
    auto bigString   = std::string(1337, '?');       // 1337 elements

    fmt::println("size of {}\t is {}", "emptyVector", sizeof(emptyVector));
    fmt::println("size of {}\t is {}", "smallVector", sizeof(smallVector));
    fmt::println("size of {}\t is {}", "bigVector", sizeof(bigVector));

    fmt::println("size of {}\t is {}", "emptyString", sizeof(emptyString));
    fmt::println("size of {}\t is {}", "smallString", sizeof(smallString));
    fmt::println("size of {}\t is {}", "bigString", sizeof(bigString));
}

Eeee… dlaczego ilość zajmowanej pamięci jest taka sama, niezależnie od tego, ile dany kontener przechowuje elementów?

To dlatego, że ten kontener nie przechowuje elementów “w środku”. std::vector i std::string alokują pamięć dynamicznie — w końcu nie wiadomo, ile jej będzie potrzebne, prawda? Oznacza to, że przechowują one wskaźnik(i) na alokowane elementy. Wskaźnik ma zawsze taką samą wielkość — niezależnie od tego, czy wskazuje na tablicę 5 czy 5000 elementów.

Oznacza to jednak, że próba zapisania jakiegoś std::vectora do pliku w taki sposób:

#include <fstream>
#include <vector>

#include <fmt/ostream.h>

auto main() -> int {
    auto data = std::vector<int>{2, 1, 3, 7};

    auto file = std::fstream(
        "data.bin", std::ios::out | std::ios::binary
    );
    file.write(reinterpret_cast<char const*>(&data), sizeof(data));
}

Nie zadziała. Zapiszemy jedynie wskaźnik(i), który(e) przechowuje obiekt data.

Aby poprawnie zapisać dane przechowywane przez wektor, należy zrobić to tak, jak zostało to zaprezentowane wyżej, czyli zapisać elementy znajdująca się pod .data() danego wektora.

Zamiast sizeof(JakiśTyp) można użyć sizeof(jakiśObiekt), jeżeli prowadzi to do prostszego i czytelniejszego kodu.

Koszt operacji tekstowych

Nie sposób nie zauważyć, że — przynajmniej dla nas — czytanie i pisanie tekstu zdaje się być prostsze od czytania i pisania surowych bajtów. Dlaczego zatem w ogóle opłaca się używać plików binarnych?

Odpowiedź jest prosta — kosztowność operacji. Komputer zapisane dane binarnie, co oznacza, że uzyskanie tekstowej reprezentacji jakiejś liczby wymaga relatywnie sporo pracy. W końcu liczba 1337 zapisana w pliku tekstowym to nic innego jak sekwencja czterech znaków.

Gdy do pliku tekstowego zapiszemy inta o wartości 0, plik ten będzie zajmował 1 bajt w pamięci. Gdy zapiszemy wartość 1337, plik będzie zajmował 4 bajty. Gdy zapiszemy wartość 2147483647, plik będzie zajmował 10 bajtów.

Ale przy zapisywaniu tych intów do pliku binarnego, plik ten będzie zawsze zajmował 4 bajty. Jest to:

  • pewniejsze;
  • szybsze;
  • mniej skomplikowane przy większych, bardziej złożonych (ale wciąż trywialnych) typów.

  1. Ten output jest przykładowy, ponieważ różne implementacje biblioteki standardowej mogą implementować std::string i std::vector w różny sposób. Jednak niezmienne jest to, że sizeof() każdego obiektu tego samego typu zwróci zawsze taką samą liczbę. Niezależnie od tego, “jak duży” jest dany std::string czy std::vector. ↩
