Przeciążanie operatorów jako metody i wolne funkcje

We wcześniejszej części rozdziału dowiedzieliśmy się (i zauważyliśmy), że operatory można przeciążać na dwa sposoby — metodą oraz wolną funkcją. Większość operatorów tak można przeciążać. Istnieją jednak pewne wyjątki.

operator= nie może być przeciążony jako wolna funkcja. Musi być zaimplementowany jako metoda. To dlatego, aby nikt “z zewnątrz” nie mógł zmienić tego, co się dzieje, gdy nadpisywane są obiekty typów stworzonych przez kogoś innego. Jak wielka tragedia mogłaby się stać, gdybyśmy nadpisali operator= dla std::string nie będąc świadomym tego, jak dużo rzeczy właśnie zepsuliśmy w implementacji {fmt}?

operator+, któremu przyjrzeliśmy się w poprzednim podrozdziale, może być przeciążony na obydwa sposoby. Weźmy pod uwagę przykład z klasą Point:

#include <string>

#include <fmt/format.h>

struct Point {
    int x;
    int y;
};

auto operator+(Point const left, Point const right) -> Point {
    return Point(left.x + right.x, left.y + right.y);
}

auto format_as(Point const p) -> std::string {
    return fmt::format("({}, {})", p.x, p.y);
}

auto main() -> int {
    auto p1 = Point(1, 2);
    auto p2 = Point(5, 8);
    fmt::println("{}", p1 + p2);
}

#include <string>

#include <fmt/format.h>

struct Point {
    int x;
    int y;

    auto operator+(Point const right) const -> Point {
        return Point(x + right.x, y + right.y);
    }
};

auto format_as(Point const p) -> std::string {
    return fmt::format("({}, {})", p.x, p.y);
}

auto main() -> int {
    auto p1 = Point(1, 2);
    auto p2 = Point(5, 7);
    fmt::println("{}", p1 + p2);
}

Efekt jest wciąż identyczny. Spójrzmy zatem na jedyną różnicę w kodzie:

1
2
3

auto operator+(Point const right) const -> Point {
    return Point(x + right.x, y + right.y);
}

Należy zaobserwować ciekawe rzeczy:

  1. Zniknął nam lewy argument.
  2. Metoda jest oznaczona jako const.

Gdy binarny operator przeciążamy przy pomocy metody, jego lewy operand staje się obiektem, na rzecz którego go wywołujemy.

Oznacza to, że przy fragmencie:

1
2
3

auto p1 = Point(1, 2);
auto p2 = Point(5, 7);
fmt::println("{}", p1 + p2);

Ten + jest efektywnie wywoływany na p1. x oraz y z implementacji przeciążenia operatora referują do p1.x oraz p1.y.

p2 staje się oczywiście right.

Przeciążony operator (jako metoda) oznaczyliśmy jako const, bo chcemy zaznaczyć, że ten operator nie modyfikuje nam lewego operandu (w przykładzie wyżej — p1). W przykładzie, gdzie zaimplementowaliśmy go jako wolną funkcję, obydwa argumenty były const. Prawy operand został const, ale żeby metoda miała oznaczony lewy operand jako niezmienny, cała metoda musi być tak oznaczona.

Problem z przeciążeniem operatora jako metody dla istniejących klas

W poprzednim podrozdziale dostarczyliśmy operator+ również dla dwóch std::vector<int>ów. Również był on przeciążony jako wolna funkcja. Jak zatem można by go zamienić na metodę?

Nie da się.

Nie mamy dostępu do szablonu std::vector. Nie możemy sobie go “otworzyć” i dopisać tam operator+ jako metodę. Stąd pojawiła się wręcz konieczność, aby dostarczyć go jako wolną funkcję.

Popularne przykłady, gdzie operator dostarcza się jako wolną funkcję

Nie możemy edytować istniejących już klas (co najwyżej możemy dodawać specjalizacje szablonowe, ale co jeżeli dany typ nie jest szablonem?).

Nie zawsze możemy skorzystać z {fmt} (bo, przykładowo, produkt tworzony przez naszą firmę jest na niezgodnej licencji).

Mimo tego czasem chcemy, aby nasze typy dało się “wyświetlać”. Przez wprowadzeniem {fmt} korzystaliśmy z std::cout. Typem tego obiektu jest std::ostream. Oznacza to, że gdybyśmy chcieli udostępnić możliwość wyświetlania naszego typu (np. Point), to trzeba by to zrobić przy pomocy odpowiednio przeciążonego operatora <<:

#include <iostream>

#include <fmt/format.h>

struct Point {
    int x;
    int y;
};

auto operator+(Point const left, Point const right) -> Point {
    return Point(left.x + right.x, left.y + right.y);
}

auto operator<<(std::ostream& out, Point const p) -> std::ostream& {
    out << '(' << p.x << ", " << p.y << ')';
    return out;
}

auto main() -> int {
    auto p1 = Point(1, 2);
    auto p2 = Point(5, 8);
    std::cout << p1 + p2;
}

Warto zauważyć, że skoro lewy operand jest typu std::ostream, a ewidentnie jest to klasa stworzona przez kogoś innego, to nie ma innego sposobu jak dostarczyć wymagany operator inaczej niż przez wolną funkcję.

Pozostałe operatory, które muszą być przeciążone jako metody

Poznaliśmy już operator=, który musi być przeciążone jako metoda. Jakie inne operatory tego wymagają?

Istnieją takie trzy1:

  • operator()
  • operator[]
  • operator->

Ostatnim nie będziemy się przejmować.

operator()

Operator wywołania (ang. function call operator) to operator, dzięki któremu obiekty naszej klasy mogą być wywoływane jak funkcje. Spójrzmy na przykład:

#include <string>

#include <fmt/base.h>

struct Printer {
    std::string message;

    auto operator()() const -> void {
        fmt::println("{}", message);
    }
};

auto main() -> int {
    auto greeter   = Printer("Hello");
    auto announcer = Printer("Get ready!");

    greeter();
    announcer();
    greeter();
}

#include <fmt/base.h>

struct Adder {
    auto operator()(int const a, int const b) const -> int {
        return a + b;
    }
};

struct Reverser {
    auto operator()(int const a) const -> int {
        return -a;
    }
};

auto main() -> int {
    auto add     = Adder();
    auto reverse = Reverser();

    fmt::println("{} {}", add(1, 2), reverse(-3));
}

#include <fmt/base.h>

struct Reverser {
    auto operator()(int const a) const -> int {
        return -a;
    }
};

auto main() -> int {
    auto reverse1 = Reverser();
    auto reverse2 = [](int const a) { return -a; };

    fmt::println("{} {}", reverse1(3), reverse2(3));
}

Wyjście, jak poprzednio, jest takie samo, czyli -3 -3.

Podobieństwo nie jest przypadkowe — dokładnie tak działają lambdy!

Literał lambdy (jakaś forma [](){}) skutkuje powstaniem anonimowego typu, który — między innymi — ma przeciążony operator() o ciele zgodnym z tym, co podaliśmy w literale. Następnie literał jest zastępowany stworzeniem obiektu nowopowstałego typu.

Oczywiście to, co dokładnie znajduje się w wygenerowanym przez wyrażenie lambda typie, jest troszkę bardziej skomplikowane. Nie jest to jednak w tym momencie istotne.

operator[]

Operator indeksowania również musi być zdefiniowany jako metoda. Służy on do ujednolicenia sposobu dostępu do elementów większości kontenerów. Dzięki niemu std::array, std::vector czy std::string mogą oferować identyczny sposób dostępu do danych. Przypomnijmy, że w Javie:

  • tablice indeksujemy przy pomocy [];
  • listy (i generalnie kolekcje) przy pomocy .get();
  • a typy tekstowe przy pomocy .charAt().

W C++ to jest zawsze [].

operator[], do standardu C++23, mógł przyjmować wyłącznie pojedynczy argument. Oznaczało to, że gdy chciało się reprezentować dwuwymiarową kolekcję, trzeba było korzystać z niewydajnych (albo skomplikowanych) konstrukcji, które udostępniały składnię [i][j][k][...] lub udostępniać indeksowanie poprzez operator().

Jego implementacja nie różni się szczególnie od reszty operatorów. Weźmy na przykład pod uwagę jakiś typ opakowujący std::string, który wyświetla informację w momencie, gdy do tego std::string ktoś spróbuje się dostać:

#include <fmt/base.h>

class StringWrapper {
    std::string buffer;

public:
    StringWrapper(std::string const & buffer) : buffer(buffer) { }

    auto operator[](int const index) -> char& {
        fmt::println("Accessing index #{}" , index);
        return buffer[index];
    }

    auto print() const {
        fmt::println("{}", buffer);
    }
};

auto main() -> int {
    auto sw = StringWrapper("Hello");
    sw.print();
    sw[0] = 'h';
    sw.print();
    sw[2] = 'e';
    sw[3] = 'e';
    sw[4] = 'y';
    sw.print();
}

Ten kryptyczny błąd to C++owy sposób powiedzenia, że operator[] nie obiecuje, że w ramach jego wywołania nie zmodyfikujemy zawartości obiektu. Nie robimy tego, ale kompilator nie zawsze może to wykryć. Aby to naprawić, powinniśmy zadeklarować go jako const:

main.cpp:11:28: error: binding reference of type 'char&' to 'const __gnu_cxx::__alloc_traits<std::allocator<char>, char>::value_type' {aka 'const char'} discards qualifiers
   11 |         return buffer[index];
      |                            ^

Przetłumaczmy błąd na język ludzki — chodzi o to, że mówimy, że return buffer[index] zwróci nam char& (bo tak napisaliśmy po ->). Problem w tym, że… tak nie można. Wyrażenie return buffer[index] w ramach const metody zwraca char const&.

Brzmi to najpewniej strasznie nielogicznie, dziwnie, tragicznie i bezsensownie. Ale z drugiej strony efekt jest dosyć zrozumiały — metoda const nie powinna zwrócić nam surowej (nie-const) referencji do pola obiektu. Gdyby mogła, to taki kod musiałby się skompilować:

1
2
3
4

auto main() -> int {
    auto const sw = StringWrapper("Hello");
    sw[0] = 10;
}

Co byłoby oczywiście bezsensowne. const ma oznaczać prawdziwą niezmienność. Można na takim obiekcie wywoływać tylko const metody. Ale gdyby operator[], będąc const, pozwalał na zwrócenie nie-const referencji do pola, to kod powyżej by się skompilował bez żadnego problemu.

No to jak to się dzieje, że to działa w przypadku std::vector? Mogę na i const i nie-const wektorze wykonać operację indeksowania. W przypadku nie-const wektora pozwala mi ona zmieniać obiekty, a w przypadku const wektora nie. Jak to jest zrobione? Jakiś “trzeci stan”?

#include <fmt/base.h>

class StringWrapper {
    std::string buffer;

public:
    StringWrapper(std::string const & buffer) : buffer(buffer) { }

    auto operator[](int const index) -> char& {
        fmt::println("Accessing (maybe mutating) index #{}" , index);
        return buffer[index];
    }

    auto operator[](int const index) const -> char const& {
        fmt::println("Accessing (immutably) index #{}" , index);
        return buffer[index];
    }


    auto print() const {
        fmt::println("{}", buffer);
    }
};

auto main() -> int {
    auto const first = StringWrapper("Hello");
    auto second      = StringWrapper("Friends");
    fmt::println("{} {}", first[0], second[0]);
}

Gdy mamy const obiekt (first) i używamy indeksowania, wersja const jest wybierana. Gdy mamy nie-const obiekt (second) i używamy indeksowania, wersja bez const jest wybierana.

Można przeciążać metody na ich “constness”.

Warto też zwrócić uwagę, że wersja nie-const zwraca char&, gdzie wersja const zwraca char const&. Dzięki temu wszystko dobrze działa3.

Wszystkie inne operatory mogą być przeciążone jako wolne funkcje.

  1. Dlaczego akurat te trzy muszą być implementowane jako metody? Nie wiem. Jak ktoś wie, to niech mi napisze. Widziałem wiele opinii, ale żadna nie była potwierdzona rzetelnymi źródłami, które by wyjaśniały tak podjętą decyzję przez komitet standaryzacyjny języka C++. ↩

  2. Pierwsze dwie linie prezentowanego wyżej outputu mogą zostać wyświetlone w odwrotnej kolejności. To dlatego, że C++ może obliczać argumenty wysyłane do funkcji w dowolnej kolejności (tj. niekoniecznie od lewej do prawej). ↩

  3. Programiści C++ od dawna wyrażają pewien dyskontent w związku z tym, że takie przeciążenia są potrzebne. C++23, wraz z narzędziem deducing this częściowo z tym pomaga, choć nie jest to idealne rozwiązanie problemu. ↩
