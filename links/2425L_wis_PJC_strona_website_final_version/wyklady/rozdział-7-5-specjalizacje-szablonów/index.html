Tworzenie szablonów i ich specjalizacji

W języku Java jedną z najpopularniejszych kolekcji są HashMap i HashSet. Są to kolekcje przechowujące swoje elementy w miejscach sprecyzowanych przez tak zwany hash, czyli wartość liczbową wyliczoną na podstawie jakiejś określonej logiki. W Javie wszystkie obiekty mają metodę .hashCode() odziedziczoną z Object, ale w C++ tak nie jest.

std::unordered_map i std::unordered_set (C++owe odpowiedniki Javowych HashMap i HashSet) korzystają z obiektów funkcyjnych do obliczania odpowiednich hashy. Stwórzmy prostą wersję takiego obiektu:

template <typename T>
struct Hasher {
    auto compute(T const& t) const -> T {
        return t;
    }
};

auto main() -> int {
    auto const intHash = Hasher<int>();

    intHash.compute(3);
    intHash.compute(214743);
    intHash.compute(-4384);
}

Na pierwszy rzut oka taki Hasher nie robi nic ciekawego. Ma metodę .compute(), która jedyne co robi, to zwraca przekazaną liczbę. Jest jednak pewien problem — hash musi być zawsze liczbą całkowitą, a zatem nie powinniśmy zwracać T, tylko — przykładowo — int. Gdy jednak wprowadzimy tę zmianę, to zorientujemy się, że pojawi się kolejny problem:

auto main() -> int {
    auto const floatHash = Hasher<float>();

    fmt::println("{} {}", floatHash.compute(2.01f), floatHash.compute(2.99f));

Oczywiście to problem. Jak już wiemy, hash dla dwóch różnych obiektów powinien1 być różny. Tutaj tak jednak nie jest. Jak naprawić ten problem?

#include <bit>  // std::bit_cast

#include <fmt/base.h>

template <typename T>
struct Hasher {
    auto compute(T const& t) const -> int {
        return t;
    }

    auto compute(float const f) const -> int {
        return std::bit_cast<int>(f);
    }
};

auto main() -> int {
    auto const floatHash = Hasher<int>();

    fmt::println("{} {}", floatHash.compute(2.01f), floatHash.compute(2.99f));
}

Jak widać, wartości się już zdecydowanie różnią (o całe 4110418). Fantastycznie.

Użyty std::bit_cast pozwala na uzyskanie wartości jednego typu na podstawie binarnej reprezentacji innego typu. Nie należy zwracać na to teraz szczególnej uwagi.

Z jednej strony sukces (bo działa), ale z drugiej pojawia się więcej problemów, a mianowicie:

  • Gdy stworzymy Hasher<float>, to kod nam się nie skompiluje, bo .compute() przyjmujące T będzie “wyglądało zbyt podobnie” do naszego dodanego przeciążenia.
  • Gdy użytkownik tworzy własne typy, nie ma jak dodać przeciążeń do naszego Hashera. A gdybyśmy tworzyli własną hash-mapę, to musielibyśmy zdecydować się na jakiś typ, który by dla nas wykonywał hashowanie.

Problem ten możemy rozwiązać przy pomocy specjalizacji szablonów.

Specjalizacja szablonu

template <typename T>
struct Hasher {
    auto compute(T const& t) const -> int {
        return t;
    }
};

template <>
struct Hasher<float> {
    auto compute(float const f) const -> int {
        return std::bit_cast<int>(f);
    }
};

template <>
struct Hasher<short> {
    auto compute(short const s) const -> int {
        auto doubled = (s << 16) | s;
        return doubled;
    }
};

template <typename T>
struct Hasher {
    auto compute(T const& t) const -> int {
        return t;
    }
};

struct Point {
    int x;
    int y;
};

template <>
struct Hasher<Point> {
    auto compute(Point const p) const -> int {
        return p.x * 31 + p.y;
    }
};

Jest to bardzo istotne, ponieważ gdy potrzebujemy takiej mechaniki, to zwykle używamy szablonów, aby dopasować się do odpowiedniego hashera. Przykładowo, std::unordered_set ma taki nagłówek:

template <
        typename Key,
        typename Hash = std::hash<Key>,
        typename KeyEqual = std::equal_to<Key>,
        typename Allocator = std::allocator<Key>
> class unordered_set;

Gdy tworzymy std::unordered_set<int>, to efektywnie będzie on korzystał z std::hash<int> (oraz kilku innych rzeczy, które nas nie interesują). Oznacza to też, że gdybyśmy stworzyli std::unordered_set<Point>, to korzystałby on z std::hash<Point>. Biblioteka standardowa nie ma pojęcia o naszym typie Point, dlatego, aby to poprawnie zadziałało, musielibyśmy dodać własną specjalizację std::hash (czego nie będziemy na razie robić, bo korzystałoby to jednego, jeszcze przez nas nieopanowanego narzędzia).

Na tej samej zasadzie działa również optymalny sposób formatowania własnych typów w bibliotece {fmt} — musimy tam stworzyć specjalizację typu fmt::formatter, któremu zaimplementujemy w odpowiedni sposób metody .parse() oraz .format().

  1. Nie zawsze to wychodzi, ale implementacja zdecydowanie nie powinna zamieniać każdej liczby rzeczywistej na całkowitą przy pomocy obcinania części dziesiętnej. ↩
