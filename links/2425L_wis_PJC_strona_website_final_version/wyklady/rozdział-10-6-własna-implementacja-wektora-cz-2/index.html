namespace pjc {
    template <typename T>
    class Vector {
        int size_ = 0;
        T* data_ = nullptr;

    public:
        auto push_back(T const& newElement) -> void {
            size_ += 1;

            auto buffer = new T[size_];
            for (auto i = 0; i < size_ - 1; i++) {
                buffer[i] = data_[i];
            }
            buffer[size_ - 1] = newElement;

            data_ = buffer;
        }

        auto size() -> int {
            return size_;
        }

        auto print() -> void {
            for (auto i = 0; i < size_; i++) {
                fmt::print("{} ", data_[i]);
            }
        }
    };
}

Problemem jest to, że .push_back() w momencie nadpisywania data_ = buffer; “zapomina” o poprzedniej tablicy. Pamięć zajmowana przez tę tablicę wycieka, czyli wciąż jest oznaczona jako zarezerwowana dla naszego programu, ale z naszej perspektywy jest niedostępna.

Można temu wbrew pozorom w dosyć prosty sposób zaradzić. Wystarczy usunąć niepotrzebną tablicę tuż przed tym, gdy o niej zapomnimy:

auto push_back(T const& newElement) -> void {
    size_ += 1;

    auto buffer = new T[size_];
    for (auto i = 0; i < size_ - 1; i++) {
        buffer[i] = data_[i];
    }
    buffer[size_ - 1] = newElement;

    delete[] data_; // new operation
    data_ = buffer;
}

delete[] data_ zwolni pamięć, na którą wskazuje data_. Nie należy się przejmować sytuacją, gdzie .push_back() jest używane po raz pierwszy, bo o ile wtedy faktycznie data_ wskazuje na nullptr, to zarówno delete nullptr jak i delete[] nullptr gwarantują, że nic nie zrobią.

Należy tutaj użyć delete[], a nie delete, bo pamięć otrzymaliśmy z new[], a nie new. Użycie delete na pamięci uzyskanej z new[] lub delete[] na pamięci uzyskanej z new skutkuje Zachowaniem Niezdefiniowanym (UB).

Nikt. A powinna ona być czyszczona! Na szczęście znamy już narzędzie, które nam pomoże w tej sytuacji — destruktor.

Nie zaimplementowaliśmy operatora = (przypisania), tak więc C++ sam go dostarczył do naszego szablonu. Wykonuje on prymitywne przypisanie pól, czyli nadpisuje .size_ i .data_ odpowiadającymi polami wektora znajdującego się po prawej stronie operatora przypisania.

Oznacza to, że operacja first = second sprawi, że znajdziemy się w następującej sytuacji:

  A(first.data_) --> D
  C(second.data_) --> D["｜ 10 ｜"]

A więc wyciek pamięci?

Tak, ale to nie jedyny problem. Tablica z wartością 1 nam wycieka, ale w momencie wyjścia z bloku funkcji main() wywołamy destruktory first i second, co poskutkuje wykonaniem kodu odpowiadającemu tym operacjom:

namespace pjc {
    template <typename T>
    class Vector {
        int size_ = 0;
        T* data_ = nullptr;

    public:
        // added operator=
        auto operator=(Vector const& other) -> void {
            delete[] data_;
            data_ = other.data_;
            size_ = other.size_;
        }

        auto push_back(T const& newElement) -> void {
            size_ += 1;

            auto buffer = new T[size_];
            for (auto i = 0; i < size_ - 1; i++) {
                buffer[i] = data_[i];
            }
            buffer[size_ - 1] = newElement;

            delete[] data_;
            data_ = buffer;
        }

        auto size() -> int {
            return size_;
        }

        auto print() -> void {
            for (auto i = 0; i < size_; i++) {
                fmt::print("{} ", data_[i]);
            }
        }

        ~Vector() {
            delete[] data_;
        }
    };
}

Czy teraz działa?

Jest lepiej, ale wciąż nieidealnie. Nasz oryginalny problem, czyli:

Teraz wywołujemy first.push_back(20). .push_back() tworzy nową tablicę, kopiuje elementy i usuwa starą. To znaczy, że będziemy mieli następującą sytuację:

graph LR
  A(first.data_) --> B["｜ 10 ｜ 20 ｜"]
  C(second.data_) --> D:::hidden

Czemu tak?

Bo przecież wykonaliśmy delete[] na tablicy, na którą oryginalnie wskazywał first.data_ tuż przed tym, jak nadpisaliśmy ten wskaźnik adresem pamięci z większą tablicą (do której dodaliśmy 20). Na tą samą tablicę wskazywał second.data_ — pech.

Oczywiście nie “pech”, a źle zaprojektowane zachowanie pjc::Vector. operator= nie powinien po prostu kopiować wskaźnika. Jest to tak zwana płytka kopia (ang. shallow copy) i zwykle nie jest tym, czego chcemy. operator= powinien samodzielnie alokować pamięć, a nie sprawiać, że dany obiekt “podpatruje” to, co stworzył inny.

Problem manifestuje się w następnej linijce, czyli w second.push_back(30). .push_back() widzi, że przed chwilą second.size_ był 1, a zatem trzeba coś skopiować z oryginalnego second.data_. Problem w tym, że ten wskaźnik wskazuje na tablicę, którą usunęliśmy z pamięci.

Poprawna implementacja operatora przypisania (=) naprawi ten problem. Powinien on wykonywać głęboką kopię (ang. deep copy):

auto operator=(Vector const& other) -> void {
    delete[] data_;
    size_ = other.size_;

    // deep copy
    data_ = new T[size_];
    for (auto i = 0; i < size_; i++) {
        data_[i] = other.data_[i];
    }
}

auto operator=(Vector const& other) -> void {
    // we perform operations only if this is not a self-assignment
    if (this != &other) {
        delete[] data_;
        size_ = other.size_;

        data_ = new T[size_];
        for (auto i = 0; i < size_; i++) {
            data_[i] = other.data_[i];
        }
    }
}

this jest wskaźnikiem na obiekt, na rzecz którego wywoływana jest metoda. Jego użycie jest tożsame do this z Javy.

A skoro this wskazuje na obiekt, na rzecz którego wywoływana jest metoda, to znaczy, że przechowuje adres tego obiektu. &other zwraca nam adres prawego operandu przypisania. Jeżeli te adresy są identyczne, to mamy do czynienia z przypisaniem obiektu do siebie samego. Wykonujemy operacje, tylko jeśli nie jest to samoprzypisanie.

A czy teraz to już wszystko?

Tak.

Nie. Podobny rodzaj problemu będzie miał miejsce przy konstruktorze kopiującym wektora. Oznacza to, że trzeba również jego odpowiednio zaimplementować:

Jak widać, trzeba było zaimplementować zarówno konstruktor kopiujący, operator nadpisania, ale również i destruktor. Tak właśnie zwykle jest, gdy musimy zaimplementować którykolwiek z nich. W końcu oni razem tworzą Wielką Trójkę.

Gdy potrzebuje zaimplementować dowolną z metod specjalnych z Wielkiej Trójki, to najpewniej potrzebujemy zaimplementować też pozostałe z nich.

namespace pjc {
    template <typename T>
    class Vector {
        int size_ = 0;
        T* data_ = nullptr;

    public:
        Vector() = default; // needs to be present, because otherwise the only valid constructor would be the below one
    
        Vector(Vector const& other) : size_(other.size_), data_(new T[other.size_]) {
            for (auto i = 0; i < other.size_; i++) {
                data_[i] = other.data_[i];
            }
        }

        auto operator=(Vector const& other) -> void {
            if (this != &other) {
                delete[] data_;
                size_ = other.size_;

                data_ = new T[size_];
                for (auto i = 0; i < size_; i++) {
                    data_[i] = other.data_[i];
                }
            }
        }

        auto push_back(T const& newElement) -> void {
            size_ += 1;

            auto buffer = new T[size_];
            for (auto i = 0; i < size_ - 1; i++) {
                buffer[i] = data_[i];
            }
            buffer[size_ - 1] = newElement;

            delete[] data_;
            data_ = buffer;
        }

        auto size() -> int {
            return size_;
        }

        auto print() -> void {
            for (auto i = 0; i < size_; i++) {
                fmt::print("{} ", data_[i]);
            }
        }

        ~Vector() {
            delete[] data_;
        }
    };
}

Mamy pierwsze wyjaśnienie problemu — nie można tworzyć wskaźnika do referencji. Dlaczego? Bo referencja nie jest formalnie obiektem. Jest aliasem na jakiś inny obiekt. Język C++ nie akceptuje konstrukcji, które by próbowały traktować referencję jako pełnoprawny obiekt.

Dodatkowo mamy jeszcze inny problem. Nawet jeśli dałoby się formować wskaźnik do referencji, to sama implementacja wektora musiałaby korzystać z operacji, które byłyby błędne dla referencji. Spójrzmy jeszcze raz na implementację .push_back():

Teraz zobaczmy, co by się stało, gdyby T było, przykładowo, referencją do inta (int&). Wykonalibyśmy operację auto buffer = new T[size_], która by zaalokowała tablicę referencji do intów o wielkości size_.

No tak, w czym problem?

A z czym byłyby te referencje połączone? Przecież nie możemy mieć referencji, która jest z niczym niepołączona.

Faktycznie…

Poza tym później trzeba by je przepinać (w pętli).

Oznacza to, że aby stworzyć poprawnie działający polimorficzny kontener, potrzebujemy referencji (aby uniknąć object slicingu), która może być z niczym niepołączona i która może być przepinana.

Taka referencja nazywa się wskaźnik.

W pewnym sensie można myśleć o wskaźnikach jako o nullowalnych referencjach, które można przepinać.

Tak naprawdę wskaźniki potrafią jeszcze trochę więcej, ale na ten moment takie uproszczenie nam wystarczy.

Skorzystajmy zatem ze wskaźników i zobaczmy, jak powinien wyglądać poprawny, polimorficzny kontener — w następnym podrozdziale.
