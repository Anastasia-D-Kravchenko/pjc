Implementacja pjc::Vector

Aby się dowiedzieć, dlaczego std::vector wykonuje takie operacje, należy zrozumieć, w jaki sposób działa wewnętrznie.

~ Pierwszy podrozdział w ramach obecnego rozdziału.

Zobaczmy zatem, jak zaimplementować taki std::vector.

Zabierzmy się zatem za implementację. Na początek stwórzmy pewnego rodzaju kontrakt między .push_back() i .size(). W końcu pierwotnie .size() powinno zwracać 0, ale każdy .push_back(), skoro ma dodawać elementy do wektora, powinien skutkować taką modyfikacją obiektu, aby .size() zwracało liczbę o 1 większą.

Z teorii programowania obiektowego wiemy, że jeżeli chcemy, aby jakiś stan został zachowany między wywołaniami metod, należy go zapisać w polu klasy. Dodajmy zatem pole .size_2:

Niestety, wywołanie vector.print() niczym nie poskutkuje. Czas zaimplementować tę metodę. Oznacza to, że .push_back() musi zacząć zapisywać te wszystkie nowe elementy, które do niego przekazujemy. Zacznijmy zatem od niego.

Gdy podczas działania programu chcemy poprosić o więcej pamięci, należy użyć new. new zwraca wskaźnik. Ten wskaźnik musimy zapamiętać — w końcu, gdy zaalokujemy pamięć, chcemy, aby .print() mogło się do niej odwołać. Znowu wracamy do zasady z OOP (programowania zorientowanego obiektowo, ang. object-oriented programming):

namespace pjc {
    template <typename T>
    class Vector {
        int size_ = 0;
        T* data_ = nullptr; // new field

    public:
        auto push_back(T const& newElement) -> void {
            size_ += 1;
        }

        auto size() -> int {
            return size_;
        }

        auto print() -> void {
            // empty for now
        }
    };
}

Dodaliśmy wskaźnik data_. Jest on pierwotnie ustawiony na nullptr, który jest odpowiednikiem Javowego null. Ten wskaźnik nie wskazuje na nic.

Teraz dodajmy odpowiednie zachowanie do .push_back():

1
2
3
4
5
6

auto push_back(T const& newElement) -> void {
    size_ += 1;

    data_ = new T[size_];         
    data_[size_ - 1] = newElement;
}

Metoda teraz nie tylko zwiększa .size_, ale też alokuje potrzebną pamięć w postaci tablicy elementów typu T i na jej ostatnie miejsce wstawia obiekt newElement.

Wskaźniki, które wskazują na elementy będące częścią jakiejś tablicy, można indeksować tak samo, jak tablice, napisy czy std::vectory3.

Operacja new T[N] alokuje pamięć, w której zostaje utworzona tablica N elementów typu T, a następnie zwracany jest wskaźnik na pierwszy z nich. Operacja *new T[N] zwraca dostęp do pierwszego elementu z tej tablicy. Natomiast — dla wygody — można używać na takim wskaźniku indeksowania.

Przykładowo, robiąc:

1

auto ptr = new int[5];

Operacja *ptr zrobi dokładnie to samo co ptr[0].

Wróćmy jednak do wektora. .push_back() teraz alokuje pamięć i dodaje do niej nowe elementy. Zaimplementujmy zatem .print():

1
2
3
4
5

auto print() -> void {
    for (auto i = 0; i < size_; i++) {
        fmt::print("{} ", data_[i]);
    }
}

Jak widać, prosta pętla for () pozwala nam na dostęp do wszystkich elementów z naszej tablicy, do której dostajemy się przez wskaźnik .data_.

#include <fmt/base.h>

namespace pjc {
    template <typename T>
    class Vector {
        int size_ = 0;
        T* data_ = nullptr;

    public:
        auto push_back(T const& newElement) -> void {
            size_ += 1;

            data_ = new T[size_];
            data_[size_ - 1] = newElement;
        }

        auto size() -> int {
            return size_;
        }

        auto print() -> void {
            for (auto i = 0; i < size_; i++) {
                fmt::print("{} ", data_[i]);
            }
        }
    };
}

auto main() -> int {
    auto vector = pjc::Vector<int>();
    vector.push_back(1);
    vector.push_back(2);
    vector.push_back(3);

    vector.print();
}

Zobaczmy, co się dzieje z naszym wskaźnikiem .data_ podczas programu.

Pierwotnie, nie wskazuje on na nic (a raczej wskazuje na nullptr):

graph LR
    A(data_) --> B(("∅"))

Następnie wykonujemy vector.push_back(1);, co skutkuje przepięciem .data_ na nową tablicę:

graph LR
    A(data_) --> B["｜ 1 ｜"]

Potem kolejny .push_back() sprawia, że .data_ wskazuje na większą tablicę:

graph LR
    A(data_) --> B["｜ ⠀ ｜ ⠀ ｜"]

Na której koniec dopisujemy 2:

graph LR
    A(data_) --> B["｜ ⠀ ｜ 2 ｜"]

Później kolejny .push_back() skutkuje stworzeniem trzyelementowej tablicy i wpisaniem do niej 3:

graph LR
    A(data_) --> B["｜ ⠀ ｜ ⠀ ｜ 3 ｜"]

A co jest w tych pierwszych dwóch miejscach (w naszym przypadku intach) w tej tablicy?

Wyśmienite pytanie! Dokładnie to samo, co by się wyświetliło, gdybyśmy zrobili tak:

int x;
fmt::println("{}", x);

Czyli… nie wiadomo! Jest to niezainicjalizowana pamięć, której próba odczytu przed pierwotnym nadpisaniem będzie skutkowała Zachowaniem Niezdefiniowanym (UB).

Ten problem można dosyć prosto naprawić. Wystarczy nie zapominać o elementach, które już kiedyś dodaliśmy. Osiągniemy to, wpierw tworząc nową, większą tablicę, kopiując do niej “stare” dane, dodając do niej nowy element i przepinając wskaźnik:

auto push_back(T const& newElement) -> void {
    size_ += 1;

    auto buffer = new T[size_];             // 1
    for (auto i = 0; i < size_ - 1; i++) {  // 2
        buffer[i] = data_[i];               // 2
    }                                       // 2
    buffer[size_ - 1] = newElement;         // 3

    data_ = buffer;                         // 4
}

Przedstawmy ten algorytm w liście kroków:

  1. Tworzymy nową tablicę, która pomieści wszystkie stare dane i nowy newElement.
  2. Kopiujemy wszystkie wcześniej dodane elementy z .data_ do nowej, większej tablicy.
  3. Dodajemy newElement do większej tablicy.
  4. Zapominamy o starej, mniejszej tablicy i przepinamy .data_ tak, aby wskazywał na nową, większą tablicę (ze wszystkimi starymi elementami i z nowym (newElement)).

Dla pełnego zrozumienia przedstawmy ten algorytm jeszcze raz, ale wspomagając się rysunkami. Każdy krok zostanie zwizualizowany. Załóżmy, że analizujemy ostatni .push_back(), czyli ten dodający trzecią wartość:

  1. graph LR
A(data_) --> B["｜ 1 ｜ 2 ｜"]
C(buffer) --> D["｜ ⠀ ｜ ⠀ ｜ ⠀ ｜"]

  2. graph LR
A(data_) --> B["｜ 1 ｜ 2 ｜"]
C(buffer) --> D["｜ 1 ｜ 2 ｜ ⠀ ｜"]

  3. graph LR
A(data_) --> B["｜ 1 ｜ 2 ｜"]
C(buffer) --> D["｜ 1 ｜ 2 ｜ 3 ｜"]

  4. graph LR
A(data_) --> D
C(buffer) --> D["｜ 1 ｜ 2 ｜ 3 ｜"]

Po zakończeniu metody .push_back(), zmienna lokalna buffer ginie. Ale to tylko wskaźnik! Tablica zaalokowana przez new nie ginie. Mamy do niej dostęp i po zakończeniu działania tej metody .data_ wygląda tak:

   graph LR
C(data_) --> D["｜ 1 ｜ 2 ｜ 3 ｜"]

Nasz wektor działa! A przynajmniej takie sprawia wrażenie. .push_back() dodaje elementy, .size() poprawnie zwraca informację, ile ich jest, a .print() je wszystkie wyświetla.

Niestety jest pewien problem. Pod koniec działania naszego programu, a konkretnie tuż w momencie dotarcia do klamry zamykającej main(), nasza pamięć wygląda tak:

   graph TD
  A["｜ 1 ｜"]
  B["｜ 1 ｜ 2 ｜"]
  C["｜ 1 ｜ 2 ｜ 3 ｜"]

Mamy zaalokowane trzy tablice. Tablice, do których nie mamy dostępu. Napotkaliśmy problem wycieku pamięci. Rozwiążmy go — zapraszam do następnej części rozdziału.

  1. Wiemy już, że nie pozwala na przechowywanie referencji, ale załóżmy, że został tutaj użyty delikatnie niepoprawny skrót myślowy. ↩

  2. Pole nazwaliśmy size_, a nie size, bo C++ nie pozwoli nam mieć pola i metody o tej samej nazwie. W Javie nie było to problemem, ale w C++ nie jest to legalne. ↩

  3. Indeksowanie wskaźnika tak naprawdę jest zamieniane na operację z dziedziny arytmetyki wskaźników, ale o niej będzie potem. Na ten moment uproszczenie w postaci możliwości indeksowania wskaźników jest wystarczająco poprawne. ↩
