Głębokie kopiowanie

public class Main {
    public static void main(String[] args) {
        int[] arr1 = {1, 2, 3};
        int[] arr2 = arr1;

        arr1[1] = 10;
        System.out.println(arr2[1]);
    }
}

W obydwu listingach zmieniamy środkowy element jakiegoś zbioru danych. W przypadku C++ jest to std::vector, w przypadku Javy jest to tablica intów.

Przed modyfikacją kopiujemy zbiór do nowej zmiennej. Modyfikacja odbywa się przy pomocy “oryginału”, a późniejsze odczytania za pomocą kopii.

Wyniki wykonania obydwu programów mogą byc nieco zaskakujące:

W przypadku Javy (znana nam już) sytuacja jest relatywnie prosta. arr1 i arr2 referują do tej samej tablicy zaalokowanej w pamięci programu. Modyfikacja elementu poprzez jedną z tych zmiennych jest widoczna poprzez drugą.

W przypadku C++ sytuacja jest inna. Operacja auto vec2 = vec1 tworzy pełnoprawną kopię vec1 pod nazwą vec2. Zmiany na vec1 nie będą miały wpływu na vec2 oraz vice versa. Nazywa się to głęboką kopią (ang. deep copy).

Różnicę w wyżej przedstawionym zachowaniu nazywamy rozróżnieniem między semantyką referencji oraz semantyką wartości.

W Javie mamy do czynienia z semantyką referencji. Oznacza to, że zmienne referują do obiektów. Kopia zmiennej jest jedynie kopią odnośnika. W ten sposób można mieć wiele zmiennych, za pomocą których otrzymuje się dostęp do jednego obiektu. Wyjątkiem są zmienne o typach prymitywnych (np. int, boolean, double).

W C++ mamy do czynienia z semantyką wartości. Oznacza to, że zmienne są faktycznymi obiektami. Kopiowanie zmiennej tworzy nam zupełnie niezależny obiekt.

Te niekiedy zaskakujące wyniki operatorów porównywania są skutkiem tego, że == w Javie oznacza:

  1. Dla zmiennych prymitywnych porównanie wartości.
  2. Dla zmiennych złożonych porównanie, czy obydwie zmienne referują do tego samego obiektu.

Punkt nr 2 był powodem, dla którego tak istotnym było opanować użytkowanie i zrozumienie wagi metody .equals() w Javie.

To dlatego, że operator == w C++ porównuje zawartość obiektów. Zachowuje się tak samo intuicyjnie, jak == dla prymitywów w Javie.

W C++ do porównywania obiektów nie używamy .equals(), tylko ==, które zachowuje się konsekwentnie z tym, jak działa dla typów prymitywnych.

Dodatkowo C++ oferuje też pozostałe operatory relacji dla większości kontenerów (między innymi dla std::string i std::vector), tj. <, <=, !=, > i >=. Elementy kontenerów są porównywane leksykograficznie.

Jak porównać dwa różne kontenery?

#include <algorithm>
#include <iostream>
#include <string>
#include <vector>

auto main() -> int {
    auto str = std::string("hello");
    auto vec = std::vector<char>{'o', 'l', 'l', 'e', 'h'};

    std::ranges::reverse(vec); // to not make it too easy
}

Ideą tego listingu jest pokazać, że czasem dwa różne kontenery składają się z tych samych elementów. Czasami chcemy sprawdzić, czy tak właśnie jest. Przykładowo, w tym przypadku zarówno str jak i vec przechowują znaki (char), które układają się w napis hello.

Niestety, próba użycia porównania na zasadzie str == vec zakończy się błędem kompilacji.

#include <algorithm>
#include <iostream>
#include <string>
#include <vector>

auto main() -> int {
    auto str = std::string("hello");
    auto vec = std::vector<char>{'o', 'l', 'l', 'e', 'h'};

    std::ranges::reverse(vec);

    auto equal = true;
    if (str.size() != vec.size()) {
        equal = false;
    } else {
        for (auto i = 0; i < str.size(); i++) {
            if (str[i] != vec[i]) {
                equal = false;
            }
        }
    }

    std::cout << equal;
}

Takie rozwiązanie działa, ale jest dalekie od optymalnego w kwestii czytelności. Najlepiej byłoby skorzystać ze standardowego algorytmu o nazwie std::ranges::equal():

    std::ranges::reverse(vec);

    auto equal = std::ranges::equal(str, vec);

    std::cout << equal;
}

Słowo kluczowe const

Słowo kluczowe const deklaruje jakąś konstrukcję (obiekt) jako niezmienną. Przykładowo, gdy stworzymy obiekt typu int const, to nie będziemy mogli go zmienić:

1
2
3
4
5

auto main() -> int {
    auto const x = 10;

    x = 20;
}

1
2
3

main.cpp:4:7: error: assignment of read-only variable 'x'
    4 |     x = 20;
      |     ~~^~~~

Niektóre osoby najpewniej widzą pewne podobieństwo do odpowiednika tego słowa kluczowego z Javy, czyli final. O ile to bardzo dobre porównanie w przypadku prymitywnych typów danych z Javy, to w przypadku typów złożonych C++ zaczyna się znacząco odróżniać.

Przykładowo, gdy w Javie tworzymy final tablicę, np. tak: final int[] arr = {1, 2, 3}, to nic nie stoi na przeszkodzie zmienić któryś z jej elementów, np. przy pomocy polecenia arr[0] = -1. Jedyne, czego nie możemy z taką zmienną zrobić, to jej nadpisać w całości, np. przy pomocy arr = new int[1337].

Podobna sytuacja ma miejsce z resztą kolekcji w Javie.

Jednak w C++ const reprezentuje dużo silniejszą semantykę niezmienności. Przykładowo, do const wektora nie można dodać żadnego elementu. Nie można żadnego elementu zmodyfikować. Nie można z niego usunąć żadnego elementu i nie można nadpisać całego kontenera. std::vector<T> const jest prawdziwie wyłącznie do odczytu.

Podobnie jak w innych językach (np. JavaScript (JS) / TypeScript (TS), Rust czy w językach funkcyjnych) niemutowalność (ang. immutability) w C++ jest uznawana za pożądaną. Dzięki niej możemy uniknąć trudnych do wykrycia błędów związanych z nieoczekiwaną zmianą stanu pamięci (zwłaszcza w kontekście danych o szerokim zakresie lub danych współdzielonych wielowątkowo).

Niestety nie było to oczywiste w momencie tworzenia tego języka. Dlatego (tak samo, jak w JS / TS) — niestety — oczekiwane jest używanie dłuższego i mniej wygodnego sposobu deklarowania typów (używać const praktycznie wszędzie).
