Tym razem tekst błędu jest całkiem przydatny. Mówi o tym, że redefiniujemy szablon template<class Object> void print(const Object&), którego pierwszą deklaracją było template<class Container> void print(const Container&).

No tak — w końcu nazwy parametrów nie mają większego znaczenia dla kompilatora. Nie wprowadziliśmy żadnego przeciążenia, bo w C++ na nazwie parametru nie można przeciążać. Obydwa print()y to nic innego jak szablon przyjmujący pojedynczy parametr szablonowy i pojedynczy parametr wydedukowanego typu.

Co w takim razie robić? Czy da się połączyć przeciążanie i szablony?

Oczywiście, że można. Ale jeśli chcemy, aby przeciążenia wspierały identyczne sygnatury, to musimy ograniczyć dopasowanie któregoś szablonu do jakiegoś podzbioru typów.

E..?

Mówiąc prościej — trzeba jakoś powiedzieć kompilatorowi, żeby używał pierwszego print() tylko jeśli wydedukowany typ spełnia dany warunek, np. jest zakresem (można przejść po jego elementach dzięki pętli zakresowej), a w przeciwnym przypadku niech używa tego “bardziej generycznego” szablonu.

Tak się da?

Tak. Należy skorzystać z Konceptów.

Koncepty

Koncepty (ang. Concepts) to wprowadzony w C++20 element języka, który pozwala ograniczać (ang. constrain) szablon do jakiegoś podzbioru typów. Aby osiągnąć nasz cel sprecyzowany w poprzedniej części tego artykułu, możemy wprowadzić jedną małą, prostą zmianę:

#include <iostream>
#include <ranges> // std::ranges::range
#include <vector>

template <std::ranges::range Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

template <typename Object>
auto print(Object const& object) -> void {
    std::cout << object << '\n';
}

auto main() -> int {
    auto const vec = std::vector<int>{2, 1};
    auto const num = 37;

    print(vec);
    print(num);
}

2

2 1
37

Kod się zmienił jedynie w dwóch linijkach — bardzo łatwo było przeoczyć tę zmianę. Oto one:

  1. Dodaliśmy #include <ranges>, aby skorzystać z Konceptu std::ranges::range.
  2. Zamiast typename Container w pierwszym szablonie napisaliśmy std::ranges::range Container.

Tak, to wystarcza! Teraz pierwszy print() zostanie wybrany, tylko jeśli przy wywołaniu print(arg) argument arg będzie spełniał Koncept std::ranges::range, czyli będzie zakresem. Jeżeli jednak arg nie spełnia tego Konceptu, to zostanie wybrana druga implementacja print().

Okej, fajne, ale czym jest ten Koncept? W jaki sposób on sprawdza, czy argument jest zakresem? Czy można tworzyć własne Koncepty? Co, jeśli chcę, aby typ wspierał więcej niż jeden z nich? Jak dokładnie std::ranges::range jest używany w szablonie print()?

Doskonałe pytania! Odpowiedzmy sobie na wszystkie z nich.

Czym są Koncepty?

Koncept to specjalny element języka, który służy do tego, aby poddawać testom jakieś typy. Przetestować możemy dowolny typ — int, double, bool, std::vector<int>, std::string itd. Koncept powie nam, czy dany typ, którego poddajemy testom, spełnia jakieś wymagania.

Aby sprawdzić, czy dany typ spełnia jakiś Koncept, wystarczy go dostarczyć do argumentów szablonowych Konceptu i przechwycić wynik w postaci boola:

#include <ranges>
#include <set>
#include <string>
#include <vector>

#include <fmt/base.h>

auto main() -> int {
    fmt::println("vector is a range? {}", std::ranges::range<std::vector<int>>);
    fmt::println("set is a range?    {}", std::ranges::range<std::set<int>>);
    fmt::println("string is a range? {}", std::ranges::range<std::string>);
    fmt::println("int is a range?    {}", std::ranges::range<int>);
    fmt::println("double is a range? {}", std::ranges::range<double>);
}

W jaki sposób Koncept sprawdza, czy dany typ spełnia jakieś wymagania?

Trzymając się przykładu z std::ranges::range, warto zobaczyć, jak on jest zdefiniowany:

1
2
3
4
5

template< class T >
concept range = requires( T& t ) {
    ranges::begin(t);
    ranges::end  (t);
};

Powyższą definicję należy czytać w następujący sposób: Koncept range jest spełniony, jeżeli przy założeniu, że mamy (surową / nie const) referencję do dowolnego typu, można wywołać funkcje std::ranges::begin() i std::ranges::end() przekazując im przez argument tę referencję.

Oczywiście zarówno std::ranges::begin() jak i std::ranges::end() mają swoje, kolejne wymagania do spełnienia, ale nie ma sensu grzebać aż tak głęboko w szczegółach. W tym przypadku wystarczy jedynie wiedza, że std::ranges::range jest spełnione, jeśli dany typ wspiera pobranie begin() oraz end().

Aby dokładniej zrozumieć, jakie cechy może sprawdzać Koncept, stwórzmy nasz własny.

Tworzenie własnych Konceptów

Aby stworzyć własny Koncept, należy skorzystać ze składni tworzenia szablonu oraz ze słowa kluczowego concept oraz requires:

    fmt::println("int has size?    {}", HasSize<int>);

Co w przypadku, gdy chcemy, aby jakiś typ wspierał więcej niż jeden Koncept?

Jeżeli piszemy szablon i chcemy go ograniczyć, to istnieje więcej niż jeden sposób, aby to osiągnąć. Biorąc pod uwagę przykład szablonu print():

1
2
3
4

template <std::ranges::range Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

Równoważną składnią byłoby napisanie:

1
2
3
4
5
6
7
8

template <typename Container>
requires std::ranges::range<Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

Oznacza to, że zamiast zastępować typename jakimś Konceptem, możemy skorzystać z dodatkowej klauzuli requires, która wymaga, aby Container spełniał Koncept std::ranges::range.

Oczywiście zawsze istnieje możliwość stworzenia własnego Konceptu, który łączy kilka innych, ale czasami nie jest to warte wprowadzania nowego elementu aplikacji. Można wtedy skorzystać z wyrażeń logicznych oraz requires:

template <typename Container>
requires std::ranges::range<Container> && HasSize<Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

W ten sposób napisaliśmy, że wymagamy, aby typ Container nie tylko był zakresem, ale również i wspierał metodę .size().

#include <iostream>
#include <ranges>
#include <vector>

template <std::ranges::range Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

template <typename Object>
auto print(Object const& object) -> void {
    std::cout << object << '\n';
}

auto main() -> int {
    auto const vec = std::vector<int>{2, 1};
    auto const num = 37;

    print(vec);
    print(num);
}

Wiemy już, jak on zadziała. Pierwsze wywołanie (print(vec)) skorzysta z pierwszego (ograniczonego Konceptem) szablonu, a drugie (print(num)) z drugiego (nieograniczonego).

Wszystko wydaje się mieć sens, ale niektórzy mogą wciąż być nieusatysfakcjonowani — no bo skąd kompilator ma wiedzieć, żeby zignorować drugi szablon przy wywołaniu z wektorem?

Z jednej strony może się to wydawać oczywiste — w końcu ten szablon się nie skompiluje. Nie jest to jednak wystarczające wytłumaczenie. To, czy jakiś kod w środku szablonu się skompiluje, z założenia nie dyskwalifikuje szablonu z bycia kandydatem przy wybieraniu odpowiedniej implementacji.

Główną rolę odgrywa tutaj większe wyspecjalizowanie lub większe ograniczenie. Jeżeli jakieś wywołanie (np. print(vec)) pasuje do więcej niż jednego szablonu, to jeżeli któryś z nich jest bardziej ograniczony (ale wciąż pasuje!), to ten szablon zostanie wybrany.
