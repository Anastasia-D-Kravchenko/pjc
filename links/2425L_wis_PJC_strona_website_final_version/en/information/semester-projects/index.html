Semester Projects

Posted Apr 3, 2025

16 min read

Warning: During the first two weeks after the publication of these project topics, the tutors reserve the right to slightly alter the details of grading rules; the goal is to verify and enhance the quality and clarity of the requirements.

A heartfelt request to all students to read this article to the very end. It would be shameful to get negative dozen or so percent of points because you named the file incorrectly or sent the wrong files, wouldn’t it?

General Information

Each student should choose a project topic from the list presented in this document. According to the passing rules, the student must submit and defend the project within the specified deadline.

The defense of the project aims not only to verify the student’s independence but also their understanding of the used tools. Therefore, the student may be questioned on each tool used. A project created independently may be not defended successfully. This occurs when, colloquially speaking, modifications are made to the code “to make it work” without understanding what they change.

It is forbidden to use tools that the student does not understand at least at a decent level.

Strict citation rules must be followed. If a student finds any source on the Internet from which they write a piece of code, they must provide that source in a comment in the source code as close as possible to its application. Lecture and exercise materials are exceptions. Failure to comply with this rule may result in the entire project not being approved.

Each project should be accompanied by a video that will present how the finished application works. Details are provided at the end of this document.

Project topics

Database

Create an application that, when launched, behaves like a simple database. The student must define (and describe in comments, preferably in one place, e.g., above main()) how data is stored and the query language supported by the database.

The application should support:

  • Data Definition Language (DDL) operations that allow creating and deleting database structures (e.g., tables or relationships between them). Additionally, modification of these structures must be supported (e.g., adding a column to a table).
  • Data Modification Language (DML) operations that allow manipulation of data within the database structures (e.g., populating tables with data).
  • Data Query Language (DQL) operations involving constructing queries that return information about data in the database (e.g., SELECT, WHERE, etc.). At least two operations should be supported.

The application must not be implemented as a form of extended dialogue. This means that operations must take the form of queries using the language created by the student. Implementations where database operations are executed by selecting options from a menu are not allowed. For example:

1
2
3

Press 1 to add a table
Press 2 to delete a table
Press 3 to add data to a table

etc.

Any doubts should be discussed with the course instructor.

The language must support some level of composing operations. For example, assuming support for operations similar to SQL SELECT and WHERE, the user should be able to use any number of conditions and WHERE clauses in a single query.

Additionally, the database must support commands for saving and loading state from a file — a kind of backup. The database should support saving and loading from different files (with paths provided by the user).

The database structure should support data type enforcement. Additionally, database operations should not modify the backup file every time (as it significantly impacts performance). It is best to keep data in memory and only occasionally (e.g. on-demand or when closing the application) save their state to a file.

Code quality\(5\)
Database structure\(5\)
Potential complexity of database\(7\)
Saving and loading state from a file\(3\)
DDL\(8\)
DML\(2\)
DQL\(10\)

Hexxagon

Create a clone of the classic DOS game Hexxagon. The game involves placing and moving pawns on a hexagonal board made up of small hexagons. Two players by cloning and moving their pawns convert opponent pawns into their own. The player with more pawns at the end of the game wins. The game ends when one player has no pawns left or the board runs out of empty spaces.

The application should support:

  • Basic menu that appears upon launching the application.
  • Ability to play alternately (hot seat) or against the computer.
  • Ability to save the game to a file.
  • Ability to load the game from a file.
  • Remembering details of several top games (the criteria of “better” is open to interpretation by the student).

The menu should allow:

  • Starting the game:
    • Against the computer;
    • Against another player taking turns.
  • Loading a saved game.
  • Displaying details of “best” saved games.

The computer player mode should incorporate a form of artificial intelligence implemented as a non-trivial set of rules by which the computer chooses its next move.

Improper usage of the application should result in appropriate error messages (e.g., during illegal moves).

After the game ends, there should be a screen displaying a short summary of the game and which player won.

The application must be implemented using the SFML GUI library.

Saving and loading the game should support operating on different files (with names specified by the user).

Grading criteria

CriteriaPoints
Code quality\(5\)
Correct game mechanics\(14\)
Saving and loading game state\(3\)
Clarity of error messages\(3\)
Support for playing with another player\(5\)
Support for playing against computer\(8\)
Displaying details of best saved games\(2\)

2D game

You are required to create a 2D game similar to The Binding of Isaac, Mario, Prince of Persia, or Castlevania. The game must offer a wide range of player interactions with the map, such as navigating challenging terrain (jumping, crawling, etc.) and engaging in combat with spawning enemies.

The theme, objectives, map interaction methods, and additional mechanics are left to individual student preferences. However, the game must support a hierarchy of elements with which the player interacts.

For example, if enemies appear on the map, there must be some hierarchy among them (e.g., regular enemy, flying enemy, boss, etc.). Another example could involve crafting new weapons — players might find elements on the map that can be combined to create better equipment.

The game must also support saving and loading. Checkpoints or saving at any time can be implemented. Saving and loading should work with different files (with names specified by the user).

Grading criteria

CriteriaPoints
Code quality\(5\)
Complexity and vastness of the world map\(7\)
Complexity of interactive elements / game mechanics\(10\)
Character / equipment development and modification\(8\)
Saving and loading the game\(5\)
“Freedom” of choices and actions\(5\)

Monkey typer

You are required to create a typing exercise game similar to Monkey Typer. The game involves words or phrases moving across the screen from one side to another. The user’s goal is to type the appearing words to make them disappear. If a word isn’t typed (i.e., the user fails to remove it), it moves to the other side of the screen. When multiple words move across without being typed, the game ends.

A good example of a similar game is the demonstration of the WSpeed program (presentation starts from timestamp 1:29).

It is suggested that the game should be diversified and offer a wider range of configurability, such as:

  • Supporting different fonts.
  • Supporting (or automatically adjusting) different speeds of word appearance and movement.
  • Supporting various settings for word sizes.
  • Supporting highlighting of typed fragments in words on the screen.
  • Supporting keyboard shortcuts for quick configuration changes.

Warning: To this project you are also required to supply an additional file with the words database, which will be read by the application after the user starts it. It is forbidden to store the words directly in the source code.

Grading criteria

CriteriaPoints
Code quality\(5\)
Word generation and animation, and their influence on the score\(10\)
Removing words by typing\(5\)
Additional configurability options\(16\)
Saving and loading game\(3\)
List of best scores\(1\)

Image steganography

The project involves creating a console application for writing and reading secret messages from computer images. The tool should modify standard graphic files (such as .png or .bmp), which at the same time is supposed to serve as a medium for reading such messages.

Supported operations include: writing a secret message into an image, reading a secret message from an image, and determining whether a given message can be written/read from a specific file.

The application should be run from the command line and, based on passed flags, modify, read, or provide information about image files.

Warning: In this project’s implementation, the usage of the SFML library is banned.

Implementation

The steganography implementation method for this project involves modifying individual image components. Students can choose from popular image formats like .ppm, .jpg, or .bmp, but must select at least two. Supporting fewer extensions will be equivalent to failing the project.

Additionally, formats must be supported by leading operating systems without installing additional tools. This means that proprietary or unsupported file formats will be disqualified (unless they are additionally supported — beyond the required ones).

Modification may (but does not have to) involve changing the last bit of each pixel in a binary map (for files representing an image as mentioned above) — this way, the image will be slightly altered (preferably imperceptibly to the human eye), and the message being saved can be long (depending on the image size — FullHD images have a lot of such bits).

For more sophisticated formats (e.g., those involving frames of variable length), the implementation approach is arbitrary. However, it should be optimized for minimal visible changes in the image. Trivial solutions are prohibited, such as saving the entire message in the comment section of the file. The message should be difficult to find for someone who doesn’t know how to look for it.

If it’s not clear what is meant by this, please consult your tutor.

Note that some image storage forms are very complicated (e.g., the .jpg or .gif extension) and there is no simple way to modify them without external libraries. Therefore, it is recommended to identify simpler formats (e.g., .png, .ppm, or .bmp). Any doubts should be discussed with the course instructor.

Functional requirements

The application should handle passed command-line arguments consisting of flags and data associated with these flags. A flag is text starting with a hyphen followed by an operation shortcut or two hyphens and the full name of that operation. The program is expected to support the following set of operations when launched with a flag:

  • -i assumes that a file path will be specified next. The program should check if the path leads to a file in a supported format. For example, if the application supports modifying .png and .jpg files, and a path with the extension .gif or .txt is provided, the program should display an appropriate error message. When a path to a supported format file is provided, the application should display information about the format and the file itself, such as image size, memory usage, and the timestamp of its last modification.
  • -e assumes that a file path and a message will be specified next. The message should be enclosed in quotes (to be treated as a single command-line argument). The program should open the image and write the specified message into it. Similar to -i, proper error handling is required if the path leads to an unsupported file type.
  • -d assumes that a file path from which we want to read a message will be specified next. Similar to other flag cases, proper error handling is required.
  • -c assumes that a file path and a message will be specified next. The flag should check if a message could be saved in the given file or if a hidden message could exist. A potential issue could be a file size too small (the image is too small to write a long message into it).
  • -h, after which no arguments are expected. This flag should print information about the program, the image file extensions supported by the program, usage instructions, and the specification of other flags on standard output (usually console).

Running the program without specifying any flags is equivalent to running it with the -h flag. Running the program with an unsupported (unknown) flag should result in an appropriate error display and a suggestion to use the -h flag. The same applies to using flags with incorrect arguments. Excessive arguments (e.g., providing 5 arguments after -h or -i) should be treated as an error.

For every operation involving file interaction (read / write), it should be checked whether the application has sufficient permissions for such a command. In case the operation cannot be completed, an appropriate error message should be issued.

Additionally, handle aliases for flags as specified in the table below.

Flag nameFlag Alias
-i–info
-e–encrypt
-d–decrypt
-c–check
-h–help

Implementation notes

The use of any programming library other than the standard (std) is prohibited without prior consultation with the course instructor. Exceptions include:

  • {fmt} library
  • SFML library (banned for the Image steganography topic)

Each project must be configured using CMake. When submitting the project, only header files, implementation files, and CMakeLists.txt should be provided (these files can be organized into folders for convenience). Dependencies on other libraries should rely on the FetchContent() command.

For projects that rely on GUI, if a student chooses to load textures or fonts from a file, they should not be included in the same .zip file. Textures or fonts should be provided in a separately packed .zip file

It’s important not to include files/folders containing environmental configuration (e.g., .idea) or compiled libraries/applications (e.g., cmake-build-debug). This also applies to the .git folder if someone uses version control with Git. It’s suggested to ensure that file explorers correctly display hidden files to avoid missing any.

Additional information

Video requirement

It is necessary to provide a video recording that presents how the finished application works. This video should only contain a presentation of the running application. It should feature no code and no explanations. It is not required for the video to contain sound (usually adding commentary leads to unnecessarily long videos). The video should include all the supported features of the finished projects. It should be at most 3 minutes long.

Please remember that the video must be sent as a separate file, i.e. not included in the project archive.

Examples of project implementation approaches

Given the relatively extensive and complex rules for project submissions, here are a few examples of how to package (and which) files (in each case, it is also necessary to include the video file):

Example 1

A student chose the Database topic. They wrote all the code in a single main.cpp file. Therefore, they should send a .zip archive containing only main.cpp and CMakeLists.txt.

Example 2

A student chose the Database topic. They organized the code into multiple folders, where subfolders contain .hpp and .cpp files. Therefore, they should send a .zip archive containing all these folders with their contents and CMakeLists.txt.

Example 3

A student chose the Database topic. They split the code into several .cpp and .hpp files but did not create additional folders. Therefore, they should send:

  • A .zip archive containing header and implementation files and CMakeLists.txt

Example 4

A student chose the Hexxagon topic. They organized the code into several folders containing implementation and header files and an additional folder containing textures. Therefore, they should:

  1. Remove all textures from the dedicated folder (but not delete the folder itself).
  2. Place all textures in a separate .zip file with the same name as the main project .zip, but with an additional - assets suffix.
  3. Package the folders containing code files and CMakeLists.txt into a .zip archive.
  4. Submit:
    • .zip with textures;
    • .zip with code;

Example 5

A student chose the 2D game topic. They wrote the code in a single main.cpp file. They don’t use textures but create graphics using code alone. Therefore, they should send a .zip containing main.cpp and CMakeLists.txt.

Naming of .zip archives

The source code of projects must be packed into a .zip archive, which must:

  • Have an appropriate name following the template 2425S_XY_s#####_ZV, where:
    • XY denotes the exercise group, e.g., 12 or 31;
    • s##### denotes the student’s index number, e.g. s17137;
    • ZV denotes the initials of the course instructor, e.g. MS, AS, or FK.
  • Contain only:
    • .cpp files created by the student;
    • .h (or .hpp) files created by the student;
    • file CMakeLists.txt;
    • Folders where the above files may be located. In summary, remove any generated elements (especially the cmake-build-debug or .idea folder) from the project folder, except for CMakeLists.txt and main.cpp.

Additionally, it is required to include the video recording.

If in doubt, consult the project structure correctness with the course instructor.

Failure to meet any of the above two project structure conditions in any way will result in a deduction of 5 points from the final project score.

macOS system and .zip files

When creating .zip archives on macOS, the system automatically adds a hidden folder __MACOSX. Users of these systems should unpack the created archive on a different operating system and remove this folder.

Alternatively, the issue can be resolved with the command zip -d ArchiveName.zip __MACOSX/\*.
