Constraining template substitution

At the beginning of this chapter, we have introduced an example where we wanted to print the contents of a vector. We create our own set of overloads called print(), which we later replaced with a single template. Let’s inspect it once more:

While {fmt}, under the hood, employs many auxiliary tools and achieves that goal in a completely different way compared to the one we will demonstrate, it would still be a good idea to show how can we use a single template to print both std::vector and std::set objects. In our example, we will be printing them in the same way (despite {fmt} printing them slightly differently — as seen above).

We will achieve this by accepting anything and assuming that it is a range:

This time, the error message is fairly useful. It claims that we are redefining template<class Object> void print(const Object&), whose first declaration was template<class Container> void print(const Container&).

Correct — after all, the parameter names don’t play much of a role for the compiler. We did not introduce any overloads, because we can’t overload on parameter names in C++. Both print()s are nothing more than a template that accepts a single template parameter and a single parameter of the deduced type.

What should we do then? Can we combine overloading and templates?

Of course, we can. But if we aim for the overloads to support the same signatures, we need to constrain the substitution of either of them to a subset of types.

Huh..?

Being more straightforward — we need to somehow instruct the compiler to use the first print() only if the deduced type satisfies certain criteria, e.g., is a range (we could use a range-based loop on it). Otherwise it should use the other, “more generic” template.

You can do that?

Yes. We need to use Concepts.

Concepts

Concepts is a C++20 language feature that allows the programmer to constrain a template to a certain subset of types. In order to achieve our goal from the previous part of this article, we could introduce one, small change:

#include <iostream>
#include <ranges> // std::ranges::range
#include <vector>

template <std::ranges::range Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

template <typename Object>
auto print(Object const& object) -> void {
    std::cout << object << '\n';
}

auto main() -> int {
    auto const vec = std::vector<int>{2, 1};
    auto const num = 37;

    print(vec);
    print(num);
}

The code has changed only in two lines — it was very easy to miss it. Those were:

  1. We added #include <ranges> to use std::ranges::range.
  2. Instead of typename Container in the first template we wrote std::ranges::range Container.

Yes, that is enough! Now, the first print() will be chosen only if in the print(arg) call, the arg argument will _satisfy the std::ranges::range Concept, i.e., it will be a range. However, if that is not the case, the second print() implementation will be chosen.

All right, nice, but what exactly is a Concept? How exactly it checks if a given argument is a range? Can we create our own Concepts? What if I want my type to satisfy more than one of them? How exactly is std::ranges::range used in the print() template?

Excellent questions! Let’s address them one by one.

What are Concepts?

A Concept is a special language feature, which aims to test types. We can test any types — int, double, bool, std::vector<int>, std::string, etc. A Concept will tell us whether a given type, which is being tested, satisfies certain criteria.

In order to check if a given type satisfies a Concept, it is sufficient to supply it to the template arguments of that Concept and capture the resulting bool:

#include <ranges>
#include <set>
#include <string>
#include <vector>

#include <fmt/base.h>

auto main() -> int {
    fmt::println("vector is a range? {}", std::ranges::range<std::vector<int>>);
    fmt::println("set is a range?    {}", std::ranges::range<std::set<int>>);
    fmt::println("string is a range? {}", std::ranges::range<std::string>);
    fmt::println("int is a range?    {}", std::ranges::range<int>);
    fmt::println("double is a range? {}", std::ranges::range<double>);
}

How exactly a Concept checks if a given argument satisfies certain criteria?

Sticking with the std::ranges::range example, it would worth it to inspect how is it implemented:

1
2
3
4
5

template< class T >
concept range = requires( T& t ) {
    ranges::begin(t);
    ranges::end  (t);
};

The above definition should be read as follows: the range Concept is satisfied if, given a (raw / non-const) reference to any type, we can call std::ranges::begin() and std::ranges::end() functions with a reference of that type.

Of course, both std::ranges::begin() and std::ranges::end() have their own constraints to satisfy, but it wouldn’t be productive to try and deep dive into such details. In this case it is enough to know that std::ranges::range is satisfied if a given type supports extracting begin() and end() from it.

To better understand what kinds of constraints a Concept can require, let us create our own one.

Creating your own Concepts

To create your own Concept, we need to use the template syntax paired with the concept and requires keywords:

What if we want a given type to satisfy more than once Concept?

If we create a template, and we wish to constrain it, there is more than one way to achieve it. Considering the print() example:

1
2
3
4
5
6
7

template <std::ranges::range Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

The equivalent alternative would be:

1
2
3
4
5
6
7
8

template <typename Container>
requires std::ranges::range<Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

It means that instead of replacing typename with a Concept, we can employ the additional requires clause, which requires that Container satisfies the std::ranges::range Concept.

Of course, we can always create our own Concepts that combine some other, preexisting ones, but sometimes it isn’t worth it. Instead, we can use boolean expressions in requires:

1
2
3
4
5
6
7
8

template <typename Container>
requires std::ranges::range<Container> && HasSize<Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

This way enables us to specify that Container must both be a range and supply the .size() method.

#include <iostream>
#include <ranges>
#include <vector>

template <std::ranges::range Container>
auto print(Container const& container) -> void {
    for (auto const& element : container) {
        std::cout << element << ' ';
    }
    std::cout << '\n';
}

template <typename Object>
auto print(Object const& object) -> void {
    std::cout << object << '\n';
}

auto main() -> int {
    auto const vec = std::vector<int>{2, 1};
    auto const num = 37;

    print(vec);
    print(num);
}

We already know how it works. The first call (print(vec)) will use the first (restricted by Concept) template, and the second (print(num)) will use the second (unrestricted) template.

Everything seems to make sense, but some may still be unsatisfied — how is the compiler supposed to know to ignore the second template when called with a vector?

On one hand, this might seem obvious — after all, that template won’t compile. However, this is not a sufficient explanation. Whether or not some code inside a template compiles does not inherently disqualify the template from being considered when selecting the appropriate implementation.

The key factor here is greater specialization or greater restriction. If a call (e.g., print(vec)) matches more than one template, the more restricted (but still matching!) template will be chosen.
