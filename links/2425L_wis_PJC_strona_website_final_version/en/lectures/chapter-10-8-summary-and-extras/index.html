Chapter 10.8 - Summary and extras

Posted May 7, 2025
By Filip Kwiatkowski
5 min read

Storing objects of different types within a polymorphic hierarchy in a single container requires the use of pointers

Storing objects of different types within the same collection is typically accomplished through inheritance. Such a collection of base type, filled with derived type objects, is sometimes referred to as a polymorphic container.

The issue with creating base type containers and adding derived type objects to them is object slicing. Containers store objects within them, and consequently, they must precisely know the type of their elements. When we call .push_back(someDerivedTypeObject) on a std::vector<BaseType>, we encounter object slicing.

The solution to this problem is references, but unfortunately, containers of references cannot be created (problems with the reference not being a full-fledged object, issues with lack of initialization, etc.). We need a reference that can be unconnected and later “reconnected” to something else. Such a reference is a pointer. Therefore, when we want to create a container that holds objects belonging to a polymorphic hierarchy, we should use pointers to the base class as the type of elements in that container.

Pointers facilitate dynamic memory allocation

When we want to allocate some amount of memory that is not known at compile time, we need to request it from the operating system. Typically, this is done using the new or new[] operators, which return a pointer (the array version also returns a pointer to a single element — there it points to the first element of the array). This means that using pointers is necessary when creating containers.

Objects with dynamic lifetimes are not automatically destroyed

When we create a local object with automatic lifetime, for example, by using the syntax:

1

auto obj = SomeType();

It will be destroyed upon leaving the block in which it was created. The destruction of an object means calling its destructor and releasing the memory it occupied.

Objects with dynamic lifetimes are not automatically destroyed. This means that creating such an object like this:

1

auto objPtr = new SomeType();

Will allocate an object of type SomeType somewhere on the heap. The objPtr object, being a pointer, is itself an object with automatic lifetime. It will be destroyed upon leaving the block in which it was created. However, destroying the pointer to the object does not destroy the object it was pointing to.

Effectively, in the above example (with new), two objects are created:

  • objPtr — a local pointer with automatic lifetime;
  • a dynamically allocated object of type SomeType with a dynamic lifetime.

If we don’t call delete on the pointer to the second object, that object will exist until the program terminates. This situation is called memory leak and should always be avoided.

new[] + delete[] and new + delete

C++ requires us to release memory allocated through “array-new” (i.e., new[]) with delete[]. Regular new-allocated memory should be released with regular delete.

Pointer serves as an implementation of the iterator concept

A pointer is the most primitive iterator, at least historically. It allows access to the pointed-to element through dereferencing (*somePtr) and enables “movement” through data, e.g., via ++, --, +=, or -=.

Effectively, it is a reference that can point to nothing (nullptr) and can be “re-pointed” to other objects.

A virtual destructor is necessary when deleting a derived type object through a pointer to the base type

The issue is quite straightforward. Having:

1

BaseType* ptr = new DerivedType();

When we delete this object like this:

1

delete ptr;

And BaseType does not have a virtual destructor, only the destructor from BaseType is called, and the destructor from DerivedType is not. In such a case, destructors in this hierarchy should be “virtualized” by adding something like this to BaseType:

1

virtual ~BaseType() = default;

Stack and heap

Stack and heap are terms that denote segments of the program’s operational memory. Locally created objects (with automatic lifetime) are placed on the stack, while objects with dynamic lifetimes reside on the heap.

Pointer to pointer

A pointer is nothing “special” (unlike references, for example). It can be treated like an ordinary type. This means that a pointer to a pointer can be created. For example, when querying where our local objects live:

#include <fmt/format.h>

auto main() -> int {
    using fmt::ptr;

    auto localInt = 2137;

    fmt::println(
        "localInt has value {} and is located at: {}", localInt, ptr(&localInt)
    );

    auto ptrToLocalInt = &localInt;

    fmt::println(
        "localInt has value {} and is located at: {}", localInt, ptr(ptrToLocalInt)
    );
}

We can start to wonder:

Since localInt is a local variable of type int, then ptrToLocalInt is also a local variable, but of a different type (int*). Does it “exist” somewhere too? Can we see the address of this variable that stores the address of another variable?

auto main() -> int {

    auto ptrToLocalInt = &localInt;

    fmt::println("ptrToLocalInt: {}", ptr(ptrToLocalInt));
    fmt::println("&ptrToLocalInt: {}", ptr(&ptrToLocalInt));
}

this is a pointer

In Java, we use the this.field syntax to access the field called field. It is useful when we encounter a name conflict, e.g., in a constructor:

public class Student {
    private String name;
    
    public Student(String name) {
        this.name = name; // here
    }
}

In C++ we would use the this->field syntax, because this is a pointer, not a reference1.

The sole example of a constructor does not illustrate a great usage of this keyword in C++, because in this language you can use a member initializer list”
