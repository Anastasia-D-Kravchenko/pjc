Chapter 8.2 - The Big Three and const

Posted Apr 24, 2025
By Filip Kwiatkowski
13 min read

Value semantics

As we already know, in the C++ language, we deal with value semantics. This means that variables we use actually represent objects we work with, rather than just references to them (as in Java, for example). When we pass an object to a function, a full-fledged, “deep” copy of it is created. Of course, we can control this behavior by defining reference types. Nevertheless, it cannot be denied that the processes governing the object’s lifecycle (such as construction, copying, assignment, or destruction) are incredibly important elements of C++ application operation.

The C++ language provides us with tools to control all these behaviors. From Java, we already know the constructor, which is a special method executed when an object is created. However, we have three other tools that together form the so-called Big Three — copy constructor, assignment operator, and destructor.

Constructor

Constructors in C++ seemingly work the same as in Java. They are executed when an object is created. They can even have the same form as in Java:

#include <string>

class Student {
    std::string name;
    std::string surname;
    
public:
    Student(std::string const& n, std::string const& s) {
        name = n;
        surname = s;
    }
};

This constructor, however, has a drawback — instad of initializing the name and surname fields, it constructs them in their “default” state, and then it overwrites them based on the supplied arguments.

But… what’s the difference?

Excellent question. Let’s look at the following code:

auto main() -> int {
    auto x = int();
    x = 10;
    
    auto y = 10;
}

How do the operations performed on x and y differ? Maybe it will be more apparent if we write 0 instead of int:

1
2
3
4
5
6

auto main() -> int {
    auto x = 0;
    x = 10;

    auto y = 10;
}

You can clearly see the difference now. In the case of the variable x, it is created with the default value 0, and then we overwrite it with the value 10. In the case of the variable y, we perform fewer operations because we immediately assign (initialize) the value 10 to it.

But how does this relate to class fields and what the constructor does with them?

Well, class fields are created before we enter the body (block) of the constructor. This means that when our constructor looks like this:

1
2
3
4

Student(std::string const& n, std::string const& s) {
    name = n;
    surname = s;
}

Then before we reach the operation name = n, the field name already exists. This means it had to be created. How? By using the default constructor of the std::string type. Later we overwrote this default value with the contents of n.

Ok, so how do we fix this to avoid unnecessary default initializations?

Use a member initializer list.

Member initializer list

Initializing directly to the intended value is usually better than default initialization followed by later overwriting. To initialize class fields using a constructor, you should use the following syntax:

1

class Student {
    std::string name;
    std::string surname;

public:
    Student(std::string const& n, std::string const& s) 
            : name(n), surname(s) { }
};

It looks a bit strange, but it doesn’t introduce any complicated philosophy. Between the constructor parameter list and its body, a colon (:) is placed, followed by a list of fields along with their respective initializations.

It’s worth noting that this is the only way to create an object that has fields of reference type:

We know that a reference must be initialized, and since the member initializer list is the only way to initialize a field (instead of its default initialization followed by overwriting), a field of reference type forces us to use this list.

Copy constructor

The copy constructor is executed when we copy a given object. For example, considering objects of type std::vector<int>:

1
2
3

13

#include <vector>

auto byCopy(std::vector<int> v) -> void { }
auto byReference(std::vector<int> const& v) -> void { }

auto main() -> int {
    auto vec = std::vector<int>{1, 2, 3};
    auto v2 = vec;
    auto v3 = vec;
    v2 = v3;
    byCopy(vec);
    byReference(vec);
}

Let’s briefly discuss each line of the main() function:

  • auto vec = std::vector<int>{1, 2, 3}; — Here we are calling a constructor, but not a copy constructor. We’re not copying anything here. We’re simply creating vec based on three literals.
  • auto v2 = vec; — Here we’re using the copy constructor. We’re creating v2 and want it to contain the same elements as vec.
  • auto v3 = vec; — Same situation as above.
  • v2 = v3; — Here we’re not calling any constructor. No vector is being created. We’re overwriting the content of v2 with the content of v3 (which doesn’t make sense by itself — it’s just an example).
  • byCopy(vec); — Here the parameter v is a copy of the argument vec, so the copy constructor is called.
  • byReference(vec); — Here no constructor is called. The parameter v being created is a reference to the original vector vec passed by the argument.

Now let’s present how you can implement a copy constructor. After all, it controls the behavior of object copying, which in C++ is undoubtedly a crucial process:

class Student {
    std::string name;
    std::string surname;

public:
    // constructor
    Student(std::string const& n, std::string const& s)
            : name(n), surname(s) { }
            
    // copy constructor
    Student(Student const& other)
            : name(other.name), surname(other.surname) { }
};

The copy constructor, as seen in line 11, is responsible for defining the behavior of the copying process. It’s natural that when we copy an object of type Student, the newly created object should be assigned the same first and last name as those found in the object we’re copying from.

The parameter other is precisely that “original” object being copied. The new object (copy) is the one for which we’re calling the copy constructor.

class Student {

Manual definition of this constructor and performing complex operations on it occur relatively rarely — we’ll show where (and how) it makes sense in the future — when manually managing resources.

Assignment Operator

In one of the previous examples, we saw that auto x = y and x = y are not the same. The former is a copy, and the latter is an assignment. We can also control assignment, but it touches on the topic of operator overloading, which we’ll cover in the next part of this chapter.

Destructor

In C++, we deal with a very interesting phenomenon — a so-called deterministic destruction.

From Java, we remember that the tool called Garbage Collector takes care of cleaning up unused memory. It periodically scans the memory area occupied by our Java process in search of fragments that we no longer use.

But sometimes, an important question arises — when?

It’s very difficult to answer that question. Effectively, it’s not really possible to control the Garbage Collector from within the application itself. Of course, one can implement their own garbage collector, but its operating principle practically ensures that it won’t run immediately when we stop needing some fragment of memory. We occupy memory that we don’t need for some time.

Resource management in C++ works a bit differently. There’s no Garbage Collector — we have precisely defined processes that release the resources used by the application at precisely defined moments (not only memory but also close open files or network connections).

All this goodness is made possible thanks to destructors. You can think of them as the opposites of constructors.

A constructor is automatically executed when an object is created, and a destructor is automatically executed when an object dies.

The declaration (and definition) of a destructor is very similar to the declaration (and definition) of a constructor — preceded by the tilde character, ~:

#include <fmt/format.h>

struct Point {
    int x = 0;
    int y = 0;

    Point(int const x, int const y) : x(x), y(y) {
        fmt::println("Created Point({}, {})", x, y);
    }

    ~Point() {
        fmt::println("Destroyed Point({}, {})", x, y);
    }
};

auto main() -> int {
    auto p1 = Point(1, 2);
    auto p2 = Point(2, 3);
    auto p3 = Point(4, 5);
}

This code will create three points, and then it will move to the closing brace of the main() block, resulting in the destruction of objects p1, p2, and p3. Formally, this refers to the end of the lifetime of these objects.

It’s worth noting the order of destructor calls in relation to the order of object creation:

Within the same block, objects with automatic storage duration (which includes all the ones we’ve discussed so far) are destroyed in the reverse order of their creation.

The above output can be easily explained by analyzing the code line by line:

  1. auto main() -> int { — We enter the main function. Its block is opened.
  2. auto p1 = Point(1, 2); — We create a point (Created Point(1, 2)).
  3. { — We enter a new block.
  4. auto p2 = Point(2, 3); — We create a point (Created Point(2, 3)).
  5. { — We enter a new block.
  6. auto p3 = Point(3, 4); — We create a point (Created Point(3, 4)).
  7. } — We exit the block in which p3 was created (Destroyed Point(3, 4)).
  8. auto p4 = Point(4, 5); — We create a point (Created Point(4, 5)).
  9. } — We exit the block where p2 and p4 were created (in that order), so the order of their destruction will be reversed — p4 “dies” first, then p2 (Destroyed Point(4, 5) and Destroyed Point(2, 3)).
  10. auto p5 = Point(5, 6); — We create a point (Created Point(5, 6)).
  11. } — We exit the block where p1 and p5 were created — p5 dies first, then p1 (Destroyed Point(5, 6) and Destroyed Point(1, 2)).

As you can see, the order of object creation and destruction does make some sense. Of course, in the above example, the constructor doesn’t need to display anything, and manually defining the destructor doesn’t bring any benefits (apart from demonstration through display).

The ability to control practically every aspect of an object’s lifecycle allows for very precise resource management. This will be incredibly useful in manual memory management scenarios.
