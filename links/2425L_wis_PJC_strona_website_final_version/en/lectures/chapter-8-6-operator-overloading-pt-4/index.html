General issues with operator overloading

So far, we have mainly discussed the advantages of operator overloading. It makes the code easier to read and interpret, provides more concise instructions, enhances consistency, etc.

However, operator overloading is not without its drawbacks. Apart from the relatively quirky syntax of its usage, we also encounter architectural problems. Let’s take a look at one of the examples we created during this chapter:

What does it really mean to add two vectors? At this point, it may seem obvious to us. It’s a concatenation (joining) — just like in the case of two std::strings.

However, if we were to ask someone educated solely in the field of mathematics what the operation v1 + v2 means, where v1 and v2 are vectors of integers, we would receive a completely different answer (very quickly):

We get a new vector whose elements are the sum of the elements of the original vectors at corresponding positions. ~ Colleague Mathematician (Physicist).

This means that in certain fields, adding two vectors is not:

A similar situation arises with operator overloading, although in this case, it goes “even further”.

We should overload operators only if what they do is immediately clear, intuitive, and unambiguous to the person reading the code.

Such code won’t compile. An error will occur, which isn’t worth citing. Its essence lies in the fact that std::ranges::sort() requires objects in the container being sorted to be compatible with std::ranges::less(). This, in turn, can only be performed on objects that satisfy the so-called std::totally_ordered_with concept. Generally, it requires the type to support all 6 relational operators (<, <=, >, >=, ==, !=).

    return right < left;

    return left > right or left == right;

    return !(left == right);

Three-Way comparison operator

The three-way comparison operator, <=>1, allows C++ to generate2 the discussed six relational operators. The rules for their creation (and overriding some of them) are quite complicated, but luckily, we neither need to know them nor worry about them, because in the end, the effect is — in most cases — the desired one.

To understand how it works exactly, it’s worth looking at a simpler example. First of all, let’s see that all relational operators work:

Which displays true true.

The whole magic lies, of course, in what <=> returns and why we’re comparing it to zero. At this point, it’s worth recalling the Comparable and Comparator interfaces from Java. They returned an int. Some positive value when the left argument was considered “greater” than the right one. Some negative value when the left argument was considered “smaller” than the right one. They returned 0 when both arguments were supposed to be considered “equal” (their .equals() for each other should return true).

operator<=> represents a similar logic. It returns something (more or less unspecified) that needs to be compared to zero afterwards:

Armed with this knowledge, we can now summarize what the line auto operator<=>(Person const& other) const = default; does:

Instructing C++ to create a default implementation of the <=> operator (using = default) results in creating an implementation that invokes <=> for each subsequent class field. When the result of such operation is something different than 0, that result is returned. Otherwise, the chain of such operations continues until there are no more fields. In such a situation, the result that compared to 0 yields true is returned.

The summary is a bit convoluted, so let’s implement operator<=> manually:

struct Person {
    std::string surname;
    std::string name;

    auto operator<=>(Person const& other) const -> auto {
        auto surnamesCompared = surname <=> other.surname;
        if (surnamesCompared != 0) return surnamesCompared;
        return name <=> other.name;
    }
};

The logic is quite simple. We check if the last names are different. We get “their difference” and store it in the variable surnamesCompared. If it is different from zero, we return this information. However, if they are not different, we return the difference in first names.

Let’s recall a certain problem we encountered earlier — the default (= default) generated operator<=> messed up the order because it compared first names first and then last names (because the first name was declared first in the class). By implementing this operator manually, we don’t have to worry about such things — we determine the logic of comparison.

The problem again lies with std::ranges::sort() and the unsatisfied std::totally_ordered_with. The reason?

If we manually define operator<=>, it doesn’t support automatic replacement of ==. Seriously…

Why?

Because there are cases where it would be suboptimal. For example, <=> for std::string or std::vector compares element by element, but == or != may introduce optimization and first check .size(). If they differ, they’re definitely different. The <=> operator doesn’t care about .size() because it can still compare objects lexicographically (in std::string, this means alphabetically) regardless of their sizes.

#include <algorithm>
#include <compare>
#include <string>
#include <vector>

#include <fmt/base.h>

struct Person {
    std::string name;
    std::string surname;

    auto operator<=>(Person const& other) const -> auto {
