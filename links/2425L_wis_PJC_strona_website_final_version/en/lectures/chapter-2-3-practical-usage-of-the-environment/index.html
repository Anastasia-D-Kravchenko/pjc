At this point, one frustrating aspect of the C++ language is the inability to conveniently display the contents of a container (unless it’s a std::string, which is an exception for obvious reasons). The following code will not compile:

  3. someone has already done it.

CMake

There has been some discussion about CMake in the introduction to C++ chapter. It’s a tool for automating the build process, especially for C++ projects. One of its major advantages is its popularity and widespread adoption.

For those familiar with Maven in Java, you can think of CMake as the C++ counterpart to Maven.

One of Maven’s major advantages is its ability to fetch and configure external dependencies, such as libraries that help developers achieve their goals more efficiently.

Fetching and Configuring External Dependencies

Pre-built libraries offer several advantages:

  • Time-saving: Instead of spending time and effort creating a tool from scratch, you can use a pre-built library developed by someone else.
  • Well-thought-out architecture: When creating a new tool, it’s easy to overlook small details that may become problematic later. With a widely used library, users contribute suggestions for improvements, enhancing its robustness.
  • Testing: The popularity of a library and the number of users contribute to its reliability.

Therefore, it’s valuable to know at least one method of integrating external libraries into C++ projects.

FetchContent commands

So far, our CMakeLists.txt file looked something like this:

1
2
3
4
5
6

cmake_minimum_required(VERSION 3.26)
project(PJC)

set(CMAKE_CXX_STANDARD 20)

add_executable(Main main.cpp)

To recap:

  • The cmake_minimum_required() command with the VERSION argument specifies the minimum CMake version required. In this example, it’s version 3.26, but if that version is slightly different from your custom configuration, it won’t be a problem — it will be sufficient to simply change it according to the message from a potential error.
  • The project() command specifies the project name, which can be used later (not relevant for us at the moment).
  • The set() command with the CMAKE_CXX_STANDARD argument sets the C++ language version of our project to C++20, as specified by 20.
  • The add_executable() command creates an executable file (.exe on Windows or a runnable file on Unix-based systems). In this case, it creates a file named Main (.exe) based on the C++ code file named main.cpp.

The fmt library, mentioned earlier, was written with CMake configuration and published on GitHub. This means that with a very simple command from the FetchContent family, we’ll be able to download and include it in our project.

To use FetchContent, we need to include it in our file using the include() command. It works similarly to the #include directive in C++:

1
2
3

cmake_minimum_required(VERSION 3.26)
project(PJC)

set(CMAKE_CXX_STANDARD 20)

include(FetchContent)   # here

add_executable(Main main.cpp)

Then, we’ll use three commands:

  1. FetchContent_Declare()
  2. FetchContent_MakeAvailable()
  3. target_link_libraries()

FetchContent_Declare() specifies what and from where we want to download. In this case, it’s the fmt library fetched from the GitHub link, version 11.0.2.

To enable FetchContent to download dependencies from a GitHub repository, you need to have Git installed on your computer.

FetchContent_MakeAvailable() downloads and builds the specified dependency (the fmt library in the specified version) declared by FetchContent_Declare().

target_link_libraries() connects (links) the built library to our executable file created by add_executable().

The final CMakeLists.txt looks like this:

cmake_minimum_required(VERSION 3.26)

include(FetchContent)

FetchContent_Declare(
        fmt
        GIT_REPOSITORY  https://github.com/fmtlib/fmt
        GIT_TAG         11.0.2
)

FetchContent_MakeAvailable(fmt)

add_executable(Main main.cpp)
target_link_libraries(Main fmt)

The order of commands is very important. We cannot use FetchContent_XYZ() before include(FetchContent). We cannot build the library with FetchContent_MakeAvailable() without declaring what to build with FetchContent_Declare(). We cannot link the built library with target_link_libraries() without building it and creating a target (representing something built by our project—in our case, the executable file Main).

After modifying the CMakeLists.txt file, changes may not be visible in the project. This happens when the programmer forgets to reload the changes. In the top-right corner of the IDE (looking at the CMakeLists.txt file), there should be a message suggesting to reload the changes with the appropriate button. Alternatively, you can use the keyboard shortcut Ctrl+Shift+O.

With this configuration, the library {fmt} should be fetched, built, and prepared for use with our project.

The {fmt} library

It’s worth noting two important facts:

  • Instead of including the <iostream> header, we include the <fmt/ranges.h> header. Of course, if we need std::cin for input (which {fmt} does not replace), we would still need to keep the #include <iostream> directive.
  • The {fmt} library formats std::vector in a visually pleasing way. It encloses it in square brackets and separates the elements with commas and spaces.

It’s also worth mentioning why the {fmt} header looks like a path to the ranges.h file in the fmt folder. Effectively, that’s exactly what it is.

The {fmt} library consists of multiple files that we can include using the #include directive depending on what we need. The ranges.h file offers formatting for various ranges, but if we’re interested only in the basic output of simple data types (primitives, std::string, etc.), including the base.h file is sufficient (which is located in fmt, so the full directive would look like this: #include <fmt/base.h>).

On one hand, this is a plus (because sets are conventionally represented with curly braces in mathematical notation, e.g., $ {1,2,3} $), but on the other hand, a programmer might want to control this behavior, for example, by applying the same formatting rules for sets and vectors.

According to the information available in the documentation of the library, to format std::set the same way as std::vector, we can use fmt::join(), which can format any object that can be iterated over:

#include <set>
#include <vector>

#include <fmt/ranges.h>

auto main() -> int {
    auto vector = std::vector<int>{1, 2, 3};
    auto set    = std::set<int>{1, 2, 3};

    fmt::println("{}", vector);
    fmt::println("[{}]", fmt::join(set, ", "));
}

To understand what’s happening here, we need to learn what {} specifically means in {fmt}.

{} is a placeholder. fmt::println() will display whatever is placed in the text passed as an argument:

1
2
3
4
5

#include <fmt/base.h>

auto main() -> int {
    fmt::println("Hello World");
}

1

Hello World

However, if {} is found in the text, {fmt} will look for the next argument to format appropriately. Referring to their documentation, for example:

1
2
3
4
5

#include <fmt/base.h>

auto main() -> int {
    fmt::println("The answer is {}", 42);
}

1

The answer is 42

It’s a very extensive and user-friendly library that we will gradually explore.

From now on, all examples involving text output will use the {fmt} library.

Let’s go back to the example. How is it that fmt::println("[{}]", fmt::join(set, ", ")) for a set containing data 1 2 3 displays [1, 2, 3]?

The key is the combination of the fact that when {} is replaced by the formatting fmt::join(set, ", "), the text 1, 2, 3 will be “inserted” there for the given data. So where did the square brackets come from?

They enclose the {} placeholder in the original text — fmt::println("[{}]", ...). When we display the text "[{}]", anything replacing {} will be surrounded by square brackets.

Certainly, using {fmt} requires more learning from us, but once we get to know this library well, we can create code that is definitely more concise, readable, and often faster. All pros!

Common mistakes when using {fmt}

A common mistake when using {fmt} is attempting to display a single value without using text with placeholders, for example:

1
2
3
4
5
6

#include <fmt/base.h>

auto main() -> int {
    auto x = 5;
    fmt::println(x);
}

This code will not compile.

In such cases, you always need to add text with {} in this way:

1
2
3
4
5
6

#include <fmt/base.h>

auto main() -> int {
    auto x = 5;
    fmt::println("{}", x);
}

A slightly less critical mistake is unnecessarily repeating the fmt::println() or fmt::print() functions when trying to display multiple objects in a specific way. For example, this code:

#include <fmt/base.h>

auto main() -> int {
    auto x = 1;
    auto y = 2;
    auto z = 3;

    fmt::print("{} ", x);
    fmt::print("{} ", y);
    fmt::print("{}\n", z);
}

Can be replaced with this:

1
2
3
4

#include <fmt/base.h>

auto main() -> int {
    auto x = 1;
    auto y = 2;
    auto z = 3;

    fmt::println("{} {} {}", x, y, z);
}

It displays exactly the same, which is 1 2 3.
