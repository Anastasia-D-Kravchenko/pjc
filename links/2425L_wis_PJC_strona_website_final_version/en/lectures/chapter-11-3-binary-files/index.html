Binary and text files

We use text files when we want to save data that can later be read or modified by users using text editors (such as Notepad). We use binary files when we want to save data from a program without the subsequent need to interpret them as text. Let’s first look at an example where we achieve the same effect using both text and binary files:

Writing a single int to a text file

Writing an int to a file is very simple. It has already been discussed as part of the subject:

#include <fstream>

#include <fmt/base.h>
#include <fmt/ostream.h>

auto main() -> int {
    auto someInt = 1337;

    {
        auto file = std::fstream("data.txt", std::ios::out);
        fmt::println(file, "{}", someInt);
    }

    someInt = 0;    // resetting the value

    {
        auto file = std::fstream("data.txt", std::ios::in);
        file >> someInt;
    }

    fmt::println("{}", someInt);
}

Thanks to the inner blocks ({ … }) used here and thanks to the std::fstream’s destructors, appropriate files are always correctly closed.

#include <fstream>

#include <fmt/base.h>

auto main() -> int {
    auto someInt = 1337;

    {
        auto file = std::fstream(
            "data.bin", std::ios::out | std::ios::binary
        );
        file.write(reinterpret_cast<char const*>(&someInt), sizeof(int));
    }

    someInt = 0;    // resetting the value

    {
        auto file = std::fstream(
            "data.bin", std::ios::in | std::ios::binary
        );
        file.read(reinterpret_cast<char*>(&someInt), sizeof(int));
    }

    fmt::println("{}", someInt);
}

As you can see, both code fragments have the same structure — we create an std::fstream, write data to the file, close the connection, and finally create another std::fstream to read data from the file.

The differences are minimal. Let’s list all of them:

Text OperationsBinary Operations
Just std::ios::in and std::ios::out flagsAdditional std::ios::binary flag required
Write using {fmt} and read using stream operationsWrite and read using dedicated methods and pointers
Use the .txt extensionUse the .bin extension

The last difference doesn’t actually matter. It’s just a convention that .txt denotes text and .bin denotes binary data. There’s nothing preventing us from writing binary data to .txt or text data to .bin. However, in such cases, a user might expect to open a .txt file in a text editor like Notepad. They’d be surprised to see binary data.

The text version should be relatively understandable. Let’s examine the new binary operations, specifically the lines:

  1. file.write(reinterpret_cast<char const*>(&someInt), sizeof(int))
  2. file.read(reinterpret_cast<char*>(&someInt), sizeof(int))

The methods .write() and .read() are quite simple, although they don’t look like it. They expect a pointer to data and the number of bytes that will:

  1. Be written to the file.
  2. Be overwritten by the data read from the file.

In other words:

  • file.write(reinterpret_cast<char const*>(&someInt), sizeof(int)):
    • file.write(…) — write to the file…
    • …the data starting at reinterpret_cast<char const*>(&someInt)…
    • …and stop after writing sizeof(int) bytes.
  • file.read(reinterpret_cast<char*>(&someInt), sizeof(int)):
    • file.read(…) — read data from the file…
    • …and paste it into (reinterpret_cast<char*>(&someInt)…
    • …but stop after reading and pasting sizeof(int) bytes.

Okay, but what in Odin’s name is reinterpret_cast<char const*>(&someInt)?! And why isn’t there const in the second example?

That’s quite an uncomfortable question, not because it’s difficult, but because it’s hard not to ask “seriously..?” after explaining this bit.

So, the idea of writing and reading binary data is relatively straightforward — we provide a pointer to memory and specify how many bytes need to be written/read. The problem is that &someInt is a pointer to an int. As we’ve seen, an int occupies 4 bytes. Such an std::fstream, using pointer arithmetic, would “step” over consecutive ints at that address, rather than individual bytes of that int.

So, we need to get a pointer to the first byte of that int. The thing is, in C and C++, there wasn’t a data type similar to Java’s byte, so the only type that had a guarantee of occupying one byte was char. The reinterpret_cast<char const*>(&someInt) instruction tells us to fetch the address in memory of someInt (via &someInt), and then interpret that address not as a pointer to an int, but as a pointer to the first byte of that int (but we have to use char). The const is added here because we don’t need to modify the memory of our int in this operation. In the second example, we are reading, so we need to modify the bytes of our int — hence, there’s no const in reinterpret_cast<char*>(&someInt).

Seriously..?

Well, yeah.

#include <algorithm>
#include <fstream>
#include <vector>

#include <fmt/ranges.h>

auto main() -> int {
    auto ints = std::vector<int>{2, 1, 3, 7};
    fmt::println("{}", ints);

    {
        auto file = std::fstream(
            "data.bin", std::ios::out | std::ios::binary
        );
        file.write(
            reinterpret_cast<char const*>(ints.data()),
            sizeof(int) * ints.size()
        );
    }

    std::ranges::fill(ints, 0);    // resetting the values
    fmt::println("{}", ints);

    {
        auto file = std::fstream(
            "data.bin", std::ios::in | std::ios::binary
        );
        file.read(
            reinterpret_cast<char*>(ints.data()),
            sizeof(int) * ints.size()
        );
    }

    fmt::println("{}", ints);
}

Here, we obtained a pointer to the first of the ints stored in the ints vector using ints.data(). The entire internal array of these ints managed by ints occupies sizeof(int) * ints.size() bytes, so that’s exactly what we write to the file, and then read.

Problem with writing non-trivial types

int, bool, char, double, or even types like struct Point { int x; int y; } are trivial. Objects of these types can be “simply” written in binary to files. Ummm… why is the amount of occupied memory the same regardless of how many elements the container holds?

That’s because the container doesn’t actually store elements “inside”. std::vector and std::string allocate memory dynamically — after all, we don’t know how much they’ll need, right? This means they store pointer(s) to the allocated elements. A pointer always has the same size — regardless of whether it points to an array of 5 or 5000 elements.

However, attempting to write a std::vector to a file like this:

It won’t work. We’ll only save the pointer(s) that the data object holds.

To correctly save the data stored by a vector, you should do it as shown above, by saving the elements located under the .data() of the vector.

Instead of sizeof(SomeType), you can use sizeof(someObject) if it leads to simpler and clearer code.

The Cost of Text Operations

It’s hard not to notice that — at least for us — reading and writing text seems simpler than reading and writing raw bytes. So, why bother with binary files at all?

The answer is simple — the cost of operations. Computers handle data in binary, which means obtaining the textual representation of a number requires a relatively large amount of work. After all, the number 1337 written in a text file is nothing more than a sequence of four characters.

When we write an int with a value of 0 to a text file, the file will occupy 1 byte in memory. When we write the value 1337, the file will occupy 4 bytes. When we write the value 2147483647, the file will occupy 10 bytes.

But when writing these ints to a binary file, the file will always occupy 4 bytes. This is:

  • more reliable;
  • faster;
  • less complicated for larger, more complex (but still trivial) types.
