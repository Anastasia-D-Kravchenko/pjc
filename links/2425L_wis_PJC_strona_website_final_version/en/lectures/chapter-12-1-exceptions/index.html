Exceptions

Regarding exceptions in C++, there’s good news and bad news:

The good news is that using them in the “classic and correct way” is even simpler than using exceptions in Java.

The bad news is that they are actually much more complicated — especially in terms of details.

Fortunately, in 99% of cases, we can completely ignore these details. So, let’s take a look at the simplest example of using exceptions in C++:

#include <exception>    // std::exception

#include <fmt/base.h>

auto main() -> int {
    try {
        fmt::println("before `throw`");

        throw std::exception();

        fmt::println("after `throw`");
    } catch (std::exception const& ex) {
        fmt::println("Exception! Message: {}", ex.what());
    }
}

Everything looks familiar — there’s try, throw, and catch, and the code after throw doesn’t execute. There’s no .printStackTrace() or .getMessage(), but the latter method is replaced by .what(), which — as the name suggests — returns information about what happened. Everything is clear!

And that’s the reality — there are no hidden problems with the classic use of exceptions, and that’s exactly how we should use them in a classic way. Of course, we will later learn what non-classic use of exceptions means, but that’s for later. Now let’s look at some larger examples to refresh and solidify our knowledge of exceptions.

Custom messages

First up is creating an exception with a custom message. In this case, you should use std::logic_error, which directly inherits from std::exception. This is because std::exception is such a “basic” type that it doesn’t even have a constructor accepting any text!

#include <exception>    // std::exception
#include <stdexcept>    // std::logic_error

#include <fmt/base.h>

auto main() -> int {
    try {
        fmt::println("before `throw`");

        throw std::logic_error(
            "You can catch exceptions in a polymorphic manner"
        );

        fmt::println("after `throw`");
    } catch (std::exception const& ex) {
        fmt::println("Exception! Message: {}", ex.what());
    }
}

1
2

before `throw`
Exception! Message: You can catch exceptions in a polymorphic manner

As the example itself indicates, when we raise an exception of type T, we can use type U to catch it, as long as U is a base class of T. In short:

Exceptions can be caught polymorphically.

It’s also worth noting that we catch exceptions by constant reference (const&). There is no reason to copy exceptions when catching them.

Exiting from any depth of the call stack

When a function calls another function, and that function in turn calls another one, and so on, we refer to this as the call stack. What does this have to do with exceptions? Well:

Exceptions allow for exiting from any depth of the call stack.

Let’s look at an example:

#include <exception>
#include <stdexcept>

#include <fmt/base.h>

auto thisFunctionThrows() -> void {
    fmt::println("we will throw");
    throw std::logic_error("From nested call stack");
    fmt::println("we threw");
}

auto delegate() -> void {
    fmt::println("delegate begin");
    thisFunctionThrows();
    fmt::println("delegate end");
}

auto call() -> void {
    fmt::println("call begin");
    delegate();
    fmt::println("call end");
}

auto main() -> int {
    try {
        fmt::println("before `throw`");

        call();

        fmt::println("after `throw`");
    } catch (std::exception const& ex) {
        fmt::println("Exception! Message: {}", ex.what());
    }
}

One can simplify it by saying that when we raise an exception, it “looks” for the nearest catch block.

It’s worth calmly analyzing the above code, and the best way would be to step through it with a debugger. This way, you can easily see what the process of “exiting” a nested call stack looks like.

Exceptions and proper resource management

An extremely important aspect of working with exceptions is ensuring that the resources used by the application are properly managed even when exceptions occur.

Resources with automatic lifetime

Let’s see what happens to local objects when an exception is raised:

#include <exception>
#include <stdexcept>

#include <fmt/base.h>

struct Foo {
    int id;

    Foo(int id) : id(id) { fmt::println("created {}", id); }
    ~Foo() { fmt::println("destroyed {}", id); }
};

auto thisFunctionThrows() -> void {
    auto foo = Foo(3);
    throw std::logic_error("From nested call stack");
    fmt::println("we threw");
}

auto delegate() -> void {
    auto foo = Foo(2);
    thisFunctionThrows();
    fmt::println("delegate end");
}

auto call() -> void {
    auto foo = Foo(1);
    delegate();
    fmt::println("call end");
}

auto main() -> int {
    try {
        auto foo = Foo(0);

        call();

        fmt::println("after `throw`");
    } catch (std::exception const& ex) {
        fmt::println("Exception! Message: {}", ex.what());
    }
}

As you can see, the destructors of objects are correctly called, even if the created objects are deep in the call stack. This means that exceptions do not prevent us from using convenient tools such as std::vector or std::fstream freely! This is, of course, because these classes provide properly written destructors.
Resources with dynamic lifetime

Well, it’s obvious that there is no destroy N because there is no delete anywhere.
That’s true, but now we have to answer a difficult question — where should we place the delete?
Ideally, of course, before the throw, but — for example — when looking at the implementation of call():
  
1

auto call() -> void {
    auto foo = new Foo(1);
    delegate();
    fmt::println("call end");
}

And not knowing that delegate() might throw an exception (and maybe sometimes it doesn’t?), we would rather place delete foo at the end of the function, like this:
  
1
2
3
4
5
6

auto call() -> void {
    auto foo = new Foo(1);
    delegate();
    fmt::println("call end");
    delete foo;
}

Of course, this won’t work because the exception will “escape” from delegate() and “exit” from call(), causing delete foo to never be invoked.
What to do?
Take into account one of the most important features of destructors, which is:
The destructor of an object with automatic lifetime will execute when exiting the block in which the object was created.
It doesn’t matter whether we exit the block by encountering its closing brace, or by return, or by throw.
The whole problem disappears when we replace raw pointers to dynamically allocated data with smart pointers:

#include <exception>
#include <memory>
#include <stdexcept>

#include <fmt/base.h>

struct Foo {
    int id;

    Foo(int id) : id(id) { fmt::println("created {}", id); }
    ~Foo() { fmt::println("destroyed {}", id); }
};

auto thisFunctionThrows() -> void {
    auto foo = std::make_unique<Foo>(3);
    throw std::logic_error("From nested call stack");
    fmt::println("we threw");
}

auto delegate() -> void {
    auto foo = std::make_unique<Foo>(2);
    thisFunctionThrows();
    fmt::println("delegate end");
}

auto call() -> void {
    auto foo = std::make_unique<Foo>(1);
    delegate();
    fmt::println("call end");
}

auto main() -> int {
    try {
        auto foo = std::make_unique<Foo>(0);

        call();

        fmt::println("after `throw`");
    } catch (std::exception const& ex) {
        fmt::println("Exception! Message: {}", ex.what());
    }
}
