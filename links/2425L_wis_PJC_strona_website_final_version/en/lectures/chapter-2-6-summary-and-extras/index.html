Chapter 2.6 - Summary and extras

Posted Mar 6, 2025

18 min read

Iterator is a universal abstraction for accessing data

While arrays, vectors, or strings offer convenient access to stored elements through indexing, std::set (and several other containers, ranges, or data abstractions) requires the use of iterators. They are universal.

That’s why standard algorithms use them.

Iterators serve as a kind of “glue” between containers (and more) and algorithms.

CMake simplifies the process of building applications and allows for convenient management of external dependencies

CMake, configured by the CMakeLists.txt file, speeds up and simplifies the configuration of C++ applications.

Standard algorithms operate on right-open ranges

On one hand, this is an unintuitive thing to remember, but on the other hand, it allows for quickly identifying the number of elements we are working with. For example:

1
2

auto numbers = std::vector<int>{1, 2, 3, 4, 5};
numbers.erase(numbers.begin(), numbers.begin() + 3);

Seeing .begin() and .begin() + 3, we immediately know that 3 elements will be removed. If ranges were closed, we would have to add + 1 or - 1 in strange places.

It’s a bit like asking:

I’m leaving on the 24th of the month and coming back on the 26th. How many days am I gone?

For 3 days. Even though 26 - 24 == 2, you have to “add 1”.

It does carry some additional consequences. Namely:

Every dereference of the .end() iterator for a given container results in Undefined Behavior (UB).

The word “every” is crucial here, because this is the case for both direct (e.g., *someVector.end()) and indirect (e.g., someVector.erase(someVector.end())1) dereference.

In summary, algorithms consider elements from the first iterator inclusive to the last iterator exclusive. In a situation where these two iterators point to the same thing (for example, if we call std::ranges::sort(vec.begin(), vec.begin())), the range is considered “empty”. There are no elements in it. Excluding the last element “wins” over including the first element.

Use std::set or std::ranges::unique() to remove duplicates

The std::set container, when you attempt to add a duplicate to it, will simply do nothing. In addition to that, it stores its elements in ascending order (and in case of letter or words — alphabetically (plainly in accordance with the < operator))/ It means that it is a perfect candidate for storing data where we only care about its presence (not the frequency or the order of adding them)/

However, if we are already dealing with another container and we wish to remove duplicates from it, a better more performant2 option may be to employ the std::ranges::unique() algorithm — which, assuming that identical elements are grouped together, will move all the duplicates to the end of the specified range. Then, all that’s left is to remove all of them.

It’s worth using references to pass large data types that we don’t want to copy

Using references allows the programmer to work on the original object passed to the function. If the programmer wants to modify the original, using references is a very convenient way to achieve this goal.

Sometimes, however, it’s worth using references even when we don’t want to modify anything. Considering that std::string or any other container can be very large (containing a large number of elements), copying it entirely to a function just to read a few elements from it is simply wasting computer resources. Therefore, it’s worth considering using references not only to allow modification of the original but also to indicate the lack of intention to copy the entire argument.

However, in the case of very small data (e.g., int or double), such “optimization” is not applicable. If we want to pass some data to a function that occupies little memory, it is often more profitable to simply copy it instead of using references.

For now, you can use a simplified flowchart (which will be expanded at the end of this summary!):

flowchart TD
    A(What kind of<br/>a parameter to choose) --> B{Do I want<br/>to modify the<br/>original object?}
    B -->|Yes|C(By reference)
    B -->|No|D{Will copying<br/>the argument be<br/>expensive?}
    D -->|Yes|E(By reference)
    D -->|No|F(By value)

In a moment we are going to add const to this mix, so it wouldn’t be a good idea to learn this exact flowchart by heart.

  • include(FetchContent)
  • FetchContent_Declare(...)
  • FetchContent_MakeAvailable(...)
  • target_link_libraries(...)

Let’s remember that each change to the CMakeLists.txt file needs a reload, e.g., using the Ctrl+Shift+O shortcut.

There is an option to set “Reload CMake project on editing CMakeLists.txt or other CMake configuration files” in CLion, so you won’t need to manually reload the project every time you make a change. Personally, I advise against enabling this option, as editing CMakeLists.txt is usually not immediate. This means that during such an edit, CLion will try to rebuild the project multiple times, which will be very slow.

Multiple executable files in a project

Presumably, many people, in order to create a convenient form of notes while learning programming, have created a single project in which they created one file per lecture, exercise, or topic. This allowed them to have “everything in one place” at the same time, while keeping the project fragments as isolated entities.

For example, in Java, within the same project, you could create multiple files with a public, static class and a public, static main() method. This allowed for consistency in the form of code within one project, but at the same time, the code from one class (“lecture”) did not affect the other.

Effectively, we need to do exactly the same for the rest of the applications we want to create. We want the code from Lecture2.cpp and Lecture3.cpp to create separate, independent applications, so let’s add the appropriate instructions. At the end of the CMakeLists.txt file, add the following lines:

add_executable(Lecture3 Lecture3.cpp)
target_link_libraries(Lecture3 fmt)

Thanks to them, we’ll be able to run the applications in the standard way and link them with the built (only once!) {fmt} library.

Can we also put these .cpp files in folders to increase readability (especially in the future, where projects will involve multiple files per application)?

Yes, nothing prevents us from doing so. Just add the appropriate folder name before the file names in CMake.

The const keyword and references

A reference allows us to work with the original data. Instead of passing a copy to a function, we gain access to objects “from the outside.” However, a small problem arises — sometimes we want to use a reference not to modify the original, but simply to avoid a copy. Consider the following example:

1
2
3
4
5
6
7
8

#include <vector>

#include <fmt/ranges.h>

auto sumOfFirstAndLast(std::vector<int> v) -> int {
    return v.front() + v.back();
}

auto main() -> int {
    auto mutableVector = std::vector<int>();

    // change mutableVector

    auto const sum = sumOfFirstAndLast(mutableVector);

    // change mutableVector again

    fmt::print("sumOfFirstAndLast: {}\n", sum);
}

Let’s discuss its assumptions:

  1. We have a mutable (not const) vector, to which we add elements in line 12.
  2. We obtain the sum of the first and last element of the vector.
  3. We modify the vector again (line 16), but we assume that in the meantime (i.e., since the end of the code in line 12), the content of the vector has not changed.

In this situation, if mutableVector is very large, copying the entire vector to a function that effectively only reads its two elements is a huge waste of computer resources (ion terms of both memory and execution time).

This can be fixed by changing the parameter type. Instead of std::vector<int>, we will use a reference to this type, i.e., std::vector<int>&:

#include <vector>

auto sumOfFirstAndLast(std::vector<int>& v) -> int { // added &
    return v.front() + v.back();
}

auto main() -> int {
    auto mutableVector = std::vector<int>();

    // change mutableVector

    auto const sum = sumOfFirstAndLast(mutableVector);

    // change mutableVector again

    fmt::print("sumOfFirstAndLast: {}\n", sum);
}

The effect is the same, but this time we don’t copy the entire vector. Unfortunately, it’s still not the optimal solution. Remember — references allow for modification of the original object. What would happen if a programmer accidentally changed v inside the function sumOfFirstAndLast()?

No way, nobody would do that, come on.

Mhn, just like no one would ever forget whether in a given huge project we use double to represent \(\frac{\text{N}}{\text{m}^2}\) (Newtons per square meter) or pounds. Especially when we’re talking about projects costing $125,000,000 that are sponsored by the US government. Right?

Moreover, as we already know, when a C++ programmer sees the absence of const, they wonder what’s the reason that it’s not there. They assume the goal is modification.

So, how can we correctly communicate that we want to avoid copying, but at the same time, we don’t want to modify the original?

Excellent question. We should use a constant reference (const reference):

A constant reference is a tool that allows us to “look” at data in the “most proper” way. It’s worth noting that this is also the only way to “look at the original data” that is by itself constant:

The error — as it often happens in C++ — is quite unclear, so let’s translate it into “human language”:

error: binding reference of type ‘std::vector&' to 'const std::vector' discards qualifiers

This error is saying that trying to bind a reference of type std::vector<int>& to an object of type const std::vector<int> discards (required) qualifiers. Here, we’re talking about the const qualifier.

To put it simply — you cannot create a “raw reference” to a constant object. Because if you could do that, you could modify the (constant) original!

To fix this problem, you need to declare the parameter type as a constant reference:

#include <vector>

auto accept(std::vector<int> const& v) -> void { } // added const

auto main() -> int {
    auto const constVector = std::vector<int>{1, 2, 3};

    accept(constVector);
}

It’s also worth noting that a constant reference can “look” at non-constant data:

    accept(mutableVector);

Well, why would that be a problem, right? accept() promises not to modify the original — regardless of whether the original is constant or mutable.

flowchart TD
  A(What kind of<br/>a parameter to choose) --> B{Do I want<br/>to modify the<br/>original object?}
    B -->|Yes|C(By raw reference)
    B -->|No|D{Will copying<br/>the argument be<br/>expensive?}
    D -->|Yes|E(By <code>const</code> reference)
    D -->|No|F{Do I want to<br/>modify the parameter<br/>inside the function?}
    F -->|Yes|G(By raw copy)
    F -->|No|H(By <code>const</code> copy)

But what about iterators? Will they allow us to illegally modify a constant container?
