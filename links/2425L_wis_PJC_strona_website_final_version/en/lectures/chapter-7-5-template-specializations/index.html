Chapter 7.5 - Template specializations

Posted Apr 13, 2025

Creating templates and their specializations

In the Java language, one of the most popular collections is HashMap and HashSet. These are collections that store their elements in locations specified by a so-called “hash,” a numerical value calculated based on some specific logic. In Java, all objects have a .hashCode() method inherited from Object, but this is not the case in C++.

std::unordered_map and std::unordered_set (C++ equivalents of Java’s HashMap and HashSet) use function objects to calculate the respective hashes. Let’s create a simple version of such an object:

template <typename T>
struct Hasher {
    auto compute(T const& t) const -> T {
        return t;
    }
};

auto main() -> int {
    auto const intHash = Hasher<int>();

    intHash.compute(3);
    intHash.compute(214743);
    intHash.compute(-4384);
}

At first glance, this Hasher doesn’t do anything interesting. It has a .compute() method that simply returns the passed number. However, there is a problem — a hash must always be an integer, so we shouldn’t return T, but rather — for example — int. However, when we introduce this change, we’ll realize that another problem arises:

Of course, that’s a problem. As we already know, the hash for two different objects should1 be different. However, that’s not the case here. How do we fix this problem?

We can add an overload:

#include <bit>  // std::bit_cast

#include <fmt/base.h>

template <typename T>
struct Hasher {
    auto compute(T const& t) const -> int {
        return t;
    }

    auto compute(float const f) const -> int {
        return std::bit_cast<int>(f);
    }
};

auto main() -> int {
    auto const floatHash = Hasher<int>();

    fmt::println("{} {}", floatHash.compute(2.01f), floatHash.compute(2.99f));
}

1073783767 1077894185

As you can see, the values are now significantly different (by 4110418 in this case). Fantastic.

The use of std::bit_cast allows us to obtain the value of one type based on the binary representation of another type. Let’s not dwell on that for now.

On the one hand, it’s a success (because it works), but on the other hand, more problems arise, namely:

  • When we create Hasher<float>, the code won’t compile because .compute() taking T will “look” identical to our added overload.
  • When users create their own types, there’s no way to add overloads to our Hasher. And if we were to create our own hash map, we’d have to settle on some type to perform hashing for us.

We can solve this problem using template specialization.

Template specialization

Specializing a template involves explicitly implementing it for a specific type (or types). Let’s see an example:

#include <bit>

template <typename T>
struct Hasher {
    auto compute(T const& t) const -> int {
        return t;
    }
};

template <>
struct Hasher<float> {
    auto compute(float const f) const -> int {
        return std::bit_cast<int>(f);
    }
};

Now, when we create Hasher<int>, an instance will be generated based on the primary template (the one from line 3). However, if we create Hasher<float>, the specialization from line 11 will be used.

The syntax template <> tells the compiler that we’re creating a specialization. We can add more of them:

template <typename T>
struct Hasher {
    auto compute(T const& t) const -> int {
        return t;
    }
};

template <>
struct Hasher<float> {
    auto compute(float const f) const -> int {
        return std::bit_cast<int>(f);
    }
};

template <>
struct Hasher<short> {
    auto compute(short const s) const -> int {
        auto doubled = (s << 16) | s;
        return doubled;
    }
};

Most importantly, we can add a specialization for a type that we create ourselves!

template <typename T>
struct Hasher {
    auto compute(T const& t) const -> int {
        return t;
    }
};

struct Point {
    int x;
    int y;
};

template <>
struct Hasher<Point> {
    auto compute(Point const p) const -> int {
        return p.x * 31 + p.y;
    }
};

This is crucial because when we need such a mechanism, we usually use templates to adapt to the appropriate hasher. For example, std::unordered_set has such a header:

template <
        typename Key,
        typename Hash = std::hash<Key>,
        typename KeyEqual = std::equal_to<Key>,
        typename Allocator = std::allocator<Key>
> class unordered_set;

When we create std::unordered_set<int>, it effectively uses std::hash<int> (and a few other things that we’re not interested in). This also means that if we created std::unordered_set<Point>, it would use std::hash<Point>. The standard library has no knowledge of our Point type, so to make this work correctly, we would have to add our own specialization of std::hash (which we won’t do for now, as it would involve using another tool we haven’t mastered yet).

The same principle also applies to the optimal way of formatting custom types in the {fmt} library — we have to create a specialization of the fmt::formatter type there and implement the .parse() and .format() methods appropriately.

  1. It doesn’t always work out, but the implementation definitely shouldn’t just truncate the decimal part when converting each real number to an integer. ↩
