Chapter 9.3 - Summary and extras

Posted May 5, 2025
By Filip Kwiatkowski
10 min read

Inheritance

Inheritance is primarily used to represent a hierarchy of types from general to specific. The general (base class) introduces some common features and behaviors (fields and methods), and the inheriting classes can add their own new features, new behaviors, and optionally override common behaviors for all types in their hierarchy.

Because inheriting classes inherit everything the base class has, inheritance can also be used to reduce code duplication.

Encapsulation manipulation

You can inherit publicly as well as privately1. If any polymorphic behavior is of interest, public inheritance should be used. When inheriting publicly, “everyone” knows that a given class inherits from another. However, when inheriting privately, “no one else” knows about it. Private inheritance can be used for delegating work when creating custom methods or exposing some of them.

The process of exposing such methods is very useful. For example, let’s say we want to create a custom type representing a stack (data structure), where elements can only be added at the end, removed only from the end, and there is possible access only to the last element. This can be achieved in several ways:

// private inheritance by default for classes
class Stack : std::vector<int> {
public:
    auto push(int const n) -> void {
        push_back(n);
    }

    auto pop() -> void {
        pop_back();
    }

    auto top() const -> int {
        return back();
    }
};

However, if we’re not interested in changing the method names and we’re satisfied with those provided by std::vector, we can do the following:

// private inheritance by default for classes
class Stack : std::vector<int> {
public:
    using std::vector<int>::push_back;
    using std::vector<int>::pop_back;
    using std::vector<int>::back;
};

In such a Stack, you can call methods like .push_back(), .pop_back(), or .back().

Polymorphism

Polymorphism in C++ requires the use of virtual methods and careful handling to avoid the problem of object slicing. In Java, this problem does not exist because all methods are inherently virtual, and due to Java’s reference semantics, object slicing is not an issue.

We denote virtual methods with the keyword virtual, and we mitigate object slicing by using references.

Pure virtual methods

In Java, a method without a body that must be overridden is called an “abstract” method. A class with an abstract method is called an “abstract class.” In C++, sometimes instead of “abstract method,” we often use the term “pure virtual method.” Pure virtual methods have no body and are marked with the syntax = 0;.

struct Animal {
    virtual auto makeSound() const -> void = 0; // pure virtual
};

struct Cat : Animal {
    auto makeSound() const -> void {
        fmt::println("Meow");
    }
};

struct Dog : Animal {
    auto makeSound() const -> void {
        fmt::println("Woof");
    }
};

Class that contains a pure virtual method becomes abstract, and it’s not possible to create objects of that class.

Multiple Inheritance

C++ supports multiple inheritance, unlike Java. A single class can inherit from any number of classes. This is achieved quite simply — after the class from which another class inherits, you simply put a comma.

For example, you can specify that class A inherits from classes B and C like this: struct A : B, C { };.

This is not possible in Java, but this language does not face the problems associated with the limitations resulting from this decision. This is because Java allows the implementation of multiple interfaces simultaneously. C++ does not distinguish between a class with only methods and an interface, so both concepts are realized by the same language element. Hence the need to allow multiple inheritance.

As a rule, it should be avoided because it carries the risk of encountering the “dreaded diamond problem”.

flowchart BT
    D(D) --> |inherits from|C(C)
    D --> |inherits from|B(B)
    B --> |inherits from|A(A)
    C --> |inherits from|A

In the above inheritance diagram, we see that both C and B inherit (separately) from A (without knowing anything about each other). Then the class D inherits from both of these classes.

The problem in this situation is that if A consists of some field (e.g., int x), then both B and C will inherit this field. This, in itself, is not problematic (after all, inheritance works this way!).

The problem arises because now the class D, inheriting from both B and C, will inherit int x from both B and C separately. This means that D consists not of one, but of two ints!

This problem can be observed using the sizeof() operator, which returns information about the number of bytes occupied by a given type or object. Like so:

    fmt::println("Size of A is {} bytes", sizeof(A));
    fmt::println("Size of B is {} bytes", sizeof(B));
    fmt::println("Size of C is {} bytes", sizeof(C));
    fmt::println("Size of D is {} bytes", sizeof(D));

    fmt::println("Size of C is {} bytes", sizeof(C));
    fmt::println("Size of D is {} bytes", sizeof(D));
}

Additionally, it’s worth noting that when creating B and C, we don’t know if someone will want to inherit from both of these classes at the same time, so we don’t know if we should use virtual inheritance. As seen, it’s not free. The general consensus is not to use it.

The override Keyword

In Java, we used the @Override annotation to instruct the compiler to check if we correctly override a method. This annotation was placed above the method in the derived (inheriting) class, causing the compiler to look at its signature and compare it with methods from the base class. If there was a method in the base class with a compatible signature that could be overridden (not final), the compilation proceeded to the next stages. However, if there wasn’t, the compilation stopped and returned an error.

In C++, we don’t have annotations. Instead, we have the override specifier, which we can place right before the method body. Its effect will be identical to what we expect when using the @Override annotation in Java. For example, considering the known hierarchy of animals:

We can enrich the overridden methods in Cat and Dog with the override specifier:

struct Animal {
    virtual auto makeSound() const -> void { }
};

struct Cat : Animal {
    auto makeSound() const -> void override {
        fmt::println("Meow");
    }
};

struct Dog : Animal {
    auto makeSound() const -> void override {
        fmt::println("Woof");
    }
};

This achieves two goals:

  1. The compiler will assist us in situations where we make a typo. It will also help us detect errors if we change the name of a method in the base class and forget to change those names in the derived classes.
  2. It’s immediately visible that a given method is part of a polymorphic hierarchy of overridden functionalities. We could achieve the same result by repeating the word virtual before each of these methods, but this is not a common practice. Instead, override is much more commonly used.

  1. In reality, you can also inherit in a protected manner (protected). Additionally, each of these types of inheritance can be enriched with the virtual keyword, representing virtual inheritance, which is mentioned in this subtext. However, because these inheritances are extremely rare, they have been described very sparingly in this chapter. ↩
