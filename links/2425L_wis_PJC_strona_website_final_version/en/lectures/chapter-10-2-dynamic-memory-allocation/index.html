Chapter 10.2 - Dynamic memory allocation

Posted May 7, 2025
By Filip Kwiatkowski
6 min read

Objects with automatic storage duration and dynamic storage duration

Value semantics, objects with automatic storage duration, The Big Three… All these concepts revolve around the behavior and lifecycle of objects, which we have discussed so far.

An object dies the moment we exit the block in which it was created.

The above is true only for objects with automatic storage duration.

The only way for a program to allocate memory is either by knowing “upfront” how much it will need in a given place, or by asking the operating system to allocate memory dynamically.

Examples of situations where our program knows how much memory it will need include:

  • Passing an argument to a function — eventually, the function must copy this argument within its parameter. The type is known to us at compile time, so we know how much memory we need to allocate.
  • Copying some primitive variable1, like an int — after all, the compiler knows where and when we copy certain numbers. An int always takes up the same amount of space on a given machine.

An example of when our program has no idea how much memory it will need is, for example, adding elements to a vector. If, for instance, we’re reading lines from a file, during compilation, we have no idea how many of these lines there will be. Such an std::vector<std::string> storing lines has no idea how many std::strings it will need to allocate.

In such situations, dynamic memory allocation should be used.

If we don’t know how much memory our program will need to function properly, we should use dynamic memory allocation.

Let’s say we want to write a program that creates either 2 ints or 5 ints. Randomly. We won’t use any container because it would effectively delegate only to dynamic memory allocation. Let’s see how to use it “manually”:

Dynamic memory allocation

To ask the operating system for memory in amounts unknown before running the code, you should use the new keyword:

auto getEither2or5() -> int;

auto main() -> int {
    auto twoOrFive = getEither2or5();
    new int[twoOrFive];
}

The syntax new int[N] will result in the following operations:

  1. The program will ask the operating system to allocate memory (e.g., from RAM2) to accommodate N objects of type int, usually \(N*4\), because an int typically occupies 4 bytes.
  2. If the operating system can afford to allocate such memory, it will reserve the appropriate amount and mark it as available for our program.
  3. The program will create the appropriate number of ints in this memory.

The new operator exists in two variants — the array version (new[]) and the “ordinary” version (new). Above, we presented the array version, which effectively created an array of N ints.

All standard library containers that allow adding and removing elements from them use the new operator (in either ordinary or array version).

It’s worth noting that we can also create “ordinary” objects using new:

So the question arises — if sometimes we need to use dynamic memory allocation (i.e., use new), why don’t we always use it?

That’s because dynamic memory allocation:

  • is somewhat slower than creating objects with automatic lifetime (without new).
  • results in creating objects with dynamic lifetime rather than automatic.

The latter issue is crucial. Let’s look at an example:

        fmt::println("The beginning of ({})", message);

        fmt::println("The end of ({})", message);
    };
};

auto createWithAutomaticStorageDuration() -> void {
    auto s = Speaker("automatic");
    fmt::println("Random text");
}

auto createWithDynamicStorageDuration() -> void {
    auto s = new Speaker("dynamic");
    fmt::println("Random text");
}

auto main() -> int {
    createWithAutomaticStorageDuration();
    createWithDynamicStorageDuration();
}

Clearly, the output is missing the text The end of (dynamic). This is because the Speaker object created within the createWithDynamicStorageDuration() function call was not deleted from memory, and its destructor was not called.

It’s worth pausing for a moment and realizing the significance of what has been written above. The Speaker object still exists in memory. It will persist there until the program finishes execution.

Variables with dynamic lifetime are not automatically removed from the program’s memory.

This is extremely important, so let’s repeat this information:

Variables with dynamic lifetime are not automatically removed from the program’s memory.

To remove a variable with dynamic lifetime, one must manually initiate the process of calling its destructor and inform the operating system that we are releasing the memory previously allocated to us. This is done using the delete keyword (or sometimes delete[], but that will be covered in subsequent chapters):

#include <string>

#include <fmt/base.h>

struct Speaker {
    std::string message;

    Speaker(std::string const& msg) : message(msg) {
        fmt::println("The beginning of ({})", message);
    };
    ~Speaker() {
        fmt::println("The end of ({})", message);
    };
};

auto createWithAutomaticStorageDuration() -> void {
    auto s = Speaker("automatic");
    fmt::println("Random text");
}

auto createWithDynamicStorageDuration() -> void {
    auto s = new Speaker("dynamic");
    fmt::println("Random text");
    delete s;   // new operation!
}

auto main() -> int {
    createWithAutomaticStorageDuration();
    createWithDynamicStorageDuration();
}

It’s immediately apparent that there is a certain problem with dynamic memory allocation — it requires manual management. This is inconvenient, error-prone, and slightly less efficient than using objects with automatic lifetime, so we should prefer the latter way of operating on data.

The situation where we allocate memory but do not release it, thereby losing access to it (e.g., when we do new int() and do not save the address of the allocated object), is called a memory leak.

Memory leaks are situations to be avoided almost as much as Undefined Behavior (UB). A program that continuously leaks memory will eventually consume so much of it that the operating system won’t be able to allocate any more. In such a situation, the system will likely start to operate very slowly, and our application will eventually be forcibly stopped.

Unfortunately, sometimes we have to resort to dynamic memory allocation. That’s how std::vector works. Let’s see exactly how it works, but first, let’s find out precisely what new returns.
