Chapter 5.1 - Standard containers

Posted Mar 30, 2025
By Filip Kwiatkowski
16 min read

Previously encountered standard containers

As we know, a container is a fundamental abstraction for a collection of data. It allows us to operate on large amounts of data that are “gathered” into a single object. It’s worth knowing that practically any container can be used to achieve any goal. However, this doesn’t mean that using the same one every time would always be a good idea.

There’s nothing stopping us from using std::vector<char> instead of std::string. There’s nothing stopping us from using std::vector<int> instead of std::set<int>, as long as we carefully maintain it to always be sorted and to always contain unique elements.

However, a fundamental question arises — why? Why would we want to make our lives more difficult?

Having a wider range of tools at our disposal (in this context — different containers), we can choose the one that will make our work easier. Therefore, it’s worth reminding ourselves of the containers we already know, when it’s worth using them, and in which cases using new containers might be better.

std::string container

When dealing with characters representing some text (a set of words, a single word, a sequence of random characters, etc.), we should use std::string. This container offers many conveniences in the form of methods that allow manipulation of text. Concatenation using + or +=, analyzing the beginning and end with .starts_with() and .ends_with(), or operations on substrings (thanks to the .substr() method and the std::string_view class) are just a few among a wide range of tools that can help us.

However, it’s worth noting that a word, term, and set of characters are different things. Of course, std::string should be the first container that comes to mind when thinking about an object that should store characters. Nevertheless, it’s not always the best choice.

A word is a term that carries some linguistic meaning. When storing a user’s name, input message (e.g., in a chat), or maybe the name of a conversation group, it’s worth using std::string.

A term is a set of characters that has no linguistic-informational meaning in a given context. Imagine we’re creating a system where a user has to register. As part of this registration, they have to come up with a password. We want our system to assist users in choosing a strong password. At the same time, we want to discourage users from using the most popular, easy-to-break passwords, such as qwerty, password, 123456, and similar.

When a user wants to enter their password, it’s worth checking if it’s identical to one we consider too simple. But how will we store these mentioned passwords (qwerty, password, 123456, etc.)? As std::string? We probably won’t display or modify them. Perhaps it’s better to use std::vector<char>.

A set of characters also sounds like something for which std::string would be ideal. Elements can be added to and removed from a set. However, when we face a specific example, it quickly becomes clear that another container would be better.

Let’s assume we want to examine how many different characters make up the content of a text file. We can read the entire file into std::string and then remove duplicates using the sort-unique mechanism.

But text files can be enormous. It’s worth considering using a container that won’t allow duplicates. In such a case, std::set<char> would be much better.

std::vector container

The vector should be the primary container we turn to every time we need to represent a collection of data. Only when it turns out that another container is better do we stop using the vector. Vector is straightforward, vector is fast, vector is convenient. There’s not much more to say here.

std::set container

std::set stores its elements in the order determined by the user (by default, they are sorted in ascending order). Additionally, it does not allow duplicates to be inserted. It’s clear that it’s worth using when we’re interested in a consistently sorted order of elements and/or their uniqueness. However, the less obvious fact is that these two attributes offer another interesting feature — in std::set, we can quickly find, add, and remove elements.

Therefore, it is the ideal container for storing data that needs to be frequently referenced. For example, a set of banned passwords or a set of characters in a specific category.

New standard containers

As usual, we’ll start by presenting a problem that we can solve using tools we already know. However, this solution won’t be “elegant.” Later, using new tools, we’ll show how to do it much easier.

Write a program that will read the path to a file from the user and display the characters along with their frequencies.

For the sake of simplification and focusing only on the new elements, let’s assume that we have already read the content of the file into an object of type std::string. So how do we count the frequency of all characters?

There are many solutions. For example, we could copy the entire content of the file, remove duplicates from it, and then iterate over the unique characters, counting their frequency in the original content of the file. It would look like this:

    std::ranges::sort(uniqueCharacters);
    auto const duplicates = std::ranges::unique(uniqueCharacters);

    for (auto const c : uniqueCharacters) {
        fmt::println(
                "'{}' occurred {} times",
                c, std::ranges::count(fileContent, c)
        );
    }
}

#include <algorithm>

auto main() -> int {

                c, std::ranges::count(fileContent, c)
        );

}

The output is the same.

However, it’s hard not to notice that when fileContent is very large, iterating over each unique character, which requires iterating over the entire file content each time, is a waste of time. Eventually, we could go through the entire fileContent once and store the character frequencies somewhere alongside. This could be achieved by using a vector of numbers with a length equal to the number of all possible characters. Limiting ourselves only to ASCII, this would be 128. A similar task might have appeared in the Basics of Programming in Java course.

#include <algorithm>
#include <string>
#include <vector>

#include <fmt/base.h>

auto main() -> int {
    auto const fileContent = std::string("some random text appears here");

    auto const totalNumberOfASCIICharacters = 128;
    auto occurrences = std::vector<int>(totalNumberOfASCIICharacters);

    for (auto const c : fileContent) {
        occurrences[c] += 1;
    }

    for (auto i = 0; i < occurrences.size(); i++) {
        if (occurrences[i] > 0) {
            fmt::println(
                    "'{}' occurred {} times",
                    static_cast<char>(i),
                    occurrences[i]
            );
        }
    }
}

static_cast<char>(i) is the C++ version of explicit conversion. In Java, we would use (char)i, and while in C++ that would also work, it’s preferred to use static_cast<>() for the sake of safety and visibility of the conversion. Generally, one should be cautious with conversions, so making them “stand out” is considered a good feature. However, not everyone agrees with this approach.

The above listing again results in displaying the same output as the two previous ones.

However, it’s hard not to notice that this vector contains a lot of empty spaces. Nowhere do we use the letter 'v' or uppercase letters or special characters.

The ideal solution would combine simplicity and efficiency. Fortunately, there is a container that allows us to achieve this goal. It’s called a map.

std::map container

Maps are containers that store key-value pairs. So far, when we created vectors or sets, we specified a single template type, for example:

  • std::vector<int> or std::set<int>;
  • std::vector<std::string> or std::set<std::string>;
  • std::vector<double> or std::set<double>.

In each of these pairs, there was only one type in angle brackets (<...>). With maps, it’s different — we provide two types there. The first one is the key type, and the second one is the value type.

In the template arguments of std::map, we provide two types. The first one is the key type, and the second one is the value type.

However, before we delve into the theory of maps, let’s look at the solution to the discussed problem and analyze how much a map helps us:

#include <algorithm>
#include <map>
#include <string>

#include <fmt/base.h>

auto main() -> int {
    auto const fileContent = std::string("some random text appears here");

    auto occurrences = std::map<char, int>();

    for (auto const c : fileContent) {
        occurrences[c] += 1;
    }

    for (auto const& charAndCount : occurrences) {
        fmt::println(
                "'{}' occurred {} times",
                charAndCount.first,
                charAndCount.second
        );
    }
}

Let’s analyze the next key sections of the code.

1

auto occurrences = std::map<char, int>();

Here, a map is being created to associate characters with their frequencies. Characters are represented as char types, and frequencies as int types. The use of a map represents the concept of association. A map represents a collection of keys, each associated with values.

1
2
3

for (auto const c : fileContent) {
    occurrences[c] += 1;
}

Maps are indexed not by numbers, but by their keys.

In our case, the keys are chars.

When indexing a map by key, we access the value associated with that key.

If we refer to a non-existent key in the map, it will be added with a default value.

That’s why in the first iteration of the loop (when c == 's'), referring to a non-existent key adds it to the map with the associated value of 0. Then, we immediately get a reference to that zero, which we increment using += 1.

This logic repeats until we encounter a repeated letter (in the case above, it’s the second letter 'o'). In such a case, a new identical key won’t be added. Instead, we’ll simply get access to the associated value 1, which we’ll increment by 1. This way, when we encounter the second occurrence of a letter, the associated value in the map will be 2.

In this snippet, we display the contents of our map. Its elements are key-value pairs. Each charAndCount is an std::pair, which holds a char as its first element (as the key) and an int as its second element (as the value). Access to individual elements is provided to us through the public fields .first and .second.

As you can see, the map allows us to conveniently associate two types of data. It’s useful for representing various kinds of relationships. For example, if we wanted to represent a container of bus stops with additional information about which stops can be reached from a selected one, a good idea would be to consider using an object of type std::map<std::string, std::set<std::string>>. The key would be the name of a bus stop, and the value associated with this key would be a set of bus stop names reachable from it.

Structured Bindings

While we’re on the topic of maps, it’s worth getting to know an interesting tool that can reduce unnecessarily complex programming constructs. These are called structured bindings.

In the previous listing, we saw that the charAndCount object is a structure that contains two objects - .first and .second. To demonstrate how structural bindings can help us simplify this code fragment, let’s see how they work with a simple pair object we create:

#include <utility>  // std::pair

#include <fmt/base.h>

auto main() -> int {
    auto const pair = std::pair<char, int>('a', 5);

    auto const [c, i] = pair;

    fmt::println("{} {}", c, i);
}

1

a 5

Here are two important code snippets:

  1. auto pair = std::pair<char, int>('a', 5);
  2. auto [c, i] = pair;

The first snippet is a simple construction of an object that is a pair. Calling pair.first gives us access to the char with the value 'a', and pair.second to the int with the value 5.

The more interesting part is the second instruction. Here, we’re dealing with a structured binding, which creates a copy of the pair object and introduces two names into the current scope - c and i. c refers to .first of the mentioned copy, and i refers to .second of the same copy.

Structured bindings allow us to introduce names that refer to parts (e.g., fields) of objects. It’s worth using them when we don’t need to refer to the entire object, only to its components.

Naturally, we can avoid the mentioned copy by using references, i.e., replacing auto [c, i] = pair; with auto& [c, i] = pair; (we added & after auto).

So, how can we use structured bindings in the example with a map? We can replace this part of the code:

With this one:

    fmt::println("'{}' occurred {} times", c, count);
}

Thanks to this, during each iteration, each key-value pair from the map will be “decomposed” into c and count, referring to its .first and .second, respectively. This allows us to omit the name of the entire pair.

Structural bindings can be used in a variety of cases. In the previous part of this chapter, we came across the following code snippet:

The object duplicates holds two iterators, which can be accessed via .begin() and .end(). However, we can use structural bindings to eliminate the need to name the entire duplicates subrange:

auto uniqueCharacters = fileContent;
std::ranges::sort(uniqueCharacters);
auto const [from, to] = std::ranges::unique(uniqueCharacters);
uniqueCharacters.erase(from, to);

std::deque container

Let’s recall the moment when we learned that std::vector is generally the best container “to start with.” One of its drawbacks was that adding elements to its beginning is highly inefficient. The std::deque1 container fixes this issue at the cost of a minimal decrease in the efficiency of other operations.

That’s it. If we need precisely std::vector and we add elements to both the beginning and the end with the same frequency, it’s worth considering std::deque, which, since it offers additional methods like .push_front() and .pop_front(), explicitly indicates that these operations are implemented efficiently in this container.

std::array container

An array is often the first collection/container someone learns. Like all containers, it has its pros and cons. An obvious downside may seem to be its fixed size, but sometimes we want a segment of memory of a constant size reserved for a process. Data buffers are a prime example.

In C++, std::array requires defining the size of the array as part of the type. This means that unlike in Java, when creating an array variable, you cannot later assign a larger or smaller array to it. If we want a variable-sized array that can change its size, we use a vector.

Here’s an example of using std::array:

Container adaptors

Contrary to initial intuition, sometimes it’s desirable to deliberately limit the capabilities offered by the objects we use in a program. We do this to convey more information.

For example, std::queue represents a queue. Elements are added to the end of the queue and removed only from the front. Formally, std::deque can model this phenomenally — we would use only .pop_front() and .push_back(). However, using std::queue (which internally relies on std::deque), which restricts us to practically these two operations, explicitly indicates that the business need discourages the use of the rest of the operations available in std::deque.

There are more adapters, but at this point, the three most important ones are:

  • std::queue, which has been described above;
  • std::stack, which allows adding and removing only from its “top”;
  • std::priority_queue, a queue (thus supporting only removal from the front and addition to the end), which, however, does not maintain the order of adding elements but arranges them according to some priority. It usually represents an abstraction over a binary heap.

  1. deque is pronounced as “deck.” Just like a deck of cards. ↩
